# ADR-0013：公共域分层持久化与检索增强

> 状态：已批准 · 日期：2026-10-13 · 决策者：首席架构师、数据负责人 · 批准：项目负责人

## 背景

信源数据（原始网页、附件、正文）是平台体量最大的数据，写入后基本不变，主要用于检索、证据查看和重新处理。把它们全部放进 PostgreSQL 会挤占事务数据库的容量与性能，也不利于检索质量的持续改进：每次改进分类、标签或分词，都需要对历史内容批量重新处理并重建索引。

## 决策

1. 公共域数据分为五层：L0 原始层、L1 规范化层、L3 增强层存放于**对象存储**（权威、不可变或按版本追加）；L2 结构层存放于 **PostgreSQL**（只含结构化字段、元数据、证据定位符、实体与关系）；L4 检索层存放于 **OpenSearch**（派生、版本化、可重建）。
2. 正文、附件文本、分块、AI 增强结果和向量不进入 PostgreSQL。
3. 设立**增强层**：由 `evidence` 的增强管线运行规则与 AI 增强器（文档分类、品类分类、标的抽取、实体提及、业务标签、摘要、分块向量），结果按“增强器 × 版本”存放，可整体重算、可回退；公共域增强按内容哈希只计算一次，全租户复用。
4. 区分**领域事实字段**（权威、带证据、用于判断）与**检索增强**（概率性、带置信度、用于召回与排序）；增强结果经质量评估可被解析器采纳为领域事实字段。
5. 检索层采用**版本化索引 + 别名切换**；映射、分析器、词表、标签体系或生效增强器变化时构建新版本索引，经相关性评估不劣化后切换。
6. 按月生成 **Parquet 语料快照**，供批量重算增强、评估与模型调优；批处理在工作流 worker 中以嵌入式工具（Arrow / DuckDB）执行，不引入独立数据湖服务。

## 备选

- **全部存 PostgreSQL**：实现简单，但大文本挤占事务库，批量重算低效；拒绝。
- **以 OpenSearch 作为正文权威存储**：OpenSearch 不适合作为唯一原件，映射变更需重建且存在数据丢失风险；拒绝，OpenSearch 只作派生层。
- **独立数据湖（如 Iceberg + 查询引擎）**：当前规模下运维成本高于收益；语料快照已满足批处理需求。规模或分析需求显著增长时再评估。

## 后果

- 正面：PostgreSQL 只承担结构化数据，容量与性能可控；对象存储成本低且天然适合不可变数据；
- 正面：检索质量可以通过“新增强器 → 批量重算 → 新索引 → 评估 → 切换”的闭环持续改进，并可回退；
- 代价：证据查看需要从对象存储读取规范化文档（通过缓存与签名地址降低延迟）；
- 代价：需要建设增强管线、语料快照、索引版本管理与相关性评估体系；
