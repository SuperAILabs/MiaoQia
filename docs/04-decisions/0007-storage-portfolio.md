# ADR-0007：存储组合

> 状态：提议 · 日期：2026-10-12 · 决策者：首席架构师、产品负责人

## 背景

平台需要事务一致性、海量原始文件、中文全文与语义检索、订阅反查、大规模统计、多跳关系查询。

## 决策

| 需求 | 存储 | 角色 |
|---|---|---|
| 结构化事务数据（公共域结构层、全部租户与平台数据） | PostgreSQL（每子系统独立逻辑数据库与账号，RLS） | 权威 |
| 原始制品、规范化正文与分块、AI 增强结果、语料快照、文件 | S3 兼容对象存储 | 权威 |
| 检索、语义、订阅反查（版本化索引） | OpenSearch | 派生 |
| 统计、审计、计量、仿真计算 | PostgreSQL 分区表 + 统计汇总表 + 只读副本 | 权威或派生 |
| 缓存与限流 | Valkey（Redis 协议，ADR-0015） | 非权威 |
| 多跳关系查询 | 图查询引擎读模型（引擎经基准测试选定） | 派生 |

图查询以 `entity-graph.GraphQuery` 接口固定契约，引擎作为可替换投影，权威关系始终在 PostgreSQL。

公共域内容的分层方式见 ADR-0013。

## 备选

- **ClickHouse 等列式分析库**：评估后不引入。预估数据规模（公告千万级、组织千万级、关系千万至亿级、审计与计量每日百万级以内）在 PostgreSQL 分区、汇总表与只读副本的能力范围内；多一套存储会增加运维和数据同步成本。统计查询接口已固定，将来出现面向客户的交互式多维分析且现有方案无法满足时，以新 ADR 引入，调用方不受影响。

## 后果

- 正面：每类负载使用合适引擎；派生存储均可重建；
- 代价：运维面较大；需要完善的投影与重建工具。
