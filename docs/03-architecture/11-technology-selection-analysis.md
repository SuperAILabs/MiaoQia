# 技术选型分析

> 状态：评审中 · 版本：1.0 · 更新：2026-10-13 · 负责人：首席架构师

本文是技术选型专题的分析底稿，记录每项选型的需求依据、候选对比与推荐结论。结论以 ADR 固化（ADR-0014、ADR-0015、ADR-0016），选型清单见 [技术选型](08-technology-stack.md)。

## 0. 专题输入：项目负责人确定的方向（2026-10-13）

| 编号 | 方向 | 对本文的影响 |
|---|---|---|
| D1 | 服务端不全部使用 Python；数据抓取与数据维护面使用 Python，平台服务在 Go 与 TypeScript 中经对比选定 | 第 2 节：按负载拆分语言边界并对比 |
| D2 | 不依赖任何云厂商的专有服务；能自建的开源方案全部自建，除非托管价格优势明显 | 第 3 节：逐项自建方案与价格例外判断 |
| D3 | AI 推理前期只接 API，不做私有部署，不考虑 GPU | 第 4 节：模型网关、嵌入、OCR、敏感数据路由 |
| D4 | 基础设施搭建工作量不作为否决理由（由编码 Agent 承担大部分搭建工作） | 选型以长期运行质量、许可证与可迁移性为准；**日常运维（升级、备份恢复、扩容、故障）仍计入成本** |

## 1. 从项目需求推导的选型约束

| 需求 | 出处 | 约束 |
|---|---|---|
| 数据供应平面以解析、OCR、抽取、实体解析、增强为核心 | `evidence`、`entity-graph`、ADR-0013 | 需要 Python 的文档与 NLP 生态；信息领域包的代码型 SPI（`SourceHandler`、`Extractor`、`Enricher`、`Aggregator`、`RelationExtractor`）由领域团队大量编写 |
| 公共域与租户域物理分离，数据供应平面不读取租户数据 | 总体架构原则 4 | 语言边界最好与“公共域 / 租户域”边界重合，安全边界即部署边界 |
| 每日百万级信号匹配；领域事件到信号 P95 < 1 分钟 | `detection` | 确定性匹配是 CPU 密集的热路径；策略 DSL 需要安全、可限时的表达式求值 |
| 交互式检索 P95 ≤ 500 毫秒；订阅反查 | `search`、质量与验收 | 在线查询热路径，需高并发与稳定尾延迟 |
| 万级租户；REST、BFF、MCP、Webhook；渠道长连接 | `gateway`、`channels` | 高并发 I/O、长连接、流式输出 |
| 研究运行是长时、多步、可中断的工作流 | ADR-0005、ADR-0010 | Temporal SDK 的成熟度是 `research` 选语言的首要因素 |
| 契约先行：OpenAPI、AsyncAPI、JSON Schema 生成多端代码 | 集成契约 | 每种语言都必须有可靠的契约代码生成 |
| 专属单元与私有部署使用同一套代码与清单 | ADR-0008、商业模式 | 全部组件可离线安装；许可证允许向客户分发 |
| 等保、生成式 AI 合规 | 立项清单 B4/B5 | 供应链可审计；依赖数量与来源可控 |

## 2. 服务端语言

### 2.1 按负载对子系统分类

| 负载类别 | 子系统 | 特征 |
|---|---|---|
| **A 数据处理型** | `acquisition`、`evidence`、`domain-intelligence`、`entity-graph` | 抓取、文档解析、OCR、抽取、规则与模型增强、实体解析；大量领域包代码；只处理公共域数据 |
| **B 在线检索型** | `search` | 在线查询热路径；同时持有租户数据（订阅查询、租户私有索引）；映射与词表声明式注册 |
| **C 事务与规则型** | `customer-context`、`detection`、`assessment`、`pursuit`、`identity`、`commerce`、`governance`、`operations` | 事务、状态机、审批、策略编译与求值、审计；处理租户数据 |
| **D 编排与 AI 调用型** | `research`、`learning`、`ai-platform` | Temporal 长流程、模型调用、工具调用、计量；`ai-platform` 是高并发流式代理 |
| **E 接入型** | `gateway`、`channels` | 高并发 I/O、长连接、MCP、Webhook、渠道回调 |

### 2.2 A 类保持 Python 的依据

| 依据 | 说明 |
|---|---|
| 生态不可替代 | Playwright、lxml/selectolax、pdfplumber/pypdfium2、PaddleOCR、python-docx/openpyxl、jieba 等分词、rapidfuzz 等相似度库、Arrow/DuckDB/Parquet，以及抽取与分类的模型工具链，Go 与 TypeScript 都没有同等完整的替代 |
| 领域包作者 | 信息领域包是长期增长最快的代码，作者是数据与领域工程师，Python 门槛最低 |
| 只处理公共域 | A 类子系统不读取租户数据，Python 部署单元可以整体划为公共域，安全边界清晰 |
| 已有实践 | Tender Intel 原型的采集与解析经验来自 Python |

例外：客户上传的授权文档（租户知识资产）也由 `evidence` 解析。处理租户文档的 `document-worker` 以租户单元为范围单独部署（同一代码，单元级实例与凭证），不与公共域实例混用。

### 2.3 B–E 类：Go 与 TypeScript 对比

评分为 1–5（5 最好），权重按本项目需求设定。

| 维度 | 权重 | Go | TypeScript（Node.js） | 依据 |
|---|---|---|---|---|
| Temporal SDK 成熟度 | 高 | **5** | 4 | Temporal 服务端以 Go 编写，Go SDK 是参考实现，功能最先到位，并有 `workflowcheck` 静态检查确定性；TS SDK 成熟，以 V8 沙箱保证确定性，但资源开销更大 |
| Kafka 客户端 | 高 | **5** | 3 | Go 有 franz-go（纯 Go、性能与功能完整、维护活跃）；Node 生态中 KafkaJS 长期缺乏维护，Confluent 的 librdkafka 绑定较新，需原生模块构建 |
| 策略 DSL 与特征函数求值 | 高 | **5** | 3 | `cel-go` 是 CEL 的参考实现：非图灵完备、确定性、可做静态类型检查与成本上限，正好满足 SPI 规范中“确定性、无副作用、资源限制”；JS 的 CEL 实现成熟度低，自研表达式沙箱风险高 |
| 匹配热路径性能 | 高 | **5** | 3 | 匹配是 CPU 密集的确定性计算；Go 多核并行、内存占用低、尾延迟稳定；Node 单线程事件循环需 worker_threads 拆分 CPU 任务 |
| 高并发 I/O 与长连接 | 中 | **5** | 4 | 两者都适合；Go 的 goroutine 对渠道长连接、流式代理（`ai-platform`）、Webhook 并发投递更直接 |
| PostgreSQL 与 RLS | 中 | **5** | 4 | Go：pgx + sqlc（SQL 优先、编译期类型安全、会话变量设置直接）；TS：Kysely/Drizzle 可行，Prisma 对 RLS 会话变量支持不佳 |
| 契约代码生成 | 中 | 4 | **5** | TS 的 OpenAPI/JSON Schema 类型生成最完整；Go 的 ogen/oapi-codegen 可用，但 `oneOf` 等联合类型表达较笨重 |
| 领域建模表达力 | 中 | 3 | **5** | TS 有可辨识联合、字面量类型，适合研究报告、策略、机会路径等复杂结构；Go 无和类型，需靠代码生成与约定弥补 |
| LLM 与 MCP 生态 | 中 | 4 | **5** | TS 的 MCP SDK 与 LLM 工具链最丰富；Go 有官方 MCP Go SDK 与主流模型官方 SDK。模型网关自研、国内供应商普遍提供 OpenAI 兼容协议，差距对本项目影响有限 |
| 渠道 SDK | 低 | 4 | 4 | 飞书、钉钉都有官方 Go 与 Node SDK（含长连接模式）；企业微信两边都依赖社区实现或直接调用 HTTP API。OpenClaw 等参考项目是 TypeScript，但本项目只借鉴其模式（见 `channels`） |
| 与前端共享 | 低 | 2 | **5** | TS 前后端同语言；但契约先行后，前端类型由 OpenAPI 生成，共享代码的实际收益主要在 BFF |
| 部署与私有化 | 中 | **5** | 3 | Go 单一静态二进制、镜像小、启动快、内存低，适合多进程角色与客户机房离线部署；Node 需运行时与 `node_modules` |
| 供应链安全 | 中 | **5** | 2 | Go 依赖少、模块校验和数据库与最小版本选择；npm 依赖树深、近年多次投毒事件，对等保与私有部署交付的审计负担更大 |
| 招聘（中国大陆后端） | 中 | **5** | 3 | 国内后端 Go 人才池大且集中在高并发服务；Node 服务端人才相对少 |
| 编码 Agent 产出质量 | 中 | **5** | 4 | Go 语言面小、风格统一（gofmt）、编译期检查严格、编译快，Agent 生成的代码差异小、易评审；TS 的灵活性带来更大的写法差异，运行时校验依赖额外约定 |
| **加权结论** | | **胜出** | | Go 在本项目权重最高的维度（工作流、事件、策略求值、匹配性能、私有化、供应链）全面领先；TS 的优势集中在类型表达力与前端共享，可通过契约生成弥补 |

**推荐：B–E 类全部使用 Go。** TypeScript 只用于前端（Web 应用与运营控制台），服务端不引入第三种语言。BFF 由 Go 的 `gateway` 实现。

### 2.4 边界子系统的归属判断

| 子系统 | 结论 | 依据 |
|---|---|---|
| `search` | **Go** | 在线检索与订阅反查是全平台热路径（`detection`、研究工具、`gateway` 都调用）；持有租户订阅查询与租户私有索引，应位于租户可信边界内；映射、分析器、词表都由领域包声明式注册，不需要 Python 代码 |
| `entity-graph` | **Python** | 实体解析依赖名称相似度、规则与模型候选排序；领域包提供 `RelationExtractor` 代码；只处理公共域实体 |
| `domain-intelligence` | **Python** | 领域包提供 `Aggregator` 代码、领域 Schema 与迁移；统计与查询模板是受审查的 SQL，在线负载由只读副本承担 |
| `learning` | **Go** | 处理租户反馈与评估集，属于租户域；策略仿真复用 `detection.DryRunPolicy`，与匹配同一份 CEL 求值代码，避免双语言实现不一致；离线指标计算用嵌入式 DuckDB（Go 绑定）；公共域解析与实体的质量评估在 `evidence`、`entity-graph` 内以 Python 完成 |
| `operations` | **Go** | 是内部人员访问租户数据的工作台（托管研究、客户成功），需持有支持访问授权；数据维护操作（人工修正、实体合并、聚合确认）调用 A 类子系统的命令接口完成，维护逻辑本身仍在 Python 一侧 |
| `research` | **Go** | Agent 运行时自研且构建在 Temporal 之上，Go SDK 最成熟；工具是对平台接口的受控调用，模型调用经 `ai-platform`；研究质量评估集在 `learning` 中运行 |

### 2.5 扩展机制随之调整

| 扩展包 | 形式 | 运行位置 |
|---|---|---|
| 信息领域包 | Python 代码 + 声明 | A 类 Python 子系统 |
| 应用领域包 | **纯声明 + CEL 表达式**（特征函数、处置规则、判断框架条件、机会路径衔接条件） | Go 子系统中以 CEL 求值 |
| 行业包 | 纯声明（词表、分类、模板、规则） | 两侧按插入点加载 |

应用领域包不再包含可执行代码：CEL 的确定性、无副作用与成本上限天然满足 SPI 规范，扩展包作者也无需掌握 Go。若某个特征确实需要复杂计算，以平台内置函数的形式加入 CEL 函数库（经架构评审），而不是开放任意代码。

### 2.6 多语言的代价与控制

| 代价 | 控制措施 |
|---|---|
| 两套 `kernel` | Go `kernel` 完整实现；Python `kernel` 只覆盖 A 类所需：配置、数据访问与 RLS、发件箱写入、事件消费、Temporal worker、OpenTelemetry、请求上下文、授权客户端 |
| 发件箱中继 | 只用 Go 实现一份，读取所有子系统库的 `outbox` 表（与语言无关） |
| 跨语言调用 | 跨语言一律走远程接口（OpenAPI 生成的客户端）；依赖方向决定只有 Go → Python（查询领域事实、实体、证据）与 Python → Go 平台平面（`ai-platform`、`identity` 授权）两类，均已有契约 |
| 契约测试 | 以 OpenAPI/AsyncAPI 为准做黑盒契约测试，同一套用例验证两种语言实现 |
| 依赖规则 | Go 用 `internal/` 目录可见性 + golangci-lint `depguard`；Python 保留 import-linter |
| 部署单元 | 由两个变为三个：`acquisition`（Python）、`data`（Python：`evidence`、`domain-intelligence`、`entity-graph`）、`platform`（Go）。语言边界与“公共域 / 租户域”边界一致 |

### 2.7 未入围的方案

| 方案 | 不选的原因 |
|---|---|
| 全部 Python（原 ADR-0006） | 匹配、检索、接入等热路径受 GIL 与进程模型限制；CEL 实现成熟度低；私有部署镜像与内存开销大 |
| 全部 Go | 失去文档解析、OCR、NLP 生态，领域包作者门槛高 |
| TypeScript 服务端 | 见 2.3 |
| Java / Kotlin | 生态成熟，但运行时与内存开销、启动时间不利于多进程角色与私有部署；与 Go 相比没有本项目需要的额外优势 |

## 3. 基础设施：自建优先

### 3.1 判断规则

1. 只使用开源、可离线安装、许可证允许向私有部署客户分发的组件；
2. 云厂商只作为 **IaaS 供应商**（虚拟机、云盘、VPC、四层负载均衡、公网带宽），不使用其 PaaS 专有能力；
3. 例外：托管服务在同等可靠性下**价格优势明显**（总成本低 30% 以上，含人力与冗余），且只通过标准协议使用（可无改动切换到自建）时，允许托管；
4. 被托管的组件必须同时在 `staging` 或私有部署包中以自建方式持续运行，保证切换路径始终可用。

### 3.2 逐项方案

| 组件 | 推荐 | 依据 | 备选 |
|---|---|---|---|
| Kubernetes | **RKE2**（虚拟机或物理机上自建） | CNCF 认证、默认安全加固（CIS 基线，利于等保）、支持离线安装，SaaS 与私有部署同一发行版 | kubeadm |
| 入口与网关 | **Envoy Gateway**（Kubernetes Gateway API） | ingress-nginx 已宣布退役；Gateway API 是标准接口 | Apache APISIX |
| PostgreSQL | **PostgreSQL 17+ + CloudNativePG** | 声明式高可用、只读副本、PITR 备份到对象存储；自建后扩展不受托管白名单限制 | Patroni |
| Kafka | **Apache Kafka 4.x（KRaft）+ Strimzi** | Kafka 4 去除 ZooKeeper，运维面变小；Strimzi 是成熟的 CNCF operator | — |
| 缓存 | **Valkey 8+** | Redis 7.4 起改为非开源许可（Redis 8 增加 AGPL 选项）；Valkey 由 Linux 基金会托管、BSD 许可、协议兼容 | Redis 8（AGPL） |
| 检索 | **OpenSearch 3.x + OpenSearch Operator**（已确认自建） | Apache 2.0；k-NN、混合检索、percolator 内置；中文分词插件（IK 移植版、smartcn、HanLP）需随版本做兼容评估 | — |

| 工作流 | **Temporal**（自建，独立 PostgreSQL 集群持久化） | 与业务库隔离负载 | — |

| 授权 | **OpenFGA**（PostgreSQL 存储） | 同 ADR-0012；Go 编写，与 Go 服务同栈 | — |
| 密钥与租户数据密钥 | **OpenBao**（Transit 引擎做信封加密）+ External Secrets Operator | 替代云 KMS；Vault 改为 BSL 后，OpenBao 是 Linux 基金会下的 MPL 2.0 分支 | — |
| 镜像仓库 | **Harbor** | 镜像签名、漏洞扫描、复制到私有部署环境 | — |

### 3.3 对象存储的价格例外判断

对象存储是唯一可能触发价格例外的组件：它是体量最大（TB 级、持续增长）且纯容量型的负载，而公有云上自建只能使用云盘。

| 方案（每 100 TB 有效容量） | 估算月成本 | 说明 |
|---|---|---|
| 公有云对象存储（标准型） | 约 1.2 万元 | 约 0.12 元/GB/月，冷数据转低频可再降；不含请求与外网流量费 |
| 公有云虚拟机 + 云盘自建 Ceph（纠删码 4+2，1.5 倍） | 约 5 万元以上 | 150 TB 高效云盘约 0.35 元/GB/月，另计存储节点计算资源 |
| 自有机房或托管机柜（大容量机械盘服务器） | 低于公有云对象存储 | 需要硬件采购与机房 |

单价为公开报价量级 **[待核验：以实际商务报价为准]**。即使误差较大，公有云上自建对象存储的成本也是托管的数倍，满足价格例外。

**推荐：** 生产环境的对象存储使用 IaaS 供应商的对象存储，**只通过 S3 标准协议**访问（不使用其专有的图片处理、事件通知、生命周期以外的特性）；私有部署与 `staging` 使用 Ceph RGW，保证切换路径持续可用。若将来迁入自有机房，对象存储随之改为自建。

其他组件（PostgreSQL、Kafka、OpenSearch、Valkey）在虚拟机上自建的成本通常不高于托管溢价，且自建后扩展与版本不受限，不触发价格例外；C1 商务报价完成后按 3.1 规则复核一次。

### 3.4 云厂商选择（C1）的范围变化

云厂商只提供 IaaS 后，选择依据变为：境内区域与可用区数量、虚拟机与带宽价格、等保合规配套、对象存储价格、出口地址资源。选择不再形成锁定，可在阿里云、腾讯云、华为云或自有机房之间迁移；OpenTofu 按供应商编写网络与计算模块，Kubernetes 以上的清单不变。建议在 C1 中以三家报价对比决定。

## 4. AI：前期只接 API

### 4.1 方案

| 能力 | 方案 | 依据 |
|---|---|---|
| 生成与结构化输出 | 境内已备案的多家模型 API，经 `ai-platform` 统一路由 | 合规已确认；供应商以评测（研究黄金集、解析评估集）选主选与备选 |
| 适配协议 | **OpenAI 兼容协议适配器为主**，个别供应商专用适配器为辅 | 主流境内供应商都提供 OpenAI 兼容接口，适配器薄；私有部署客户可把模型端点指向自有推理服务，平台代码不变 |
| 嵌入与重排 | 供应商的嵌入与重排 API | 公共域分块按内容哈希只计算一次、全租户复用，调用量可控（见 4.2）；嵌入模型与版本记录在索引版本中，更换即触发重建 |
| OCR 与版面 | 先用文档解析/OCR API 与多模态模型 API；PaddleOCR CPU 推理作为可选自建方案 | 公告多为 HTML 与文本型 PDF，扫描件是少数；按页计量成本，超过阈值再评估自建 |
| 私有推理与 GPU | 不建设 | D3 |

### 4.2 嵌入的调用量估算

每年千万至亿级分块 × 每块约 500 token ≈ 每年 50 亿至 500 亿 token。境内嵌入 API 单价约为每千 token 0.0005 元量级 **[待核验]**，年成本约在数千元至数万元之间。即使增强器升级导致整体重算一次，成本也在同一量级，不构成自建理由。

### 4.3 敏感数据路由

原设计“敏感数据仅路由到私有部署模型”不再成立，改为：

| 分级 | 模型路由 |
|---|---|
| 公开 | 已备案模型 API |
| 内部 | 已备案模型 API（租户可限制供应商） |
| 敏感 | **默认不进入模型**；租户显式授权后，仅路由到签有零留存、禁止训练、境内处理条款的指定供应商；私有部署客户使用其自有端点 |
| 个人信息 | 默认不进入模型（不变） |

### 4.4 重新评估私有推理的条件

满足任一条件时以新 ADR 评估自建推理：某类任务的月度 API 成本超过同等 GPU 资源成本；签约客户合同要求由妙洽提供私有模型；关键能力在合规供应商中无可用模型。
