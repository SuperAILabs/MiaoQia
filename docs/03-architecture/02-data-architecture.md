# 数据架构

> 状态：评审中 · 版本：1.1 · 更新：2026-10-13 · 负责人：数据架构负责人

## 1. 数据分区

```text
┌──────────────────────────── 公共域 Public Zone ────────────────────────────┐
│ 原始制品 → 快照/文档/解析修订/证据 → 领域事实/事件 → 实体/关系 → 检索投影 │
│ acquisition    evidence             domain-intelligence  entity-graph search │
└─────────────────────────────────────────────────────────────────────────────┘
                     ▲ 只读引用（subject_ref + version）
┌──────────────────────────── 租户域 Tenant Zone（按租户单元部署）────────────┐
│ 客户上下文/策略/知识资产 → 监测/信号 → 研究 → 判断/决策 → 推进/结果 → 反馈   │
│ customer-context          detection   research assessment pursuit learning   │
│ + 客户授权原始数据与文档（租户隔离存储）                                    │
└─────────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────── 平台域 Platform Zone ──────────────────────────┐
│ 身份与授权 · 订阅计量 · 审计 · 模型目录与调用记录 · 运营工单               │
└─────────────────────────────────────────────────────────────────────────────┘
```

规则：

- 公共域永不读取租户域；
- 租户域通过 `subject_ref` 引用公共域对象的特定版本，不复制公共数据（检索结果快照与特征快照只保存判断所需的最小字段与引用）；
- 平台域数据带租户标识，按租户访问控制。

## 2. 持久化原则：按数据特征分层存放

不同数据的写入模式、体量、查询方式和生命周期差异很大，平台**不把所有数据放进 PostgreSQL**。分配原则：

| 数据特征 | 存放位置 | 原因 |
|---|---|---|
| 体量大、写入后不变、主要用于检索与重新处理（原始网页、附件、正文、规范化文档、AI 增强结果） | **对象存储**（权威） | 成本低、天然不可变、适合批量重新处理；不占用事务数据库 |
| 需要全文、语义、标签、多条件组合检索的内容 | **OpenSearch**（派生，可重建） | 倒排索引、中文分词、向量、聚合、订阅反查 |
| 结构化、需要事务、约束、关联、版本指针和精确查询的数据（来源目录、快照元数据、领域事实字段、实体与关系、全部租户数据） | **PostgreSQL**（权威） | 事务一致性、约束、行级安全 |

一句话：**正文与大对象在对象存储，检索在 OpenSearch，结构与状态在 PostgreSQL。**

## 3. 公共域的分层持久化

公共域信源数据是平台体量最大的数据，按以下五层组织：

```text
            写入一次，永不修改                         可随处理器版本演进
┌──────────────────────────────┐   ┌───────────────────────────────────────────┐
│ L0 原始层  对象存储            │   │ L3 增强层  对象存储（权威）+ PG 登记         │
│ 原始响应、附件（内容哈希寻址） │──►│ AI 抽取、标签、分类、实体提及、摘要、向量    │
└──────────────┬───────────────┘   │ 按 增强器×版本 存放，可整体重算               │
               ▼                   └───────────────────┬───────────────────────┘
┌──────────────────────────────┐                       │
│ L1 规范化层  对象存储          │───────────────────────┤
│ 正文、版面、表格、分块（chunk）│                       ▼
│ 按 快照×处理管线版本 存放      │   ┌───────────────────────────────────────────┐
└──────────────┬───────────────┘   │ L4 检索层  OpenSearch（派生，版本化索引）   │
               ▼                   │ 文档索引 · 分块索引 · 领域事实索引 · 实体索引 │
┌──────────────────────────────┐   │ 订阅反查索引                                  │
│ L2 结构层  PostgreSQL          │──►│ 由 L1 + L2 + L3 组装，别名切换实现零停机重建 │
│ 来源与快照元数据、领域事实字段 │   └───────────────────────────────────────────┘
│ 证据定位、实体与关系、版本指针 │
└──────────────────────────────┘
```

| 层 | 内容 | 存储 | 所有者 | 可变性 | 是否可重建 |
|---|---|---|---|---|---|
| L0 原始层 | 原始响应、附件、抓取元数据 | 对象存储 | `acquisition` | 不可变 | 否（唯一原件） |
| L1 规范化层 | 正文文本、版面结构、表格、分块、页码坐标 | 对象存储 | `evidence` | 按管线版本追加 | 是（由 L0 重新处理） |
| L2 结构层 | 来源目录、快照与修订元数据、领域事实的结构化字段、证据定位符、实体、关系、生命周期 | PostgreSQL | `acquisition`、`evidence`、`domain-intelligence`、`entity-graph` | 版本化 | 部分（领域事实可由 L1 重放） |
| L3 增强层 | AI 与规则产生的检索增强：标签、分类、实体提及、关键词、摘要、分块向量 | 对象存储（结果）+ PostgreSQL（增强运行登记） | `evidence`（增强管线） | 按增强器版本追加 | 是（由 L1 重算） |
| L4 检索层 | 面向检索的组合文档 | OpenSearch | `search` | 随索引版本重建 | 是（由 L1+L2+L3 重建） |

### 3.1 PostgreSQL 中**不**存放的内容

- 公告正文、附件文本、HTML；
- 分块文本与向量；
- AI 增强的标签明细与摘要（PostgreSQL 只登记增强运行的版本、范围和状态）；
- 原始响应与抓取的完整响应头。

PostgreSQL 中的领域事实只保存结构化字段（采购人、金额、截止时间、品目代码等）及其证据定位符（`snapshot_id + locator`），定位符指向对象存储中的规范化文档。

### 3.2 对象存储的组织

| 前缀 | 内容 | 格式 | 生命周期 |
|---|---|---|---|
| `raw/<source>/<yyyy>/<mm>/<content_hash>` | 原始制品 | 原始格式 | 标准存储 → 数月后转低频 → 按来源权利转归档 |
| `normalized/<pipeline_version>/<snapshot_id>.json.zst` | 规范化文档（含分块） | 压缩 JSON | 当前版本保持标准存储，旧版本按策略降级或删除 |
| `enrichment/<enricher>/<version>/<partition>/…` | 增强结果 | 压缩 JSONL（每行一个快照或分块） | 当前与上一版本保留，其余删除 |
| `corpus/<domain>/<yyyy-mm>/…parquet` | 语料快照：按月汇总的规范化文本与元数据 | Parquet | 用于批量重算增强、评估与模型调优 |

语料快照让大规模重算（例如新分类器上线后对三年历史数据重新打标）可以用批处理顺序读取，而不必逐条访问对象或查询数据库。批处理在 `workflow-worker` 中使用 Arrow / DuckDB 等嵌入式工具执行，不引入独立的数据湖服务。

### 3.3 增强层：AI 驱动的检索质量提升

增强层的作用是**提高检索与匹配的召回率和精准度**，与领域事实（权威字段）区分：

| | 领域事实字段（L2） | 检索增强（L3） |
|---|---|---|
| 用途 | 判断、硬门槛、生命周期、统计 | 检索、召回、排序、订阅匹配候选 |
| 准确性要求 | 高；带证据与质量状态；不确定时进入复核 | 允许概率性；带置信度 |
| 示例 | 预算金额、投标截止时间、中标人 | “含管材供货”标签、品类分类、项目类型、技术关键词、摘要、向量 |
| 变更方式 | 新解析修订，版本可追溯 | 新增强器版本整体重算，旧版本可回退 |

增强器（Enricher）类型：

| 增强器 | 方法 | 产出 |
|---|---|---|
| 文档类型分类 | 规则 + 小模型 | 公告类型、采购方式 |
| 品类分类 | 规则映射 + 嵌入近邻 + 大模型兜底 | 政府采购品目、行业包产品分类（多标签、带置信度） |
| 标的与需求抽取 | 大模型结构化抽取 | 标的清单、规格关键词、品牌型号要求 |
| 实体提及 | 规则 + 模型 | 组织、地点、项目名称提及（交给 `entity-graph` 解析） |
| 主题与业务标签 | 标签体系 + 模型 | 业务标签（如“EPC”“含设备供货”“续约项目”“允许联合体”） |
| 摘要 | 大模型 | 检索结果摘要与卡片摘要 |
| 分块向量 | 嵌入模型 | 语义检索与 Agent 研究的分块向量 |

设计规则：

- **一次计算、全租户复用**：公共域增强只按内容哈希计算一次，结果对所有租户可用；租户私有的语义（如“对我方是否相关”）不在增强层计算，属于 `detection` 与 `assessment`；
- **成本分级**：规则与小模型优先，大模型只处理规则无法覆盖或置信度不足的部分；热数据（近期、仍在有效期内）优先，历史数据批量低优先级处理；
- **标签体系版本化**：标签与分类体系由平台和行业包定义，体系变更产生新的增强器版本；
- **可回退**：新版本增强与旧版本并存，经评估通过才用于索引；
- **可提升为领域事实**：增强结果经质量评估达到门槛的字段，可由解析器采纳为领域事实字段，并标注方法为模型、附带证据定位。

### 3.4 检索层的版本化与持续改进

检索质量的改进不是一次性的，而是闭环：

```text
用户检索与反馈、信号否决、研究工具调用记录
  → 检索相关性评估集（learning）
  → 新增强器版本 / 新标签体系 / 新分词词表 / 新映射 / 新排序
  → 批量重算增强（语料快照，Temporal 工作流）
  → 构建新版本索引（shadow 索引）
  → 离线相关性评估（nDCG、召回率、订阅匹配召回）与线上影子比对
  → 别名切换；旧索引保留一个周期以便回退
```

索引命名为 `<index_family>-v<mapping_version>-<build_id>`，读写通过别名访问；映射或分析器的变更通过新索引版本完成，而不是原地修改。

### 3.5 存储组合总表

| 存储 | 用途 | 所有权规则 |
|---|---|---|
| **对象存储（S3 兼容）** | 公共域 L0、L1、L3 与语料快照；租户知识资产文件；导出；大型研究产物 | 按域与子系统划分桶与前缀；租户对象使用租户前缀与租户密钥 |
| **PostgreSQL** | 公共域 L2 结构层；全部租户域数据；平台域数据 | 每个子系统独占一个逻辑数据库与数据库账号；禁止跨库访问 |
| **PostgreSQL 只读副本** | 领域统计、仿真与评估等重查询 | 与主库同一所有权；只读 |
| **OpenSearch** | L4 检索层：文档、分块、领域事实、实体索引；订阅反查；租户知识检索 | `search` 子系统独占；全部为派生数据，可由权威数据重建 |
| **Kafka** | 领域事件与集成事件 | 主题按发布子系统划分所有权 |
| **Redis** | 缓存、限流、短期幂等记录、分布式锁 | 不作为任何数据的权威来源 |
| **图查询引擎**（读模型） | 实体关系的多跳遍历 | `entity-graph` 独占；由 PostgreSQL 权威数据投影 |

选型理由见 [ADR-0007](../04-decisions/0007-storage-portfolio.md) 与 [ADR-0013](../04-decisions/0013-tiered-persistence-and-search-enrichment.md)。

### 3.6 数据规模估算

| 数据 | 量级估算 **[待核验]** | 存放 |
|---|---|---|
| 原始制品与附件 | 每年数百万篇公告、附件数倍于此，TB 级 | 对象存储（L0） |
| 规范化文档与分块 | 每年千万至亿级分块 | 对象存储（L1）+ OpenSearch（L4） |
| 增强结果与向量 | 随分块数量与增强器版本增长 | 对象存储（L3）+ OpenSearch（L4） |
| 领域事实结构化字段 | 每年数百万条公告对应的结构化记录，数年千万级 | PostgreSQL 按时间分区 |
| 企业主数据 | 千万级组织 | PostgreSQL |
| 实体关系 | 千万至亿级边 | PostgreSQL 分区 + 图查询读模型 |
| 租户信号、判断、反馈 | 每租户每年数万至数十万条 | PostgreSQL 分区 |
| 审计与计量事件 | 每日数十万至数百万条 | PostgreSQL 按月分区，过期归档到对象存储 |

由于大体量内容不进入 PostgreSQL，PostgreSQL 承担的是结构化数据，在分区、索引、汇总表与只读副本下能力充足，**不引入专用分析数据库**：

- **统计汇总表**：`domain-intelligence` 维护按采购人、品类、区域、月份等维度预聚合的汇总表，随领域事实增量更新；
- **只读副本**：仿真、评估回归、运营报表等批量查询走只读副本；
- **OpenSearch 聚合**：面向检索结果的分面统计（如检索结果按地区、品类分布）由 OpenSearch 聚合完成。

统计查询以 `domain-intelligence.GetDomainStatistics` 等接口固定契约。

## 4. 标识符

- 格式：`<类型前缀>_<ULID>`，例如 `org_01JA…`、`sig_01JA…`；ULID 保证时间有序与全局唯一；
- 前缀登记在 `contracts/identifiers.yaml`，由各子系统申请，禁止重复；
- 外部业务标识（统一社会信用代码、项目编号、公告编号）作为属性存储，不作为主键；
- 标识一经分配永不复用；实体合并后旧标识保留并指向存续实体。

## 5. 时间模型

所有长期对象使用双时态，并按需记录来源时间：

| 时间字段 | 含义 |
|---|---|
| `published_at` | 来源声明的发布时间（可能缺失或不准确） |
| `observed_at` | 系统首次观察到该内容的时间 |
| `valid_from` / `valid_to` | 事实在现实世界中的有效区间（如资质有效期、关系存续期） |
| `recorded_at` | 系统记录该版本的时间 |

所有时间以 UTC 存储，原始时区与精度作为属性保留（如“仅精确到日”）。

## 6. 版本模型

```text
RawArtifact (内容哈希, 不可变)
  └─ SourceSnapshot v1, v2 …          来源内容实际变化 → 新快照
       └─ ExtractionRevision r1, r2 … 解析器升级/人工修正 → 新修订
            └─ DomainFactVersion       领域事实版本（引用修订）
                 └─ Entity/Relationship 版本（引用事实）

TenantSide:
  PolicyVersion, ContextSnapshot, ModelVersion, PromptVersion, TemplateVersion
  ResearchReport  ─固定引用→  事实版本 + 上下文快照 + 模型/提示/工具/模板版本
  Assessment      ─固定引用→  研究报告 + 策略版本 + 特征快照 + 框架版本
  Decision        ─固定引用→  判断版本
```

- 原始制品与快照不可变；解析修订与事实版本追加式；
- “当前版本”是指针，不是覆盖；
- 任何租户侧产物都可以按其固定的版本重放。

## 7. 通用对象字段

所有长期对象至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 类型化 ULID |
| `schema_version` | 对象 Schema 版本 |
| `tenant_id` | 租户域对象必填，只能由服务端从认证上下文写入 |
| `visibility` / `rights_tags` | 可见性与来源权利标签（公共域对象） |
| `classification` | 数据分级 |
| `created_at` / `recorded_at` | 记录时间 |
| `source_refs` / `evidence_refs` | 来源与证据引用（适用时） |
| `quality` | 质量状态与警告（适用时） |
| `change_reason` | 变更原因（可变对象） |

## 8. 数据库设计约定

- 每个子系统一个逻辑数据库；数据库内按信息领域或聚合划分 schema；
- 迁移工具统一（Alembic），迁移必须向前兼容，至少支持“扩展—迁移—收缩”三步；
- 大表按时间分区（领域事实、抓取记录、信号、审计）；
- 租户域表全部带 `tenant_id`，启用行级安全（RLS），会话变量由数据访问层从请求上下文设置；
- 事务性发件箱表 `outbox` 存在于每个发布事件的子系统数据库中；
- 禁止数据库触发器承载业务逻辑。

## 9. 派生数据与重建

| 派生数据 | 来源 | 重建方式 |
|---|---|---|
| 规范化文档（L1） | 原始制品 | 按管线版本重新处理 |
| 增强结果（L3） | 规范化文档 | 按增强器版本批量重算（语料快照） |
| 检索索引（L4） | L1 + L2 + L3、实体、知识资产 | 构建新版本索引，别名切换 |
| 统计汇总表 | 领域事实 | 从领域事实增量或批量重算 |
| 图查询读模型 | 实体与关系 | 从 PostgreSQL 批量投影 |
| 实体画像 | 关系与统计 | 重新计算 |

派生数据的任何不一致都以权威数据为准；派生数据不得被写回权威数据。

## 10. 数据保留与删除

- 保留期限由 `governance` 的保留策略定义，按数据类别配置；
- 公共域原始制品与证据默认长期保留（受来源权利约束）；
- 租户数据在租户注销后按合同约定期限删除，删除覆盖所有存储及备份的过期策略；
- 模型调用记录不保存敏感原文，按策略短期保留。

## 11. 备份与容灾

| 数据 | 恢复点目标（RPO） | 恢复时间目标（RTO） |
|---|---|---|
| PostgreSQL（全部子系统） | ≤ 5 分钟（持续归档） | ≤ 1 小时 |
| 对象存储 | 跨可用区冗余，版本保护；L0 原始层另做跨区域复制（唯一原件） | ≤ 1 小时 |
| Kafka | 多副本；事件可由发件箱重发 | ≤ 1 小时 |
| OpenSearch、图读模型、统计汇总表 | 可重建 | 数小时（重建） |

目标在生产上线前以恢复演练验证，演练每季度执行一次。
