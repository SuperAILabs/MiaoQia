# 实体与关系图谱子系统（entity-graph）

> 状态：评审中 · 版本：2.4 · 更新：2026-10-18 · 平面：数据供应

## 1. 使命

建立跨信息领域共享的实体主数据与关系图谱，使“谁、在哪里、和谁、做过什么”这类问题可以跨来源、跨时间被回答。它是买方历史、竞争格局、项目链、合作伙伴、交易对手风险等研究能力的共同基础，也是平台最难被复制的数据资产。

## 2. 职责与非职责

**职责**

- 实体主数据：组织、项目、地点、品类、品牌等实体的标识、名称、别名、属性；
- 实体解析：把领域事实中的名称或标识解析为实体，支持统一社会信用代码等强标识与名称、地址等弱特征；
- 合并与拆分：合并历史、撤销、冲突处理；
- 关系图谱：带类型、时间区间、证据、置信度的关系；
- 图查询：邻居、路径、子图、时间切片查询；
- 实体画像：面向研究的组织画像（由关系与领域统计聚合而成的读模型）。

**非职责**

- 不存储领域事实本身（只持有引用）；
- 不处理租户私有的关系（例如客户自己的客户名单），租户私有实体与关系属于 `customer-context`，可引用公共实体；
- 不构建个人画像：自然人只作为组织关系的端点（4.2），不建画像、不提供以个人为入口的查询；其他场合自然人以公开业务职务/联系属性出现，公开来源按公开数据检索与进入模型，租户私有内容按租户分级处理。

## 3. 内部组件

| 组件 | 说明 |
|---|---|
| `registry` | 实体与别名的主数据存储 |
| `resolver` | 实体解析：阻塞（候选生成）→ 特征比较 → 决策（自动/候选/拒绝） |
| `merge_manager` | 合并、拆分、撤销与历史 |
| `relationship_store` | 关系边的权威存储（PostgreSQL） |
| `graph_projection` | 图查询读模型：权威数据投影到图查询引擎 |
| `profile_builder` | 实体画像读模型 |

## 4. 拥有的数据（公共域）

| 实体 | 说明 |
|---|---|
| `Organization` | `org_`：强标识（统一社会信用代码等）、名称、别名、类型、地区、状态 |
| `Project` | `prj_`：跨信息领域的项目实体（投资项目、采购项目的上位对象） |
| `Location` | `loc_`：行政区划与地点 |
| `Category` | `cat_`：品类（多分类体系的统一节点及映射） |
| `Brand` | `brd_`：品牌（名称、别名、行业包词表来源）；型号是品牌下的属性与原文，不单独建实体 |
| `Relationship` | `rel_`：类型、起点、终点、约束、有效时间区间、证据引用、置信度、来源事实及其版本、状态（有效 / 已修订 / 已撤销），见 4.1 |
| 自然人端点 | 只作组织关系的端点，不是画像对象，见 4.2；标识前缀随首个实现登记 |
| `ResolutionDecision` | 解析决策记录：输入、候选、得分、结果、方法 |
| `MergeEvent` | 合并与拆分历史 |

### 4.1 关系的端点、约束与版本

- **类型定义**：关系类型由信息领域包的 `relationships.yaml` 定义（招投标见 [INF-PROC](../../../packs/information_domains/procurement/relationships.yaml)、项目链见 [INF-INVP](../../../packs/information_domains/investment_projects/relationships.yaml)），声明端点、约束、有效区间与抽取来源路径，`mqc` P8 校验路径与种类；平台级类型（如品牌归属的人工维护）在本节登记。
- **端点与约束**：端点是实体图谱实体（组织、项目、地点、品类、品牌）；约束限定这条边成立的上下文（领域事实如 `pp_`/`bdr_`、标包、区域、期间），不是端点。同一端点在不同约束下是不同的边，例如同一供应商在两个标包供应同一品牌是两条边。
- **品牌路径**：采购标的指定品牌（`specified_brand`，项目 → 品牌）回答“业主要什么”；中标或合同明细中的品牌（`supplied_brand`，供应商 → 品牌，约束为项目、结果与标包）回答“实际供了什么”，两者分开统计、不互相推断。品牌归属（`brand_owned_by`，品牌 → 组织）是本节登记的平台级关系，只有两种来源：行业包品牌词表中带证据的归属声明、运营复核。中标或合同明细中的制造商（`manufacturer`）只证明产品由谁制造，代工时与品牌所有者不同，不作为归属依据，制造信息保留在领域事实中；每条带证据与有效区间（品牌转让、授权变化按区间区分），同一时点多个归属并存时保留并标为冲突，不按供应商推断归属。“中标方供过哪些厂商的产品”按供应时点沿 `supplied_brand` → `brand_owned_by` 查询。
- **修订与撤销**：来源事实更正时按新版本重新抽取，旧边标为已修订并指向新边；来源事实撤回、权利撤销或实体合并撤销时边标为已撤销，保留历史；两者都发布 `entity.relationship.changed.v1`（`action: remove` 附原因）。
- **项目归属与时间线**：采购项目 `pp_`（可带标包约束）到项目 `prj_` 的 `part_of` 是归属边，是唯一允许以领域事实为起点的关系，终点只能是项目。合并采购的一个采购项目或其中的标包可以归属多个项目，“同一采购项目只属于一个 `prj_`”不是不变量；显式标识直接建边，属性或语义匹配产生带置信度的候选边，可复核、修订与撤销。信号与推进的求值单位保持 `pp_` 与标包，不保存归属快照；对象页的跨目标时间线（事实、信号、推进）按归属边组装：默认取当前有效的边，需要说明“当时为什么这样判断”时按记录时点取当时已记录的边。归属边的新增、修订与撤销发布 `entity.project_link.changed.v1`（载荷含方式、置信度与复核状态），不走 `entity.relationship.changed.v1`，后者的端点仍只接受实体标识。归属边修订或撤销后时间线随之变化，已有信号与推进不改写。
- **版本语义**：实体事件的 `entity_version` 是实体主数据（名称、别名、属性、合并状态）的版本；关系有独立的 `relationship_version`，关系变化不递增端点实体的版本。`subject_ref.version` 指向实体时取引用时的 `entity_version`；合并后旧标识的引用经合并历史解析到存续实体，合并撤销后恢复原实体，已固定版本的引用保持可解释。

### 4.2 自然人关系端点

只用组织之间的关系表达不了完整的控制链：同一自然人分别控制两家投标企业时，组织之间并没有直接的边。因此自然人可以作为关系端点，但这是一项新增的个人信息处理，按以下边界执行（2026-10-17 决定）。

- **关系范围**：只用于自然人与组织之间的出资、实际控制、担任法定代表人或主要人员等关系，类型由企业信息领域包（INF-ORG）定义；不建自然人与自然人、自然人与项目或品牌的关系。
- **身份消歧**：同一自然人跨组织合并为一个端点，必须有来源给出的强标识或授权数据源给出的明确人员标识；只凭姓名、地址或模型相似度一律不合并，各组织保留各自的端点。合并与撤销合并和组织一样记录决策并可撤销。证件号码等强标识只用于消歧，不展示、不进入检索与模型输入。
- **证据**：每个端点和每条边都引用来源事实及其版本，没有证据不建边；来源事实更正、撤回或权利撤销时按 4.1 修订或撤销。
- **用途**：只服务以组织为中心的研究与规则，例如股权与控制链、组织之间是否存在共同控制人。不提供自然人对象页、不以自然人为检索或查询入口、不汇总个人的资产或联系方式；`GraphQuery` 只在从组织出发的路径中返回自然人端点，返回内容限于来源公示的姓名与职务。联系人使用仍按 [identity 第 7.3 节](identity.md#73-高影响动作与审批) 审批。
- **排除**：不对评标专家、监管人员建立端点；自然人的司法与信用记录不采集（[安全与租户第 6 节](../06-security-and-tenancy.md#6-个人信息)）。
- **治理**：该处理登记在 `governance` 的个人信息清单中，写明目的与范围；删除、更正请求覆盖端点、边、检索投影与派生路径。

自然人端点的标识前缀与关系端点类型随首个需要控制链的规则或研究一起登记（[契约覆盖第 9 节](../13-contract-readiness.md#9-随功能追加的契约)），新增前缀经架构评审。在此之前，企业登记事实中的自然人股东等信息仍作为事实属性保存，不进入图谱。

## 5. 接口

| 接口 | 类型 | 说明 |
|---|---|---|
| `ResolveEntity` | 查询 | 名称/标识 → 实体候选及置信度 |
| `GetEntity` | 查询 | 实体主数据。调用方指明口径：**当前**，或**当时已知**某记录时点 R（只取 `recorded_at` 不晚于 R 的实体版本与合并记录）；响应返回同一口径与 R。旧标识按该口径经合并历史解析：当前口径解析到存续实体，合并撤销后解析回原实体；当时已知口径按 R 时的合并状态解析，R 之后的合并或撤销不影响结果。响应另返回当前口径下的合并或撤销事件（时间、依据），供页面单独提示，不并入历史结果。从信号还原“信号判断时”视角时，R 取信号的逻辑求值时间 `evaluated_at`（回填时为被回放事件的时间），不取信号的写入时间 `created_at`，与求值和回放选取版本的方式一致（[策略 DSL 4.3](../11-policy-dsl.md#43-确定性与记录)、[learning 8.1](learning.md#81-时点正确)）；信号视图快照中已固定的版本由调用方直接读取，不经本查询重新解析。对象页据实体版本与关系版本检查查看期间的变化（[PRD 第4段](../../01-product/prd/04-object-page-evidence.md) F7、F8） |
| `GetEntityProfile` | 查询 | 组织画像，返回截至时间与所用统计版本。画像读模型只维护当前值，只支持当前口径；收到当时已知口径的请求返回“历史不可用”，不以当前画像代替 |
| `GetRelationships` | 查询 | 按实体、类型、约束、时间区间查询关系；默认只返回有效边，可按时点返回当时有效的边，也可按记录时点返回当时已记录的边（还原历史判断所见的归属；从信号还原时记录时点取信号的 `evaluated_at`，不取 `created_at`）；响应返回所用口径与时点 |
| `GraphQuery` | 查询 | 受限的图查询（预定义查询模板 + 参数，不开放任意查询语言） |
| `ConfirmResolution` / `MergeEntities` / `SplitEntity` | 命令 | 运营人员复核 |

## 6. 事件

载荷唯一定义见[`contracts/events/entity/events.asyncapi.yaml`](../../../contracts/events/entity/events.asyncapi.yaml)。复用公共事件原语，稳定制品引用不含签名URL或凭据；事件正反例及引用兼容检查通过不代表生产发布/消费、事务发件箱或重放已实现。

**发布**：`entity.entity.created.v1`、`entity.entity.updated.v1`、`entity.merge.applied.v1`、`entity.merge.reverted.v1`、`entity.relationship.changed.v1`、`entity.project_link.changed.v1`（归属边）。

**消费**：`domain.fact.upserted.v1`（抽取实体提及与关系）、`domain.aggregation.changed.v1`。

## 7. 扩展点

- 信息领域包提供：实体提及抽取规则、关系类型定义与抽取规则；
- 行业包提供：品类与品牌词表、品类映射；
- 解析特征与模型可插拔（规则、统计模型、嵌入相似度）。

## 8. 伸缩与可靠性

- 实体规模预期为千万级组织、亿级关系；
- 权威数据在 PostgreSQL（分区），多跳图遍历由图查询读模型承担；图查询引擎是可替换的投影，契约固定在 `GraphQuery` 接口，见 [ADR-0007](../../04-decisions/0007-storage-portfolio.md)；
- 实体解析的错误代价高：自动合并阈值保守，低置信度进入复核队列；所有合并可撤销且撤销会向下游发布事件。

## 9. 安全要点

- 公开来源的个人业务信息（法定代表人、联系人等）按公开数据明文存储、检索、展示并可进入模型；删除更正覆盖实体属性、检索与派生画像，执行[安全与租户](../06-security-and-tenancy.md#6-个人信息)；
- 不对评标专家、监管人员建立任何实体画像或关系端点；
- 自然人端点只在以组织为中心的路径中出现，消歧、证据与用途边界见 4.2。

## 10. 开放问题

1. 图查询读模型引擎的选型（候选：PostgreSQL递归查询、Apache AGE、NebulaGraph），在图查询负载基准测试后确定；
2. 企业主数据的授权数据源选择。
