# 审计与合规子系统（governance）

> 状态：评审中 · 版本：1.0 · 更新：2026-10-12 · 平面：平台

## 1. 使命

让平台的数据处理、AI 使用和关键操作可证明地合法、合规、可审计，并把合规要求转化为可执行的系统策略。

## 2. 职责

- **审计**：接收所有子系统的结构化审计事件（谁、何时、对什么、做了什么、结果、依据），不可篡改存储与查询；
- **数据分级目录**：数据类别、分级（公开、内部、敏感、个人信息、重要数据）、处理目的、允许的模型路由、保留期限；
- **保留与删除**：保留策略执行；租户注销与数据删除请求的跨子系统编排（Temporal 工作流），删除证明；
- **个人信息处理**：个人信息清单、处理目的、访问记录、主体权利请求处理；
- **来源权利合规**：与 `acquisition` 的来源权利联动，权利变更时编排下游下线；
- **生成式 AI 合规**：模型备案/登记信息登记、AI 生成内容标识策略、生成元数据、用户申诉记录；
- **合规报表**：数据清单、处理活动记录、跨境评估、安全事件记录。

## 3. 拥有的数据

`AuditEvent`（追加式，PostgreSQL 按月分区，过期后归档到对象存储）、`DataCategory`、`ClassificationRule`、`RetentionPolicy`、`DeletionRequest` / `DeletionCertificate`、`PersonalInfoInventory`、`ModelRegistration`、`ComplianceRecord`。

## 4. 接口

| 接口 | 类型 | 说明 |
|---|---|---|
| `EmitAudit` | 命令 | 审计事件写入（通过 SDK，异步可靠投递） |
| `QueryAudit` | 查询 | 租户管理员查询本租户审计；平台合规人员查询全局 |
| `Classify` | 查询 | 数据类别 → 分级与处理约束（供 `ai-platform` 路由、`gateway` 净化等使用） |
| `RequestDeletion` | 命令 | 发起删除编排 |
| `GetComplianceReport` | 查询 | 合规报表 |

## 5. 事件

**发布**：`governance.deletion.requested.v1`（各子系统订阅并执行本地删除，回报完成）、`governance.retention.expired.v1`、`governance.classification.changed.v1`。

**消费**：`acquisition.source.rights_changed.v1`、`identity.tenant.suspended.v1`、各子系统的删除完成回报事件。

## 6. 设计要点

- 审计是“写入不可失败”的路径：审计 SDK 本地持久化后异步投递，投递失败告警；
- 审计事件不包含敏感内容本身，只包含引用与摘要；
- 删除采用“各子系统负责本地删除 + 中心编排与证明”的模式，覆盖数据库、对象存储、索引、缓存、只读副本、备份过期与模型调用日志；
- 合规规则（保留期、分级）以配置版本化，可随法规更新。

## 7. 合规基线

平台需在设计与运行中满足个人信息保护、网络数据安全、数据安全、生成式人工智能服务管理和生成合成内容标识等法律法规与标准的要求。法务团队已完成适用条款与义务的确认并授权立项（2026-10-13），具体义务清单由法务维护在合规登记中，本子系统按登记内容执行。
