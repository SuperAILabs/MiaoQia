# A02 真实贯通验收线

> 状态：已批准 · 版本：1.2 · 更新：2026-10-26 · 负责人：项目负责人、首席架构师、产品负责人

本文定义建材供应商 A02 首条旅程从“服务端切片”走到“真实客户可用”的验收线：汇总第1–4、7段服务端切片（PR #26–#32）登记的未实现与未接入项，按“激活策略 → 收到信号 → 查看原文 → 简报触达”梳理真实贯通所需的依赖，给出分级验收与建议顺序。各段的功能规则以[功能 PRD](../01-product/prd/README.md) 为准，首次使用门禁以[阶段基线](06-stage-baseline.md)为准；本文不改变任何门禁，只把分散在各 PRD 验收表与子系统“实现状况”中的缺口收拢成一张可跟踪的清单，并规定进度口径。

## 1. 为什么需要这条验收线

第7、3、4段的服务端切片都按同一模式交付：接口、事件契约、迁移、实现与测试同时提交，身份、数据库、授权与内部调用用真实组件验证，外部依赖经端口隔离，未接入时失败关闭（`NotWired`，503），测试用夹具。这一模式让每段都可自动验证，但也意味着：

- **每个子系统的缺省装配都是“未接入”**：learning 的数据集、detection 的事实视图与订阅反查、gateway 的数据平面读取、channels 的企业微信适配器、identity 的 IdP 管理接口，在 `Module()` 缺省下都返回不可用；
- **数据供应平面仍是骨架**：acquisition、evidence、domain-intelligence、entity-graph 的 Python 子系统只有分层目录，INF-PROC 只有招标公告解析器，A02 需要的中标结果公告解析、领域事实与 `domain.fact.upserted.v1` 的生产者都不存在；
- **Web 与 H5 尚未实现**：`web/` 只有契约生成包；[Web 专项设计](../03-architecture/14-web-application.md)已给出浏览器端流程、BFF 契约、保存视图所有者与 PRD 中“随 Web”行为的页面落点（W-01），实现按 D4 在 L1 之后开始；
- **调度器角色只有登记**：`scheduler` 进程角色存在，但邀请到期、审批到期、绑定重试、简报定时、跟进提醒都没有装配到任何定时任务。

因此 M2 的进度应同时按两个口径衡量：段的**服务端切片**（PRD 验收表中“部分（服务端）”的覆盖）与段的**贯通级别**（第3节）。前者已推进到第4段，后者目前所有段都停在 L0。

## 2. 贯通链路与依赖

A02 的最短可用链路分四个环节。每个环节列出“真实贯通”还缺什么，编号对应第4节缺口清单。

| 环节 | 用户看到的结果 | 已有（服务端切片） | 真实贯通还缺 |
|---|---|---|---|
| ① 激活策略 | 管理员配置档案与 A02 目标，看仿真报告，提交并批准激活 | 档案与目标、策略草案/版本/差异、仿真与报告、审批服务、激活执行（#26、#30） | 仿真数据集与信息领域服务状态（D-09、D-10）、代表样本按查看者权限过滤（D-17）、真实 IdP 与 TOTP（C-03）、审批通知（C-05）、Web 页面（W-02）、审批到期定时（R-01） |
| ② 收到信号 | 新的中标结果公告进入平台后，命中的目标收件箱出现信号，可反馈与批量处理 | 生效边界匹配、收件箱、详情与解释、反馈与批量撤销（#31） | 公告采集→快照→结果解析→领域事实→事实事件（D-01～D-05）、订阅反查与事实视图适配器（D-06、D-07）、企业主数据（D-08）、Web 收件箱（W-02） |
| ③ 查看原文 | 从信号进入项目、中标方页面，字段回到原文片段 | 对象页与证据面板 BFF、对象信号分区、查看计量（#32） | 数据平面读取与证据读取适配器（D-11）、覆盖判断适配器（R-05）、归属边与组织解析（D-12）、信息领域服务状态与字段状态（D-10、D-13）、Web 对象页与证据面板（W-02） |
| ④ 简报触达 | 早间在企业微信收到按目标分区的简报，卡片上反馈或跳转 Web | 企业微信绑定、免登会话与撤销（#29，内存适配器） | 第5段服务端（主线进行中，C-04）、生产企业微信适配器与外网回调入口（C-01、C-02）、浏览器免登会话与卡片落地（W-04，按 Web 专项设计 WD2）、简报定时（R-01）、H5 落地页（W-03） |

第6段跟进（指派、截止提醒、结果）在环节④之后接入，它的真实贯通依赖与④相同（渠道、调度、Web），不另列环节；第6段服务端由主线在第5段之后交付。

## 3. 分级验收

把“真实贯通”拆成五级，每一级都有独立的通过证据，前一级是后一级的输入。级别是对整条链路的判断，不是对单个子系统的判断。

| 级别 | 名称 | 数据 | 渠道 | 界面 | 通过证据 |
|---|---|---|---|---|---|
| L0 | 服务端切片 | 夹具 | 内存适配器 | 无 | 各段 PRD 验收表的自动化用例（现状） |
| L1 | 回放贯通 | 仓库内冻结语料中的官方公告（中标结果、更正），经真实数据平面管线处理；企业主数据用标明为夹具的样本 | 内存适配器 + 站内 | 无（API 脚本走查） | 一套端到端测试：在同一环境中启动 data 与 platform 部署单元的真实进程角色，所有端口装配生产实现（不含任何 `NotWired`），从“投放一份结果公告文档”到“目标收件箱出现信号 → 对象页字段回到原文片段 → 站内简报”全程通过；含跨租户与无权限的负向用例 |
| L2 | 界面贯通 | 同 L1 | 同 L1 | Web 最小页面集 + 企业微信内置浏览器的 H5 落地页 | 开发 VPS 上的部署（M0-01）；内部人员按 PRD 各段“可运行”的步骤走查并截图，记录走查时的版本 |
| L3 | 真实渠道 | 同 L1 | 生产企业微信适配器，在**测试企业微信企业**中安装、绑定、免登、收简报、卡片动作 | 同 L2 | C10 对测试企业的验收记录（安装授权、凭证、验签、重放、限流、负向用例）；简报经企业微信实际送达的走查记录 |
| L4 | 真实数据 | 试点区域的 P0 来源持续采集，INF-ORG 来自供应商接口 | 同 L3 | 同 L2 | M1-P1/P2/P3/P7 在试点范围内关闭；连续运行期间的信号、证据与简报抽查记录；数据截至时间与覆盖如实显示 |
| L5 | 客户走查 | 同 L4 | 客户自己的企业微信企业 | 同 L2 | M2-P8/P9 关闭；试点建材客户按 PRD 各段走查，任务观察与缺陷处置记录齐备，即各段的“功能验收” |

说明：

- L1 使用的是仓库内已冻结的官方公告语料（[`packs/information_domains/procurement/corpus/`](../../packs/information_domains/procurement/corpus/)），作为测试材料处理，不构成来源启用，不宣称 INF-PROC 就绪，不改变 M1-P1/P2 的门禁；
- L2 与 L3 互不依赖，可以并行；L4 依赖第5节的外部事实，L5 依赖 L4；
- 每一级的负向用例都在该级环境中重新执行，不沿用 L0 的结论（第6节）。

## 5. 建议顺序

建议的顺序按依赖排列，不给日期；每一级的开始以前一级的通过证据为准，周数按[路线图](01-roadmap.md)的规划窗口在每个交接点校准。

1. **L1 回放贯通**：本文合并后即开始，与主线第5、6段服务端并行。工作集中在数据供应平面（D-02～D-07、D-09～D-12，Python 与适配器）、运行装配（R-01、R-02）与覆盖判断（R-05）；仿真接入真实数据集之前先关闭样本权限过滤（D-17）。简报环节先接站内，第5段服务端合并后补上。
   - 与主线的分工：数据平面的 Python 子系统、INF-PROC 结果公告解析器与贯通 E2E 测试由独立线程实现，和主线改动的 Go 服务端基本不重叠；detection、learning、gateway 端口的生产适配器会改到主线也在改的子系统，开工前与主线协调，按“谁先合并谁占用修订号，后合并的顺延”处理；
2. **L2 界面贯通**：Web 专项设计已完成（W-01 已关闭），实现等 L1 的端到端测试通过后开始，按[Web 专项设计第10节](../03-architecture/14-web-application.md#101-批次)的批次覆盖第2节四个环节需要的页面（W-02～W-07）；同时完成 R-03 与 C-03 的 Web 登录部分；
3. **L3 真实渠道**：与 L2 并行，前提是 U-01 测试企业与 C10 真实调用授权到位；交付 C-01、C-02（生产企业微信适配器、渠道网页授权与 `ChannelSSO` 的生产接入、外网回调入口），以及 W-04 中浏览器免登会话与卡片落地在真实渠道下的验收（按 Web 专项设计 WD2）；
4. **L4 真实数据**：前提是第6节的外部事实到位；先在一个试点区域的少量 P0 来源上关闭 M1-P1/P2/P7，不以全国覆盖为前提；
5. **L5 客户走查**：L4 通过且 M2-P8、M2-P9 关闭后，由试点客户按各段 PRD 走查，关闭各段的“功能验收”。

- **负向验证随级别重做**：每升一级，在该级环境中重新执行跨租户、无权限、令牌重放与失败关闭的负向用例；涉及授权或租户隔离的实现 PR 附独立的越权与反例测试，不以 CI 全绿或验收表标记代替；
- **外部事实**：B2b、D1c/D2、建材试点客户候选、C3/C7a、C10 的状态以[阶段基线第4节](06-stage-baseline.md#4-m2-前置条件与能力交接)和[立项清单](00-initiation-readiness.md)为准，本文只标注它们阻断哪一级。
