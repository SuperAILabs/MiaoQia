# 研发规范与质量门禁

> 状态：评审中 · 版本：1.2 · 更新：2026-10-17 · 负责人：首席架构师

## 1. 分支与评审

- 主干开发：短生命周期分支，合并到 `main` 前必须通过 CI 与代码评审；
- 跨子系统契约变更需要所有受影响子系统负责人评审；
- 架构层面的变更需要更新相关文档与 ADR；
- 提交信息说明变更动机与影响范围；
- 评审开始后冻结 PR 范围：只修改评审意见指出的问题，新增内容另开 PR。评审中途扩大范围会让旧问题未关闭、新问题又出现（任务书 v0.3 第二批 PR 因此评审了 8 轮）；
- 设计文档按事实所有者分组修改，每组一次提交，评审可以逐组核对；同一事实只在所有者文档中定义，其他文档引用，不另写平行规则；
- 决策与讨论通过 PR 进行：需要项目负责人决定的事项，由提交人把推荐做法写进所有者文档并开 PR，PR 描述逐条列出决策点、推荐与理由；项目负责人在 PR 上评论确认或改写，文档中注明确认人、日期与 PR 编号。只有外部信息（如供应商交付进度）才能回答的问题列在 PR 描述中，答复前不写入文档；
- 合并条件：指定评审人对当前 head 提交的最新结论为通过、无未关闭的评审意见、CI 全部通过；含决策点的 PR 另需每个决策点已获项目负责人明确同意，或其改写意见已落实且没有未决分歧；拒绝、暂缓或要求改写不算满足。决策确认前，文档只写“推荐方案、待确认”，不写成已确认或已通过的状态。满足后由提交人直接合并，不再单独请求合并指令；
- 待决事项在拍板前不写成已批准的规则；文档中的每条新论断须能指向已有文档、ADR 或负责人的明确决定，不能凭推测补写。

## 2. 测试分层

| 层级 | 范围 | 要求 |
|---|---|---|
| 单元测试 | `domain` 与 `application` 层 | 业务规则全覆盖；`domain` 层无基础设施依赖 |
| 集成测试 | 子系统与其数据库、事件、工作流 | 使用真实 PostgreSQL/Kafka/Temporal 测试容器 |
| 契约测试 | 子系统接口（本地与远程绑定）、事件生产与消费 | 契约变更必须通过 |
| 扩展包测试 | 来源处理器、解析器、规则、模板 | 附带夹具与样本，结果与基线一致 |
| 端到端测试 | 关键业务流程（数据供应、监测、研究、推进、策略变更） | 在预发布环境运行 |
| 安全测试 | 跨租户、未知字段、提示注入、审批绕过、删除完整性 | 阻断项 |
| 评估回归 | 解析、实体、匹配、研究、判断 | 指标不劣化 |
| 性能测试 | 吞吐与延迟关键路径 | 版本发布前 |

## 3. CI 门禁

合并请求必须全部通过：

1. 格式化与静态检查（Go：gofmt、golangci-lint；Python：ruff、pyright；TypeScript：eslint、tsc）；
2. 依赖规则检查（Go：`internal/` 与 `services/archtest`；Python：import-linter）；
3. 单元与集成测试；
4. 契约检查（`mqc check`：Schema 方言、样例、事件契约、扩展包一致性）、契约兼容性检查（`mqc compat`，与目标分支比较）与契约测试；
5. 生成代码一致性检查（`mqc generate --check`）与往返测试，见 [代码库结构](../03-architecture/09-codebase-structure.md#5-代码生成)；
6. 安全负向测试；
7. 受影响扩展包的测试与评估回归；
8. 依赖与镜像漏洞扫描（含 govulncheck）；
9. 数据库迁移检查（可向前兼容）；
10. 文档检查：任何改动 Markdown 的变更都运行 `docs` 工作流，检查相对链接与锚点（`tools/dev/check_doc_links.py`）、空白与行尾、`mqc check`。其他工作流按路径触发，只改文档的变更不会经过它们。

## 4. 数据库迁移

- 每个子系统只迁移自己的数据库；
- 遵循“扩展—迁移—收缩”：先加新结构、双写或回填、切换读取、最后删除旧结构，跨越至少一个发布版本；
- 迁移脚本可重复执行或具备幂等保护；
- 大表迁移使用后台工作流分批执行。

## 5. 可观测性要求

每个子系统必须：

- 对所有接口、事件消费、工作流活动产生追踪与指标；
- 使用结构化日志，禁止记录敏感级数据与租户提供的个人信息；
- 定义并上报业务指标（如解析成功率、信号延迟、研究成本）；
- 定义告警与值班手册。

## 6. 完成的定义

一项功能视为完成，需要：

- [ ] 代码、测试、契约、迁移已合并；
- [ ] 对应文档已更新（子系统规格、领域文档或 ADR）；
- [ ] 指标与告警已配置；
- [ ] 审计与授权已覆盖；
- [ ] 安全负向测试已覆盖新增接口与事件；
- [ ] 涉及 AI 的变更已通过评估回归；
- [ ] 在预发布环境完成端到端验证。

## 7. 文档要求

- 新子系统接口、事件、扩展点必须同步更新子系统规格；
- 新信息领域、应用领域、行业必须有对应业务文档；
- 难以逆转的决策必须有 ADR；
- 一个 PR 中修改的文档，头部版本号只升一次，更新日期为合并前的日期；
- 设计中写明“随首个功能追加”的契约，必须登记到 [契约覆盖第 9 节](../03-architecture/13-contract-readiness.md#9-随功能追加的契约)，功能启动时逐项核对；
- 文档规范见 [文档体系](../README.md)。

## 8. 设计变更自查

设计类 PR 提交前，作者对每条新增或修改的规则回答以下问题，并在 PR 描述中写明“已按第 8 节自查”。评审发现的问题主要集中在前三类，均可在提交前查出：

| 问题 | 核对内容 | 反例 |
|---|---|---|
| 输入缺失或未知时，结论是什么？ | 三值逻辑下未知不能变成确定的通过或排除；缺表、未关联、无候选、数据未接入都要有明确去向（未知、待复核或暂不能诊断） | 部分主体缺资质表时被当作不满足；求值为排除但没有候选时被归为规则排除 |
| 用的是业务时间还是系统记录时间？ | 业务有效区间（`valid_from`/`valid_to`、生效时间）与系统记录时间（`recorded_at`、获知时间）分开；回测、诊断与回放只用当时已记录的版本（[数据架构第 5 节](../03-architecture/02-data-architecture.md#5-时间模型)） | 撤回生效早于平台发现时，回放把后来才知道的撤回当作当时已知 |
| 改动的事实在所有出现处都同步了吗？ | 文档、契约 Schema、事件端点、夹具、三语言生成代码、SDK、PRD 与术语表；不改契约的设计要写明契约何时追加并登记 | 文档改了归属边方向，事件契约端点没同步；新增字段没进入匹配 |
| 幂等、重放与并发下结果一致吗？ | 幂等键覆盖所有区分维度；重试复用原结果；撤销与签发并发时有确定顺序 | 简报幂等键缺少来源与周期，不同计划互相去重 |
| 权限与可见性在每个出口都检查了吗？ | 写入、通知、导出、派生与组合结果都按当前权限与来源权利判断 | 无权限页露出对象标题 |

自查不替代评审，也不替代运行时验收；设计层面通过的能力，上线时仍按阶段门禁验证。
