# PRD 第5段：简报与快捷动作

> 状态：设计交接通过 · 版本：1.2 · 更新：2026-10-19 · 负责人：产品负责人、身份与渠道负责人、客户智能负责人 · 原型：[prototypes/05-briefing-quick-actions.html](prototypes/05-briefing-quick-actions.html)

本段让销售每天早上在企业微信里收到一份按目标分区的简报，在卡片上直接对信号反馈“相关 / 不相关”、发起跟进，或打开 Web 查看命中理由与对象页。它承接第3段（信号与反馈）、第4段（对象页与证据）和第1段（渠道绑定与免登），卡片上的“跟进”接到第6段。简报只是信号的另一个入口：卡片上的每个动作都调用第3段与第6段的同一接口、经同一授权，渠道不另有一套业务规则（[channels 第3节](../../03-architecture/subsystems/channels.md#3-职责与非职责)）。

## 1. 用户与目标

| 用户 | 角色 | 本段要完成的事 |
|---|---|---|
| 销售 | 业务开拓者 `business_developer`（目标参与人） | 早上在企业微信看简报，在卡片上对信号反馈、发起跟进，需要时打开 Web 看理由与对象页 |
| 销售负责人 | 决策者 `decision_maker` | 看各目标的新信号与“待我处理”（待审批、到期任务），从卡片进入 Web 审批 |
| 研究分析者、项目推进者 | `research_analyst`、`pursuit_lead`（目标参与人） | 看简报，按各自权限反馈 |
| 业务专家、租户管理员 | `domain_expert`、`admin`（目标参与人） | 只读：卡片上只有“查看”，没有反馈与跟进按钮 |
| 成员本人 | 全部角色 | 在偏好中设置简报的发送时间、时区、安静时段与是否接收空简报 |

权限依据 [identity 7.2](../../03-architecture/subsystems/identity.md#72-权限矩阵)：简报中的目标区只给有该目标 `can_view_signals` 的成员；卡片上的反馈按钮需 `can_feedback`，跟进按钮需 `can_assign`；按钮在渲染时按收件人当时的权限决定是否出现，点击时再以当前权限实时检查。外部协作者不接收简报。

**成功标准**：销售在企业微信打开早间简报后 5 分钟内处理完简报中的 A02 信号（约 5–10 条，看卡片、反馈或跟进），不需要登录；每条卡片动作的结果（成功、无变化、被拒绝及原因）在卡片上看得懂；渠道投递失败时简报不丢失，Web 与站内能看到同一期简报。

## 2. 范围

| M2 包含 | 不在 M2 |
|---|---|
| 每日简报：按目标分区（每个启用且收件人可看的目标一区）与“待我处理”区；保存简报历史 | “关注变化”区（随关注功能，第13节第9项）；持续型推进的变化简报（随第6段与 B03，简报来源不同） |
| 企业微信推送：一张简报总览卡 + 首要条目的信号卡片（第13节第1项）；渠道不可用时站内兜底 | 飞书、钉钉、邮件的简报推送（适配器分别验收后启用，规则与本段相同） |
| 信号卡片上的快捷动作：相关、不相关（选原因，默认同时忽略）、跟进（随第6段）、查看；动作结果与 10 分钟内撤销 | 卡片上调整处置、批量反馈（回到 Web，第3段）；渠道内提问与追问（随 M3 研究入口） |
| A02 跟进候选的即时通知卡片（策略 `route` 的 `immediate`，与简报卡片同一模板与动作） | 群聊中的简报与卡片（第13节第10项） |
| Web“今日简报”：简报历史、完整简报（H5）、投递记录与“重新推送” | AI 开头摘要（第13节第8项） |
| 简报偏好：发送时间、时区、发送日、安静时段、空简报是否推送、每区条数 | 退订单个目标的简报区（目标参与关系决定，退出目标即不再收到） |
| 从卡片打开 Web：免登、强认证（审批等）与链接过期 | 渠道内审批或任何高影响动作（[channels 第3节](../../03-architecture/subsystems/channels.md#3-职责与非职责)） |

## 3. 前置条件

- 第1段：企业微信应用已安装并通过 [M2-P7](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接) 的回调、验签、网页授权与真实客户测试安装；成员已绑定企业微信；免登会话可签发；
- 第3段：信号、`TriageSignal`、`UndoSignalTriage`、反馈原因标签（APP-TENDER）、操作标识与幂等规则；第7段：A02 目标已激活；
- 第4段：对象页与“来自信号”上下文；第6段：`CreatePursuit` 从信号创建跟进（第6段交付前卡片不显示“跟进”按钮）；
- `channels` 的简报组装与投递（[M2-P5](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接)），动作令牌与回调去重；`domain-intelligence` 的 `GetCoverage`（数据截至时间与来源中断）；
- APP-TENDER 声明简报的区顺序与每区条数默认值（第13节第2项）。

## 4. 主流程

### F1 简报的周期、受众与组装

1. **受众**：每个成员一份简报，内容按其本人的权限组装。成员需同时满足：租户内有效成员；至少是一个已激活目标的参与人且有该目标的 `can_view_signals`，或有待其处理的审批或任务。推送到企业微信还要求该成员的企业微信绑定有效（“已绑定”，不含“失效中”）；没有有效绑定的成员只在 Web 与站内收到；
2. **周期**：每日简报的周期是固定的时间区间，不是“上次打开以来”。默认每个工作日 07:30 发送，周期为上一次计划发送时间到本次计划发送时间，例如周二的周期为 [周一 07:30, 周二 07:30)，周一的周期从上周五 07:30 起。时间按成员偏好的时区（默认租户时区 Asia/Shanghai），周期起止以带时区偏移的时刻保存（如 `2026-10-19T07:30:00+08:00`）；成员修改发送时间或时区从下一期生效，新旧周期首尾相接，不重叠、不留空；
3. **幂等**：同一期简报只生成一份，幂等键为租户 + 受众（成员）+ 简报来源（日常简报定义）+ 周期起止（[channels 4.4](../../03-architecture/subsystems/channels.md#44-简报)）。定时任务重复触发或组装重试都返回已生成的简报；
4. **目标区取数**：每个目标一区，区与区之间不混排、不合并排序分（[业务不变量第8条](../../02-business/01-business-architecture.md#7-业务不变量)）。区的覆盖窗口为左闭右开区间 [起点, 终点)（第5条）。一条信号列入本区须同时满足：
   - 组装时处理状态为待处理（含已调整处置）；
   - 在窗口内**新发现**，或在窗口内有**实质更新**。新发现按信号生成时间 `created_at`，回填信号不算新发现（第7条）；实质更新按第3段第13节第4项的口径：处置上调（向跟进候选方向），或中标方、金额、品类被更正，由 detection 在写入更新记录（`SignalUpdate`）时判定并标记，时间轴是该更新记录写入平台的时间，不是更正公告的来源发布时间，也不是逻辑求值时间。其他更新（例如不影响判断的字段变化）不使信号列入；
   - **每条信号只列一次**：同一信号在窗口内既是新发现又有更新、或有多次实质更新，只列一条。条目按组装时的当前内容版本渲染（卡片令牌记录这一版本），标“新”（窗口内发现）或“已更新”（窗口前发现），并逐次列出窗口内的实质更新（记录时间与前后值，如“10-19 14:05 中标金额 1,800 万 → 1,760 万；20:30 处置 复核候选 → 跟进候选”）。之前各期列出过的信号，本期又有实质更新时再次列出，标“已更新”；
   - 区内按当前内容版本的排序分降序，同分按发现时间新到旧；带更正的条目按更正类处理（第9条）；
5. **区的覆盖窗口**：正常情况下等于简报周期。窗口的起点是该区上一次成功取数并随简报保存的终点，只有取数成功后才前移。某一区本期没能取数（第9节），或整期组装失败时，窗口不前移，下一期该区覆盖 [上一次成功取数的终点, 本期终点)，新发现与实质更新使用同一窗口，并标“含上一期未能生成的部分”；窗口首尾相接，每条信号按第4条只列一次，不遗漏、不重复；
6. **组装时已处理的不列出**：窗口内新发现或有实质更新、但组装时已被忽略、已转跟进或已关闭的信号不列出，区头显示“本期新增 12 条、更新 2 条，其中 3 条已由团队处理”；
7. **回填信号不作为新发现列出**：目标首次激活或回填产生的信号（标“回填”）只在区头显示一行“回填产生 86 条，在收件箱查看”，不占区内条目；回填信号之后有实质更新时，按“已更新”列出；
8. **“待我处理”区**：待本人批准的审批（第7段，按提交时间）与分派给本人、即将到期的任务（第6段，按截止时间）；只显示标题、截止或提交时间与“去 Web 处理”链接，不在渠道内操作；
9. **配额与截断**：每区条数上限按 APP-TENDER 的默认值，成员可在偏好中调整（第13节第2项）。截止时间在 24 小时内的事项和更正类变化不受配额截断，排在区首；超出配额的条目在区尾显示“另有 N 条，在收件箱查看”，链接到该目标收件箱并带本期筛选。配额、去重与截断只影响简报展示，不改变 Top-K 评估列表的样本与口径；
10. **去重**：同一采购项目在多个目标区出现时（不同目标的不同信号），只在区顺序靠前的区完整展示，其他区显示一行引用“也命中 A01 直接投标，见上方”，引用行仍可打开本目标自己的那条信号；
11. **记录**：简报保存每区的状态（正常 / 空 / 来源中断 / 暂不可用 / 目标未激活 / 无权限）、覆盖窗口、所列条目的信号标识与内容版本、条目类别（新 / 已更新）与所列实质更新的引用、排序分与区内顺序、数据截至时间（按信息领域，来自 `GetCoverage`）、组装时间与规则版本；条目内容是组装时的快照。

### F2 推送到企业微信

1. **消息构成**：每期推送一张**简报总览卡**与若干**信号卡片**（第13节第1项）：
   - 总览卡：日期与周期、各区的条目数与前 3 条标题、各区数据截至时间、本期提示（来源中断、部分区不可用）、“查看完整简报”链接；
   - 信号卡片：每个目标区的前 3 条，每期合计最多 6 张；其余条目只在总览与完整简报中；
2. **发送时间与安静时段**：在成员偏好的发送时间组装并推送；成员的安静时段（默认 21:00–07:00，成员时区）内不推送任何简报或通知（第13节第4项）。安静时段内到达的即时通知延后到安静时段结束；延后到结束时仍待处理、且当期简报即将发送的，并入简报（条目标“夜间到达”），不再单独推送；
3. **空简报**：所有区都没有条目时，简报照常生成并保存（各区写明原因：无新信号、目标未激活等），默认不推送到企业微信（第13节第3项）；成员可在偏好中选择接收空简报。有区来源中断或暂不可用时不算空简报，推送一张只含提示的总览卡；
4. **部分简报**：某一目标的数据来源中断或某一区取数失败时，不等待、不整体推迟：其他区照常发送；该区在总览卡与完整简报中写明原因、受影响的信息领域与截至时间，并说明“恢复后补齐的信号会进入下一期简报”（F1 第5条）；
5. **发送前再检查**：组装与推送之间、以及每次重试前，按收件人当前状态再检查：成员仍有效、绑定仍为“已绑定”、各目标的 `can_view_signals` 仍在；失去访问的区与条目删除，不发送过期的权限；成员已退出或绑定已失效的整期不推送到企业微信，只留在 Web 历史；
6. **投递记录**：每次推送的平台提交、渠道接受、用户阅读（渠道支持时）分段记录（[质量与验收第7节](../../05-delivery/02-quality-and-acceptance.md#7-可靠性与安全)）。

### F3 卡片内容与截断

1. **信号卡片**的字段，按优先级从高到低：目标名称与处置（如“A02 进入供货 · 跟进候选”）、项目名称、中标方、金额（注明“中标金额”；未公布显示“未公布”，不用其他金额代替）、地区与品类、最多两条命中理由（规则 `say` 文本）、未知项数、发现时间、标记（已更新、夜间到达、也命中其他目标），以及按钮；
2. **截断规则**：渠道适配器声明各字段的长度与条数上限（[channels 4.2](../../03-architecture/subsystems/channels.md#42-渠道能力声明)）。超出时：
   - 文本在字符边界处截断并以“…”结尾，不截断数字、金额、金额类型、日期与单位；
   - 放不下时按优先级从低到高整项省略（先省略标记，再省略第二条理由，再省略地区与品类），被省略的内容在详情中完整可见；
   - 处置、金额类型、“未公布”“未知”等状态词、“AI 生成”标识与“查看”链接永不省略；
   - 不同类型、不同标包的金额不相加；同标包多家中标时显示“同标包共 3 家中标”；
3. **展示级别**：卡片上的字段按来源权利的展示级别逐维取最严格（[数据架构第12节](../../03-architecture/02-data-architecture.md#12-来源权利与数据权益)）；只允许“仅引用与链接”的字段在卡片上只显示“见原文”与链接，不在卡片中复述内容；
4. **时间标注**：卡片注明“内容截至 07:30”（组装时间）；发现时间与周期都带时区，成员时区与租户时区不同时同时显示两者。

### F4 卡片上的快捷动作

1. **按钮**：有 `can_feedback` 的成员看到“相关”“不相关”；有 `can_assign` 的成员看到“跟进”（第6段交付后）；所有人都有“查看”。排除信号不出现在简报中，没有“排除正确 / 排除有误”按钮；
2. **相关**：一次点击提交“相关”（不带可选标签，标签在 Web 中补充）；
3. **不相关**：点击后卡片展开原因选择（APP-TENDER 的 A02 不相关原因标签中的前 5 个与“其他”）。选原因后提交“不相关 + 移出待处理（忽略）”，与第3段默认一致；选“其他”或需要取消“移出待处理”时，打开 H5 的反馈页完成（第13节第5项）；
4. **跟进**：调用第6段的 `CreatePursuit`，来源为本信号的固定版本，负责人为点击者本人；截止时间、改派与任务在 Web 中设置。信号已有跟进时不再创建，卡片显示已有的跟进与负责人并链接过去（第13节第6项）；
5. **动作令牌**：卡片上的每个按钮绑定一个动作令牌，记录租户、收件人、信号、动作、渲染时看到的信号内容版本、到期时间（第13节第7项）。令牌不带登录身份，只是“这张卡上的这个按钮”的引用；执行时身份来自渠道回调中的点击者渠道账号；
6. **执行时的检查**（按顺序，任一不通过即停止，不执行任何部分；前四项是操作开始前的检查，拒绝只对这一次调用生效，见 F5 第7条）：
   - 回调验签通过，回调未被处理过（F5）；
   - 点击者的渠道账号有有效绑定，绑定的成员仍是租户有效成员；
   - 点击者就是令牌的收件人（卡片被转给他人时拒绝）；
   - 令牌未过期；
   - 以点击者当前的权限实时 `Check`（`can_feedback` 或 `can_assign`）；
   - 之后由 `detection`（或 `pursuit`）按第3段规则检查内容版本、处理状态与版本；
7. **组合动作逐项判断**：“不相关 + 忽略”是两个部分（本人反馈、处理状态），按第3段 F5 第4条逐项判断，卡片按部分显示结果，例如：
   - 两部分都改变：“已标为不相关（品类不符），已移出待处理”；
   - 同事已忽略：“已记录你的反馈；状态无变化（王磊于 08:12 已忽略）”，结果计为成功；
   - 本人此前已标“不相关 · 品类不符”且信号已忽略：“无变化”，不写记录；
   - 信号已关闭：反馈照常写入，处理状态部分不适用：“已记录你的反馈；该信号已关闭（公告被撤回，10-19 发现）”；
8. **结果回写到卡片**：渠道支持更新已发送的卡片时，只更新点击者本人的这张卡片为结果状态（按钮替换为结果与“撤销”）；不支持或更新失败时另发一条结果消息。团队其他成员的卡片不更新，他们之后的点击按当时的实际状态判断（第9节）；
9. **撤销**：成功的动作在卡片上提供“撤销”，10 分钟内有效（第13节第5项）。撤销调用第3段的 `UndoSignalTriage`，是新的操作、有自己的操作标识：按原操作实际改变的部分恢复操作前的值，补偿前逐部分核对版本。一项内各部分的补偿一起提交，要么全部生效，要么全部不生效：任一部分之后被人（含本人）改过，整项不撤销（`CONFLICT`），反馈与处理状态都保持当前值，卡片显示当前值；内容已更新或信号已关闭同样整项不撤销（第3段 F9）。跟进的撤销按第6段，卡片上不提供；
10. **信号已更新**：令牌记录的内容版本与当前不一致时整个动作被拒绝（`SIGNAL_UPDATED`），不按旧版本接受；卡片回复“这条信号已更新：中标金额 1,800 万 → 1,760 万（更正公告 10-19）”，并附一张按新版本渲染、带新令牌的卡片，用户看过变化后可直接再点。

### F5 操作标识、尝试与回调去重

1. **一个按钮一个操作**：动作令牌的标识就是该操作的操作标识（撤销另有令牌与操作标识）。同一按钮被点击多次、渠道重复推送同一回调、投递重试导致同一张卡片送达多次（重试发送同一条已渲染的消息，卡片与令牌不变），都是同一个操作，最多提交一次，之后返回固定的结果。本人主动“重新推送”是新的投递，卡片使用新的令牌，新令牌上的点击是新的操作（F8 第3条）；
2. **回调去重**：渠道回调先按渠道事件标识去重（没有事件标识的，以渠道账号、卡片标识、按钮键与事件时间组合），重放的回调丢弃并计入渠道健康；回调在 1 秒内确认、异步执行（[channels 第9节](../../03-architecture/subsystems/channels.md#9-伸缩与可靠性)）；
3. **尝试与幂等键**：`channels` 每次调用 `TriageSignal`、`UndoSignalTriage` 或 `CreatePursuit` 是一次尝试，带自己的幂等键，同键同结果；调用前先按操作标识查找已提交的结果，有则直接返回（第3段 F9）；
4. **暂时失败**：尝试以 `INTERNAL`、`UNAVAILABLE` 结束且确认未提交时，`channels` 用新的幂等键、同一操作标识自动重试（退避，最多 3 次，在令牌有效期内）；仍失败时卡片显示“暂时没有成功，可再点一次或打开 Web 处理”，用户再点仍是同一个操作；
5. **确定失败**（业务调用返回的 `FORBIDDEN`、`SIGNAL_UPDATED`、`SIGNAL_CLOSED`、`CONFLICT`、`NOT_APPLICABLE`）固定在操作标识上，不自动重试；用户重新查看后的新动作来自新的卡片或 Web，是新的操作；
6. **令牌只在确定结果后作废**：令牌在操作得到成功、无变化或确定失败后作废；暂时失败不作废令牌，以便同一操作再试。作废后的令牌再被点击，返回该操作已固定的结果并注明执行时间，不报“令牌已使用”，也不重新执行；之后状态已变化的（例如已在 Web 撤销），同时显示当前值；
7. **操作开始前的拒绝**：验签失败、回调重放、点击者的租户或绑定不符、点击者不是令牌的收件人、令牌已过期，都在操作开始前拒绝。这类拒绝只对这一次调用生效并写审计，不消耗令牌、不在操作标识上固定任何结果；令牌的收件人之后点击照常执行。只有通过这些检查、进入业务调用后得到的结果才固定在操作标识上。返回已固定的结果前同样先做这些检查（验签、租户、绑定、收件人），不向他人返回该结果。

### F6 从卡片打开 Web

1. 卡片与总览上的链接是短时授权链接，只指向对象（信号详情、第4段对象页并带“来自信号”上下文、完整简报、审批或任务），不携带登录身份；
2. 在企业微信内置浏览器中打开：按第1段 F7 免登，核对绑定有效后签发不带强认证的免登会话（绝对 12 小时）；免登会话过期后再次打开链接时重新免登，用户无感；绑定无效、成员已退出、渠道网页授权或 identity 不可用时转到登录页并说明原因；
3. 在普通浏览器中打开：已有会话直接进入；没有会话先登录，登录后回到原页面；已登录的是另一个成员时不切换账号（第1段 F7 第4条）；
4. **强认证**：“待我处理”中的审批（第7段）等强认证动作在 Web 中执行，要求 15 分钟内完成 TOTP；免登会话不带强认证，进入审批页时先验证 TOTP，未登记 TOTP 的先登记（第1段第13节第4项）。卡片上不提供审批按钮；
5. **链接过期**：链接有效期 7 天（第13节第7项）；过期后显示“链接已过期”与“登录后打开”，登录后按当前权限打开同一对象。无权限或对象不存在时显示第1段的通用页“无法打开此内容”，不返回标题、目标归属或负责人；
6. **打开后的视角**：信号详情与对象页默认“当前”视角；简报卡片是组装时的快照，打开时信号或公告已更新的，页面按第3段与第4段提示变化（“信号判断后公告已更正”），“信号判断时”视角以信号固定的求值输入与逻辑求值时间 `evaluated_at` 为锚点（第4段 F7）。卡片上的“发现时间”是信号生成时间 `created_at`，与求值时间分别标注；
7. 打开链接按第4段计入对象查看计量；卡片本身的展示不计量。

### F7 即时通知卡片

1. A02 跟进候选按策略 `route`（`notify: { audience: [objective_owner], mode: immediate }`）即时发给目标负责人，使用与简报信号卡片相同的模板、按钮与动作规则（F3–F5）；复核候选与观察按 `digest` 只进入简报；
2. 即时通知按 [channels 4.5](../../03-architecture/subsystems/channels.md#45-通知合并) 按收件人合并，遵守安静时段（F2 第2条）；
3. 已即时通知、在下一期简报组装时仍待处理的信号，照常出现在简报中并标“已通知”，不重复推送信号卡片（只在总览中列出）。

### F8 Web“今日简报”与重新推送

1. 导航“今日简报”列出本人的简报历史（按周期，新到旧），每期显示周期、组装时间、各区条目数、推送状态（已送达 / 渠道已接受 / 推送失败，已在站内 / 未推送：空简报、成员无绑定）；
2. **完整简报**（Web 与 H5）：按区展示全部条目（受配额，F1 第9条），每条有与卡片相同的动作。页面同时显示两条时间轴并标明：条目内容是“组装时（07:30）”的快照；每条的当前处理状态（“王磊已于 08:12 忽略”“已转跟进”）按“当前”叠加显示，并写明“状态为当前”；
3. **重新推送**：本人可对本期简报点“重新推送到企业微信”（例如推送失败、或误删消息），产生一次新的投递，不重新组装简报；推送前按 F2 第5条再检查。新卡片使用新的动作令牌，新令牌上的点击是新的操作，按第3段的版本与状态规则重新判断：请求的值已成立为无变化；之前的动作已撤销或被他人改过的，新操作照常执行，可能成功；内容版本已变的为 `SIGNAL_UPDATED`。不假定结果总是无变化。只能重新推送当日一期（第13节第11项）；
4. 简报历史、完整简报与投递记录只属于本人，其他成员与管理员看不到他人的简报内容；管理员在“设置 / 渠道”只看到投递统计与失败原因，不含条目。

### F9 偏好

成员在“个人设置 / 简报与通知”中设置：发送时间（整点或半点，06:00–10:00）、时区（默认租户时区）、发送日（默认周一至周五）、安静时段（默认 21:00–07:00）、空简报是否推送（默认否）、各目标区条数（在 APP-TENDER 声明的范围内）。修改从下一期生效（F1 第2条），写入偏好版本；简报记录所用的偏好版本。

## 5. 业务与权限规则

| 规则 | 说明 |
|---|---|
| 简报不是排名 | 按目标分区，区内按该目标的排序分；不同目标的排序分不混排、不合成总排名；简报不是 Top-K 评估列表，配额与截断不改变 Top-K 的样本与口径 |
| 每人一份，按本人权限 | 简报按收件人组装，目标区只给有 `can_view_signals` 的目标；组装、推送与每次重试前都再检查成员、绑定与权限；通知受众不能超出访问权限（[customer-context 第11节](../../03-architecture/subsystems/customer-context.md#11-分派配置)） |
| 卡片动作与 Web 同一接口 | 反馈与撤销调用 detection 的 `TriageSignal` / `UndoSignalTriage`，跟进调用 pursuit 的 `CreatePursuit`；授权、版本、无变化、冲突与撤销的规则全部沿用第3段与第6段，渠道不另作判断 |
| 动作再次授权 | 令牌只是按钮的引用；执行时身份来自渠道回调中的点击者账号与有效绑定，以点击者当前权限实时检查；令牌绑定收件人，转发后由他人点击被拒绝 |
| 操作与尝试分开 | 一次点击是一个操作（令牌标识即操作标识），最多提交一次；每次调用业务接口是一次尝试，有自己的幂等键；暂时失败用新幂等键、同一操作标识重试 |
| 组合动作逐项 | “不相关 + 忽略”按反馈与处理状态两个部分分别判断、分别显示结果；“无变化”按实际值判断，任一部分改变即为成功 |
| 撤销恢复操作前的值 | 卡片撤销按原操作实际改变的部分恢复操作前的值，带版本保护；撤销是新的操作 |
| 渠道内无高影响动作 | 审批、策略激活、调整处置、批量反馈、联系人使用都回到 Web；强认证动作要求 15 分钟内的 TOTP，免登会话不带强认证 |
| 简报不是对外发送 | 简报只发给本租户已绑定的成员本人，不属于“对外发送”；对外发送（向外部协作者或外部邮箱）只发往白名单并留审计，联系人使用仍需审批（[identity 7.3](../../03-architecture/subsystems/identity.md#73-高影响动作与审批)），均不在本段 |
| 渠道只有绑定的成员 | 未绑定、绑定失效中或已失效的渠道账号只收到绑定引导，回调中的任何动作都不执行、不返回业务内容（第1段第5节） |
| 租户隔离 | 动作令牌、简报、投递记录只属于一个租户与一名成员；他租户或他人的标识与不存在的返回相同结果，不泄露标题与归属 |
| 展示级别 | 卡片与简报中的字段按来源权利逐维取最严格的展示级别；只允许引用与链接的只给链接 |
| 缓存与每次检查 | 简报内容是按收件人裁剪后的快照，只存在本人的简报记录中，不跨成员、不跨租户复用；打开链接时按第4段 F2 第5条在每次响应现场检查授权、覆盖、权利与配额，不因卡片已展示而放宽（[安全与租户第3节](../../03-architecture/06-security-and-tenancy.md#3-隔离层次)） |
| 时间带时区、标明时间轴 | 周期、组装时间、发现时间、截止时间都保留精度与时区；简报内容按“组装时”，状态叠加按“当前”，信号解释按信号的求值时间，每处标明 |
| 未知不显示为空 | 金额未公布、品类未能识别、来源中断、目标未激活、无权限分别说明，不以空列表或零代替 |
| 审计 | 卡片动作（含被拒绝的）、撤销、重新推送、偏好变更与绑定相关拒绝写审计，记录渠道、令牌、操作标识与结果 |

## 6. 状态

```text
一期简报（幂等键：租户 + 成员 + 简报来源 + 周期起止）：
  待组装 ──组装──► 已生成（全部区正常 / 部分区不可用 / 空）
  已生成 ──推送──► 投递中 ──► 已送达（渠道接受；渠道支持时记录已读）
                        └──► 推送失败 ──退避重试──► 已送达 / 已在站内（重试截止后）
         └──空简报且偏好不推送 / 成员无有效绑定──► 未推送（只在 Web 与站内）
  已生成 ──重新推送（本人，当日）──► 新的一次投递（不重新组装）

一区（每期）：正常 / 空（原因）/ 来源中断（截至时间）/ 暂不可用（窗口顺延到下一期）/ 目标未激活

动作令牌（= 操作标识）：
  有效 ──点击──► 执行中 ──► 成功 / 无变化 / 确定失败（令牌作废，结果固定）
                       └──► 暂时失败（令牌仍有效，可再次尝试）
  有效 ──到期──► 已过期（之后点击返回“卡片已过期”，指向 Web）
  有效 ──操作开始前被拒绝（验签、他租户、绑定无效、非收件人）──► 仍有效（只拒绝该次调用并审计，不固定结果）
  投递重试：同一张卡片、同一批令牌；重新推送：新卡片、新令牌（新的操作）

卡片上的一个动作（按部分）：
  反馈：未变 / 已写入；处理状态：未变（无变化）/ 已改变 / 不适用（已关闭）
  已提交且有部分改变 ──撤销（10 分钟内，整项一起提交）──► 已撤销（全部部分）/ 未撤销（任一部分 CONFLICT，或 SIGNAL_UPDATED、SIGNAL_CLOSED；各部分保持当前值）

回调：收到 ──验签失败 / 重放──► 丢弃（计入渠道健康）
      收到 ──验签通过、首次──► 1 秒内确认 ──► 异步执行
```

## 9. 异常、重试与撤销

| 情况 | 处理 |
|---|---|
| 简报已生成、推送失败 | 简报不重新组装；投递按渠道退避重试，每次重试前按 F2 第5条再检查；当日 18:00 前仍失败则停止渠道重试，简报留在 Web 与站内，历史显示“推送失败，已在站内”与原因（第13节第11项）；本人可“重新推送” |
| 渠道接口超时，不知道是否已送达 | 视为未确认，按同一投递重试，重试发送同一条消息（卡片与令牌不变）；渠道支持重复消息检查时开启，避免重复送达；即使重复送达，两张卡片上的同一按钮是同一个令牌、同一个操作，只执行一次，再点返回已固定的结果 |
| 本人重新推送 | 新的投递、新的令牌；新令牌上的点击是新的操作，按当前的内容版本与状态判断，可能成功、无变化或被拒绝（F8 第3条） |
| 操作开始前的拒绝（验签失败、回调重放、他租户、绑定无效、非收件人、令牌过期） | 只对这一次调用生效并写审计；不消耗令牌、不固定结果，收件人之后照常执行（F5 第7条） |
| 渠道回调重放、验签失败 | 丢弃并计入渠道健康，不改变任何状态；同一回调多次到达只执行一次（F5 第2条） |
| 组装失败（整期） | 按幂等键重试组装；推迟到当日 12:00 之后仍未成功则当日不推送，下一期各区窗口顺延（F1 第5条）；组装晚于计划时间但在 12:00 前成功的，推送标“延迟发送（原定 07:30）” |
| 某一区取数失败或来源中断 | 该区写明原因与截至时间，其他区照常；该区窗口顺延到下一期，补齐的信号在下一期出现 |
| 卡片动作时信号已更新 | `SIGNAL_UPDATED`，整个动作不执行；附按新版本渲染的卡片（F4 第10条） |
| 卡片动作时信号已关闭 | 反馈照常写入，处理状态部分不适用，卡片说明关闭原因与发现时间 |
| 卡片动作时同事已处理 | 已忽略：本人反馈照常写入，状态无变化；已转跟进：“跟进”返回已有跟进；“不相关 + 忽略”时的处理状态部分按第13节第6项 |
| 卡片动作时失去权限 | `FORBIDDEN`，卡片显示“你已没有该目标的反馈权限”，不显示其他信息 |
| 绑定失效、成员已退出 | 回调只回复绑定引导，不执行、不显示业务内容；排队中的推送在发送前检查时取消 |
| 令牌过期 | 卡片显示“卡片已过期，请在 Web 中处理”与链接；不执行 |
| 暂时失败 | 自动以新幂等键、同一操作标识重试最多 3 次；仍失败时卡片提示可再点，再点仍是同一操作 |
| 撤销被拒 | 任一部分之后被人（含本人）改过：整项不撤销（`CONFLICT`），各部分保持当前值并显示；内容已更新或已关闭：整项不撤销并说明 |
| 卡片更新失败 | 另发一条结果消息；动作结果不受影响 |
| 渠道异常（整个企业微信应用） | 当期简报改投站内，管理员渠道页显示原因；恢复后不补推已过期的当日简报（第1段第9节），历史中可查看 |
| IdP 或渠道网页授权不可用 | 卡片动作仍可执行（不依赖免登）；打开链接转登录页并说明原因 |

## 10. 非功能要求

- 简报在计划发送时间后 5 分钟内完成平台提交（p95），单租户 500 名成员时组装与提交 p95 ≤ 10 分钟；
- 卡片回调 1 秒内确认；卡片动作从点击到卡片显示结果 p95 ≤ 3 秒（不含渠道平台耗时）；
- 投递与卡片动作按渠道与租户限流，遵守企业微信的频率限制；超限时排队，不丢弃；
- H5 完整简报在 375 像素宽度、企业微信内置浏览器中可完成查看与全部卡片动作；
- 简报、投递、动作令牌与偏好为租户私有数据；跨租户与跨成员负向用例覆盖简报历史、完整简报、令牌执行、重新推送与偏好接口（[安全与租户第9节](../../03-architecture/06-security-and-tenancy.md#9-安全测试要求)）。

## 11. 埋点

记录租户、成员、渠道、简报期、区、动作、耗时、结果与原因码：每期推送的平台提交、渠道接受与阅读（或以打开与动作近似，标明近似）三段；从推送到首个动作的时长；卡片动作的结果分布（成功、无变化、各确定失败原因、暂时失败）；撤销次数；卡片过期后点击的次数；截断发生的字段与次数；空简报与部分简报的期数；重新推送次数与原因。重点看业务开拓者从收到简报到处理完简报中 A02 信号的总耗时，以及经卡片提交的反馈占全部反馈的比例。

## 13. 已确认事项

以下事项由项目负责人 Sean 于 2026-10-19 确认（[PR #23 决策记录](https://github.com/SuperAILabs/MiaoQia/pull/23#issuecomment-6258408070)），附带的约束来自同一 PR 的技术评审。第6项中“同一信号已有跟进时返回已有跟进”的复用语义由第6段收口，第6段交付前卡片不显示“跟进”按钮。

| # | 事项 | 确认方案 | 理由 |
|---|---|---|---|
| 1 | 企业微信推送的形式 | 每期一张总览卡，加每个目标区前 3 条的信号卡片，合计最多 6 张；其余在完整简报中 | 只发总览卡时销售要多一步才能反馈；每条一张卡会刷屏。前 3 条覆盖多数日子的高分信号，6 张上限防止多目标时刷屏 |
| 2 | 每区条数 | A02 默认 10 条，成员可在 5–20 条之间调整；“待我处理”不设上限 | 试点目标每天约 5–20 条信号，10 条覆盖多数日子；超出的从“另有 N 条”进入收件箱，不会丢失 |
| 3 | 空简报是否推送 | 默认不推送到企业微信，只保存到历史；成员可开启 | 没有新信号的日子推送一条空消息是打扰；有来源中断时不算空简报，照常推送提示，避免“没消息”被误读为“没机会” |
| 4 | 发送时间、发送日与安静时段 | 工作日 07:30（成员时区，默认 Asia/Shanghai）；安静时段 21:00–07:00，期间所有简报与通知延后；M2 不处理法定节假日与调休 | 07:30 在上班路上可处理；A02 是供货机会，不存在需要夜间叫醒的时限。节假日可由成员临时改发送日，规则化随后续版本 |
