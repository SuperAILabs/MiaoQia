# PRD 第6段：跟进

> 状态：设计交接通过 · 版本：1.2 · 更新：2026-10-19 · 负责人：产品负责人、客户智能负责人、招投标领域负责人 · 原型：[prototypes/06-pursuit-follow-up.html](prototypes/06-pursuit-follow-up.html)

本段让销售团队把值得做的 A02 信号变成有负责人、有截止时间、有结果记录的跟进：从信号（Web 详情或企业微信卡片）或对象页创建跟进，指派与改派负责人，安排任务与提醒，公开截止时间变化时任务自动改时，结束时记录结果、金额与获知时间，结果进入本租户的评估。它承接第3段（信号与处理状态）、第4段（对象页）与第5段（卡片上的“跟进”与“待我处理”），是首条旅程的最后一段。

本段是 [pursuit 第10节](../../03-architecture/subsystems/pursuit.md#10-分阶段交付)的 M2 最小跟进切片：交易型跟进没有阶段编排、默认研究、决策门与路径衔接（M4），领域事件只处理截止时间变化，其他事件只通知负责人；持续型跟进只做跟踪计划与变化简报（周期研究随 M3）。

## 1. 用户与目标

| 用户 | 角色 | 本段要完成的事 |
|---|---|---|
| 销售 | 业务开拓者 `business_developer`（目标参与人） | 从信号创建跟进，成为负责人，安排任务，到期处理，结束时记录结果（◐） |
| 销售负责人 | 决策者 `decision_maker` | 把跟进分派或改派给团队成员，看全部跟进与结果，接手无有效负责人的跟进 |
| 项目推进者 | `pursuit_lead` | 作为负责人或协作者推进，更新任务与结果（◐） |
| 研究分析者、业务专家 | `research_analyst`、`domain_expert` | 查看跟进 |
| 租户管理员 | `admin` | 只查看本人参与的跟进（◐） |

权限依据 [identity 7.2](../../03-architecture/subsystems/identity.md#72-权限矩阵)：从信号创建跟进需目标上的 `can_assign`（决策者 ✓，业务开拓者 ◐）；查看跟进需 `can_view`；更新任务、截止时间与结果需跟进上的 `can_edit`；指定负责人与协作者需 `can_manage_team`。M2 没有外部协作者（受限视图随 M4）。

**成功标准**：业务开拓者从一条 A02 跟进候选在 30 秒内建好跟进（企业微信卡片上一次点击，或 Web 上选负责人与第一项任务）；每个进行中的跟进都有有效负责人与下一个截止时间；到期提醒只触发一次；关闭的跟进都带结果、原因与获知时间，金额区分已发生、估计与客户自报。

## 2. 范围

| M2 包含 | 不在 M2 |
|---|---|
| 交易型跟进：从信号（Web、企业微信卡片）或对象页手动创建；一个目标对象同时只有一个进行中的跟进 | 阶段、任务模板、决策门、默认研究、路径衔接（M4） |
| 负责人与协作者；改派；成员退出后的“无有效负责人” | 外部协作者与受限视图、对外发送（M4） |
| 任务：标题、负责人、截止时间（保留精度与时区）、提醒；可绑定公开截止时间 | 任务模板与依赖关系（M4） |
| 公开截止时间更正、延期与撤回后绑定任务自动改时；其他推进相关事件只通知 | 按结果发布、终止等事件推进状态（M4 通用挂钩） |
| 关闭并记录结果：结果、原因代码、金额条目、获知时间与渠道；修订结果追加记录 | 复盘（M4）；CRM 同步（M5） |
| 撤销刚创建的跟进（Web，第13节第3项） | 重新打开已关闭的跟进（第13节第10项） |
| 简报“待我处理”中的到期任务；提醒卡片上的“完成”（第13节第11项） | 渠道内改派、关闭跟进 |
| 持续跟踪（最小）：跟踪计划、暂停 / 恢复 / 停止、按周期请求变化简报 | 持续跟踪的周期研究与期间对比报告（M3） |
| Web 与响应式 H5 | 跟进看板的拖拽与自定义视图（随工作台统一列表组件，M2-P12） |

## 3. 前置条件

- 第3段：信号、处理状态与状态版本、`TriageSignal` 的组合动作语义；第4段：对象页“本租户”分区；第5段：卡片动作令牌、`ExecuteAction`、简报“待我处理”区；
- `customer-context` 的分派规则给出候选负责人（[customer-context 第11节](../../03-architecture/subsystems/customer-context.md#11-分派配置)）；
- `identity` 的 `can_assign`、`can_view`、`can_edit`、`can_manage_team` 与参与关系写入；
- `domain-intelligence` 的采购项目截止时间（`deadline`，含类型、精度与原始时区）与 `tendering.deadline.changed.v1`；`detection.pursuit_related_event.v1`；
- APP-TENDER 交付 A02 跟进的结果类型与原因代码、金额类型（第13节第8项）；
- `pursuit` 的持久化定时器（Temporal），进程重启后提醒不丢失（[pursuit 第8节](../../03-architecture/subsystems/pursuit.md#8-伸缩与可靠性)）。

## 4. 主流程

### F1 创建跟进

1. **入口**：
   - 第3段信号详情的“跟进”（Web 与 H5）：打开创建面板，填负责人（默认见第2条）、可选的第一项任务（标题、截止时间、是否绑定公开截止时间）与说明；
   - 第5段企业微信卡片的“跟进”：一次点击创建，负责人为点击者本人，没有任务；截止与任务在 Web 中补充；
   - 第4段对象页“本租户”分区的“手动跟进”：选目标（本人有 `can_assign` 的目标）与对象（采购项目及标包、中标方），没有信号时界面提示“本目标没有这条信号，可报告漏报”（不自动提交，[learning 第11节](../../03-architecture/subsystems/learning.md#11-漏报反馈与诊断)）；
2. **默认负责人**：Web 中默认取信号上的候选负责人（分派规则给出、且仍是目标参与人并有访问）；没有候选或候选无访问时默认本人（第13节第5项）。可改为目标的其他参与人；写入前检查被分派人是租户有效成员且有该目标的访问，无访问的被拒绝，不自动授予权限；
3. **一次创建是一个原子写入**：跟进、负责人、协作者、第一项任务、与来源信号的关联（F2 第5条）以及待同步的授权记录在 pursuit 的一个本地事务中写入，要么全部成功，要么全部不写。identity 中的参与关系（负责人、协作者）不在这个事务里，由授权同步写入（F12）；同步完成前跟进显示“授权同步中”；
4. **依据**：从信号创建的跟进记录信号标识与用户看到的信号内容版本（依据链，[pursuit 4.2](../../03-architecture/subsystems/pursuit.md#42-依据链)）；手动创建的标“手动创建”，可另引用对象页上看到的事实版本；
5. **检查**（任一不通过即不写入）：
   - 实时检查目标上的 `can_assign`；
   - 信号属于本租户与所选目标；信号内容版本与用户看到的一致，否则 `SIGNAL_UPDATED`（与第3段一致，用户看过变化后再确认）；
   - 排除信号不能创建跟进（`NOT_APPLICABLE`），需要跟进时从对象页手动创建（第3段第13节第7项）；已关闭的信号不能创建（`SIGNAL_CLOSED`）；
   - 唯一性按 F2；
6. 成功后：信号详情显示“已转跟进 · 负责人 王磊”与跟进链接（detection 处理关联事件之前显示“已转跟进（处理中）”）；负责人不是本人时，负责人在授权同步完成后收到一次分派通知（F12 第4条）。

### F2 唯一性与“已存在”

1. **跟进的目标对象**：从信号创建时取信号的求值单位与中标方——A02 为（采购项目、标包、中标方）；手动创建时取用户选的对象。**同一目标、同一目标对象同时只有一个进行中的跟进**（第13节第1项）：
   - 同一采购项目被不同目标命中（A01 直接投标与 A02 进入供货）时，各目标各自跟进，互不影响；
   - 同一标包多家中标、每家一条 A02 信号时，每家（中标方）可以各有一个跟进；跟进详情提示“同一标包另有 1 个跟进（浙江某建工 · 负责人 王磊）”；
   - 手动创建与从信号创建按同一目标对象判断：先手动跟进了某标包与中标方，之后该信号到达并点“跟进”，得到已有的那个跟进，并把该信号关联到它（第5条）；
   - 已关闭的跟进不占用唯一性：同一目标对象可以再次跟进，新跟进引用上一个（依据链中的前序），第13节第10项；
2. **已存在时的结果**：`CreatePursuit` 发现同一目标与目标对象已有进行中的跟进时不创建，返回“已存在”与该跟进（标识、负责人、创建时间）。“已存在”是成功的一种，不是错误：请求来自一条尚未关联到该跟进的信号时，结果为“已存在 · 已关联”（新增了关联，见第5条，是一次改变）；该信号已关联、或请求不带信号时，结果为“已存在”（无改变）；调用方看到的文案是“已有跟进：王磊 10-20 08:12 创建”并链接过去。调用者无权查看该跟进时只返回“已有跟进，负责人 王磊”，不返回其他内容；
3. **已存在时请求中的其他内容**：请求中的负责人、任务与说明都不写入已有跟进（不静默改派、不追加任务），界面提示“你填写的负责人与任务没有写入，可在已有跟进中修改”；
4. **并发创建**：Web 上甲与企业微信卡片上乙同时为同一目标对象创建，pursuit 以（租户、目标、目标对象、进行中）唯一约束保证只有一个成功创建，另一个得到“已存在”（同一信号时已由胜出者关联，为无改变）与胜出者的跟进；两者各自的结果固定在各自的操作标识上；
5. **信号与跟进的关联**：信号与跟进之间的关系由 pursuit 拥有的**关联记录**表示（关联标识、跟进、信号、建立时所见的信号内容版本、建立方式与操作标识、状态：有效 / 已解除）。从信号创建跟进时在同一事务中建立关联；“已存在 · 已关联”时只新增关联记录，负责人、任务与说明都不变。同一跟进与同一信号只有一条有效关联（唯一约束），重复请求不新增、不再发事件。建立关联时检查与创建相同（`can_assign`、信号内容版本、非排除、未关闭）。每条新关联由发件箱发布 `pursuit.pursuit.signal_linked.v1`，detection 据此把信号转为已转跟进（F3 第1条）；pursuit 不为已有跟进再发一次 `pursuit.pursuit.created.v1`。关联的建立在 pursuit 本地事务提交时完成；信号显示为已转跟进在 detection 处理该事件后完成，之前显示“已转跟进（处理中）”。发布或消费失败按发件箱与消费者的退避重试，超过上限进入死信并告警，可人工重放；detection 以关联标识幂等。M2 不单独撤销一条关联：关联只随跟进的撤销创建一起解除（F3 第4条）。

### F3 信号的“已转跟进”与相关动作

1. **转跟进**：detection 按信号维护**有效关联集合**（关联标识与跟进标识），由 `pursuit.pursuit.signal_linked.v1` 加入、`pursuit.pursuit.signal_unlinked.v1` 移除，以关联标识幂等：
   - 集合从空变为非空时，记录**转换基线**（转换前的处理状态与人工处置），把信号改为已转跟进，并记下转换写入后的状态版本 V；这是系统写入，状态版本递增。同一信号已被忽略、已调整处置时同样转为已转跟进；信号已关闭时只记录关联，状态保持已关闭；
   - 集合非空时再加入关联，只记账，不改状态、不覆盖基线、不递增状态版本；
   - 移除一条关联只移除它自己；集合变空时，如果信号的状态版本仍等于 V（转换之后没有关闭等其他状态变化，关联记账不算），恢复基线，否则保持当前值；之后清除基线；
   - 已移除的关联标识保留记录，晚到的同一关联的加入或移除事件不再生效；事件 `id` 去重之外，以关联标识判断；
   - 不依赖跨跟进的事件顺序：例如跟进 P1 撤销后立即为同一信号创建 P2，P2 的关联事件先于 P1 的移除事件到达时，集合为 {P1, P2}，基线保持 P1 转换前的值；P1 的移除到达后集合为 {P2}；之后撤销 P2，集合变空、状态版本未变，信号回到最初的待处理；
2. **已转跟进信号上的第3段动作**（第13节第4项）：
   - 反馈（相关、不相关）照常写入，按人保存；
   - 忽略、恢复、调整处置的处理状态部分为不适用（`NOT_APPLICABLE`），不改变已转跟进；
   - 组合动作逐部分判断：“不相关 + 忽略”在已转跟进的信号上，反馈部分写入，处理状态部分不适用，整项结果为成功（“已记录你的反馈；该信号已转跟进（王磊负责），状态不变”）；本人反馈已是请求的值时整项为无变化；
   - 批量中混入已转跟进的信号，按上一条逐项给出结果；
3. **关闭跟进不改信号**：跟进关闭后信号仍为已转跟进，详情显示跟进的结果；
4. **撤销创建**（Web，第13节第3项）：创建者在创建后 10 分钟内，且跟进创建后没有任何其他改动（跟进版本仍为创建时的版本：没有改派、没有新增或修改任务、没有关闭、没有新的信号关联）时，可点“撤销创建”：
   - 跟进转为“已撤销”（保留记录，不计入跟进统计与结果覆盖，不再出现在列表中），已建的任务与提醒一起取消，它的全部有效关联解除，期望的参与关系清空；这些在 pursuit 的一个本地事务中提交，identity 中参与关系的撤回由授权同步完成（F12），之前跟进已不接受任何操作；
   - 每条解除的关联发布 `pursuit.pursuit.signal_unlinked.v1`，detection 按 F3 第1条移除关联；信号只在不再有其他有效关联、且状态版本未变时回到转换基线，否则保持当前值，撤销结果中说明（例如“跟进已撤销；信号已关闭，状态不恢复”）；
   - 跟进版本已变化（有人改过，包括之后有另一条信号关联到它）时整项不撤销（`CONFLICT`），显示当前跟进；
   - 企业微信卡片上的“跟进”不提供撤销（第5段第13节第6项）；卡片创建的跟进可在 Web 的同一 10 分钟内撤销；
   - 撤销是新的操作，有自己的操作标识；撤销不能再撤销。负责人已收到的分派通知不撤回，另发一条“跟进已撤销”。

### F4 负责人、协作者与改派

1. 每个进行中的跟进有一名负责人，可有协作者（目标参与人）；负责人与协作者经授权同步获得跟进上的参与关系（F12）；
2. **改派**（`can_manage_team`）：选新负责人并写原因（可选）；写入前检查新负责人的成员状态与目标访问；原负责人失去“分派给我”的视图（如果不是协作者），仍可按角色权限查看；改派在 pursuit 本地立即生效：原负责人此后不能再以负责人身份操作，新负责人在授权同步完成后才能操作并收到一次通知（F12）；审计记录前后负责人；
3. **无变化**：改派给当前负责人、添加已是协作者的成员，为无变化，不写记录、不发通知；
4. **并发**：跟进有版本，改派、任务与关闭都带所见版本；请求的效果已成立为无变化，否则版本不一致时返回 `CONFLICT` 与当前值（“李娜于 09:10 已改派给 王磊”），不覆盖；
5. **无有效负责人**：负责人停用或退出租户（`identity.member.changed.v1`）后，跟进标“无有效负责人”，其任务提醒改发给目标所在范围的决策者（[pursuit 第10节](../../03-architecture/subsystems/pursuit.md#10-分阶段交付)），列表置顶；决策者改派后恢复。负责人失去目标访问时同样处理。

### F5 任务、截止时间与提醒

1. **任务**：标题、负责人（默认跟进负责人）、截止时间、说明、状态（待办 / 已完成 / 已取消）；
2. **截止时间保留精度与时区**：可只填日期，或精确到分钟；保存所填时区（默认填写人的时区）。只填日期的截止是该日期在所填时区的当日结束前；显示时按查看者时区换算，与原时区不同时同时显示原值（“10-25（Asia/Shanghai）”“10-25 17:00 UTC+08:00 / 18:00 UTC+09:00”）；
3. **绑定公开截止时间**（可选）：任务的截止时间可绑定目标对象的某个公开截止时间（如投标截止 `bid_submission`），显示“随公开截止时间：投标截止 10-25 09:30 UTC+08:00”，精度与时区取公告的原值；A02 的结果类信号通常没有公开截止时间，此时不可选；
4. **提醒**（第13节第6项）：精确到分钟的截止，提前 24 小时与到期时各提醒一次；只填日期的截止，在负责人时区的前一日 09:00 与当日 09:00 各提醒一次；逾期后次日 09:00 再提醒一次，之后不再重复。提醒发给任务负责人，遵守其安静时段（第5段 F2 第2条）；
5. **提醒只触发一次**：每次提醒的幂等键为任务 + 截止时间版本 + 提醒种类；截止时间改变后取消旧提醒、按新时间重建；进程重启后定时器不丢失；
6. **完成与取消**：完成或取消任务带所见版本；已完成的再完成为无变化；完成后 10 秒内（Web）或 10 分钟内（卡片）可撤销，恢复为完成前的状态（待办）与完成前的截止和提醒，版本保护同第3段 F9；
7. **修改截止时间**：手工修改写原因（可选），审计记录前后值；修改绑定任务的截止时间即解除绑定（提示“将不再随公开截止时间变化”）。

### F6 公开截止时间变化

1. pursuit 消费 `detection.pursuit_related_event.v1` 中由截止时间变化引起的事件（`tendering.deadline.changed.v1`，或更正公告改变了截止时间）；
2. **绑定的任务自动改时**：按新的公开截止时间更新任务截止，取消旧提醒并按新时间重建，跟进时间线记录“投标截止 10-25 09:30 → 10-28 09:30（更正公告 10-20 发布，10-20 10:05 记录）”，审计记录事件与前后值。提醒只按新时间触发一次；
3. **手工截止不改**：未绑定的任务不改，只通知负责人“公开截止时间已变化：投标截止 10-25 09:30 → 10-28 09:30，你的任务截止仍为 10-24”；
4. **撤回与恢复**：改变截止时间的更正公告被撤回时，公开截止时间回到撤回后的业务有效值，绑定任务同样改时并记录；恢复同理。已触发过的提醒不撤回；
5. **晚到与乱序**：事件按事实版本处理，旧版本的事件晚到时不覆盖较新的截止时间（只记录“已忽略过期事件”）；
6. **其他事件只通知**：结果发布、终止、合同公告等推进相关事件在 M2 只通知负责人，不改变跟进状态（M4 通用挂钩）。

### F7 关闭与结果

1. **关闭**（`can_edit`）：选结果类型并填写（第13节第8–9项）：
   - **结果类型**：成功（已进入供货或已签约）/ 失败 / 放弃；
   - **原因代码**：必填，取自 APP-TENDER 的 A02 结果原因；选“其他”须写说明；
   - **获知时间 `known_at`** 与获知渠道（公共公告、妙洽信号、采购人或总包通知、客户内部系统、其他）：成功与失败必填，可只填日期，保存精度与时区；放弃时可不填；
   - **金额条目**（可选，零到多条）：金额类型（本方供货金额、合同金额、预计年采购额等，取自 APP-TENDER）、币种（默认 CNY）、数值（十进制文本，不换算）、取值性质（已发生 `actual` / 估计 `estimate` / 客户自报 `customer_stated`）、来源（公共事实版本、客户文件或口述）。不同性质、不同类型的金额不相加；
   - **事件锚点**（可选）：结果对应的事件与时间，公共事件引用事实版本（如合同公告），客户私有事件记录客户给出的时间与依据；
2. 关闭时取消未完成任务的提醒，任务保持原状态并标“跟进已关闭”；
3. **修订结果**：结果、金额或取值性质变化（估计转为已发生、金额更正、结果撤销）追加新的结果记录，引用被取代的记录并写原因；旧记录保留，详情显示“当前结果”与修订历史（时间轴：记录时间）；
4. **贡献关系**：系统按记录的引用与时间判定：从信号创建、且信号生成时间早于获知时间的标“首次提示”（第13节第12项）；客户可以更正，更正追加记录。贡献关系只说明链上发生过什么，不计算“妙洽带来的金额”；
5. **进入评估**：`pursuit.outcome.recorded.v1` 由 learning 消费，只用于本租户的评估：按 `known_at` 计入时点评估，获知时间缺失的只进入事后统计；修订产生新记录，不改写已发布的报告（[learning 8.1](../../03-architecture/subsystems/learning.md#81-时点正确)）。结果不改变策略、信号或公共事实。

### F8 跟进列表与详情

1. **列表**（“跟进”导航）：我负责的、我协作的、团队的（按权限）、已关闭；每行显示目标对象、目标、负责人、下一个截止（带时区与精度）、状态（进行中 / 无有效负责人 / 已关闭）、最近变化。默认按下一个截止升序，没有截止的排后；
2. **详情**：概要（目标对象、来源信号与当时的内容版本、创建方式与时间）、负责人与协作者、任务、结果、时间线；
3. **时间线的时间轴**：跟进时间线按平台记录时间排列（创建、改派、任务变化、截止变化、关闭、结果修订）；公开截止时间的变化同时显示公告的来源发布时间与平台记录时间；结果显示获知时间、事件时间与记录时间三者；任务按截止时间排列并标明精度与时区；
4. **信号与对象**：从详情打开来源信号（第3段，默认“当前”视角，“信号判断时”以信号的 `evaluated_at` 为锚点，第4段 F7）与对象页；对象页“本租户”分区列出该对象上本人可看的跟进；
5. 展示的公共字段按来源权利的展示级别（第4段第5节）；本租户内容不进入其他租户。

### F9 简报“待我处理”、提醒卡片与跟进入口

1. **待我处理**：第5段简报的“待我处理”区列出分派给本人、未完成、截止时间在下一期简报之前或已逾期的任务，按截止时间排序（带精度与时区），每条链接到跟进详情；无有效负责人的跟进出现在相应决策者的“待我处理”中。取数时点为简报组装时，内容是组装时的快照；
2. **提醒卡片**：到期提醒以企业微信卡片发给任务负责人，按钮为“完成”与“查看”（第13节第11项）。“完成”按第5段 F4–F5 的动作令牌规则执行：令牌标识即操作标识，每次调用 `CompleteTask` 是一次尝试；操作开始前的拒绝（验签、他租户、绑定无效、非收件人、令牌过期）只对该次调用生效并审计，不消耗令牌；投递重试送达的同一张卡片令牌不变，再点返回已固定的结果；提醒重新发送（截止时间改变后重建的提醒）是新的卡片与新令牌；
3. **卡片动作结果**：成功（“已完成：提交报价”）、无变化（已完成）、`CONFLICT`（任务已被改动，显示当前值）、`FORBIDDEN`（已不是负责人）；成功后 10 分钟内可在卡片上撤销；
4. **跟进入口放开**：第3段信号详情与第5段卡片上的“跟进”按钮，在本段的功能验收（第12节）通过后，经发布开关在租户上开启；开启前按第5段第13节第6项不显示。开关开启不改变已有信号与跟进。

### F10 持续跟踪（最小）

1. **跟踪计划**：决策者或业务开拓者为一组组织（竞争对手、目标总包，取自企业清单或手选）创建持续型跟进：名称、对象集合、周期（默认每周一 08:00，负责人时区）、负责人；
2. **生命周期**：建档 → 跟踪中 ⇄ 已暂停；跟踪中或已暂停 → 已停止 → 已归档（[业务架构 4.2](../../02-business/01-business-architecture.md#42-客户生命周期租户域)）。暂停期间不生成变化简报；恢复后从恢复时起的下一周期开始，不补暂停期间的各期；停止不删除已有简报；
3. **每期变化简报**：按周期请求 channels 生成一期变化简报（简报来源为跟进标识，与日常简报分开去重），内容来自 detection 对这些对象的关注变化。每期记录实际期间（左闭右开，带时区）、本期成员快照（期末时点的对象集合与来源版本）与对比基准（上一期）；成员变化后重看旧一期，看到的仍是当期成员；
4. M2 不触发周期研究（随 M3）；单个事项需要推进时，按交易型另建跟进。

### F11 幂等、尝试与撤销（汇总）

1. **操作与尝试**：每个用户意图（一次创建、一次改派、一次完成、一次关闭、一次撤销）有固定的操作标识；Web 中由页面在打开表单时生成，卡片上为动作令牌标识。每次请求是一次尝试，带自己的幂等键，同键同结果；尝试先按操作标识查找已提交的结果，有则直接返回；
2. **暂时失败**：确认未提交的 `INTERNAL`、`UNAVAILABLE` 可用新的幂等键、同一操作标识重试；确定结果（成功、已存在、无变化、`CONFLICT`、`FORBIDDEN`、`SIGNAL_UPDATED`、`SIGNAL_CLOSED`、`NOT_APPLICABLE`、参数校验失败）固定在操作标识上；
3. **“已存在”与“无变化”按实际值判断**：已有进行中的跟进为“已存在”；改派给当前负责人、完成已完成的任务、设相同的截止时间为“无变化”；
4. **撤销恢复操作前的值**：撤销创建（F3 第4条）、撤销完成（F5 第6条）都是新的操作，按原操作改变的部分恢复操作前的值，带版本保护，一项内各部分一起提交、要么全部生效要么全部不生效；跨子系统的派生状态（信号的已转跟进）由关联事件按 F3 第1条的有效关联集合与转换基线恢复，恢复前核对状态版本；identity 中的参与关系由授权同步收敛（F12）；
5. **不提供撤销的**：改派（再改派一次即可）、关闭（修订结果追加记录）、手工修改截止时间（再改一次，历史保留）。

### F12 授权同步

跟进的参与关系（负责人、协作者）的授权权威在 identity（OpenFGA，[identity 7.7](../../03-architecture/subsystems/identity.md#77-列表与过滤)），不能与 pursuit 的数据在一个事务中写入（[集成契约 2.3](../../03-architecture/03-integration-contracts.md#23-跨子系统一致性)）。因此分两步：

1. **本地写入**：创建、改派、协作者变化与撤销创建在 pursuit 的本地事务中写入跟进的**期望参与关系**与参与版本（每次变化递增），并在同一事务中写入发件箱的同步请求；
2. **同步**：同步任务把该跟进在参与版本 N 下的完整期望关系交给 identity 的 `SyncResourceParticipants`；identity 在一次写入中加上应有的关系、删掉多余的关系，只接受比已应用版本更高的 N，同一 N 重复提交返回同一结果。暂时失败按退避重试（1 分钟起，最长间隔 30 分钟）；同步待处理超过 5 分钟告警，超过 24 小时转为失败处理（第6条）；
3. **同步中的可见状态与准入**：已应用版本低于期望版本时，跟进显示“授权同步中”。准入失败关闭：
   - 依赖参与关系的操作（业务开拓者、项目推进者以负责人或协作者身份更新任务、关闭）须同时满足 pursuit 本地的期望关系与 identity 的 `Check`；
   - 新负责人在同步完成前 `Check` 不通过，看到“授权同步中，稍后可操作”；
   - 原负责人在本地期望关系中已不是负责人，即使 identity 中残留旧关系，pursuit 也拒绝其以负责人身份的操作；
   - 按角色范围有权限的成员（决策者）不受影响；
4. **调用的返回与通知**：创建与改派在本地提交后即返回结果，并带授权状态：同步在返回前已完成为“已生效”，否则为“授权同步中”（操作结果仍是已创建或已改派，固定在操作标识上，不会因同步再执行一次）。分派通知、任务提醒与提醒卡片只在该参与版本同步完成后发给新负责人；同步期间到期的提醒在同步完成后发送（已过的只发一次“已到期”）；
5. **撤销创建与同步**：撤销创建在本地提交即生效（跟进不再接受任何操作），期望关系清空并排队同步；identity 不可用时返回“已撤销（授权清理中）”，恢复后删除关系；
6. **永久失败与补偿**：identity 拒绝部分关系（例如被分派人在同步前已退出或失去目标访问）时，identity 应用其余关系并返回被拒的成员；pursuit 把被拒的负责人标为“无有效负责人”（F4 第5条），提醒改发给决策者，并通知操作者。重试超过 24 小时仍未成功时，跟进标“授权同步失败”，通知目标范围的决策者与运营告警，只允许决策者改派或关闭；之后同步成功即恢复。

## 5. 业务与权限规则

| 规则 | 说明 |
|---|---|
| 一个目标对象一个进行中的跟进 | 同一目标、同一目标对象同时只有一个进行中的跟进，pursuit 以唯一约束保证；不同目标、同一标包的不同中标方各自跟进；已关闭的不占用（F2） |
| “已存在”不是错误 | 重复创建返回已有跟进，请求中的其他内容不写入；无权查看已有跟进时只返回负责人姓名 |
| 创建逐项授权 | 创建需目标上的 `can_assign`，改派与协作者需 `can_manage_team`，任务与结果需 `can_edit`，提交时实时检查；被分派人须是租户有效成员且有目标访问，分派不授予权限 |
| 版本绑定 | 从信号创建时带所见信号内容版本，已更新则 `SIGNAL_UPDATED`；跟进的写操作带跟进版本，冲突以 `CONFLICT` 返回当前值 |
| 已转跟进只由关联决定 | 信号与跟进的关联由 pursuit 拥有并以事件通知 detection；detection 按有效关联集合维护已转跟进，基线只在集合从空变为非空时记录一次，最后一条关联解除且状态版本未变时才恢复；忽略、恢复、调整处置在已转跟进的信号上不适用，反馈照常 |
| 授权分步收敛 | pursuit 本地事务只写期望的参与关系与同步请求，identity 的关系经授权同步写入；同步完成前准入失败关闭，原负责人由 pursuit 本地关系拒绝，通知在同步完成后发出（F12） |
| 组合动作逐部分 | 一次请求含多个部分（反馈与处理状态；创建与任务）时逐部分给出结果；“无变化”按实际值判断；撤销一项内各部分一起提交 |
| 时间带精度与时区 | 截止时间、获知时间、事件时间保留所填或原始的精度与时区；只填日期的不补成某个时刻；每个列表与时间线写明时间轴 |
| 金额不相加 | 不同类型、不同取值性质、不同币种的金额分别显示，不相加，不换算成单一价值 |
| 结果只在本租户 | 结果、金额与原因只属于本租户，只用于本租户的评估，不回写公共事实，不用于其他租户的策略（[pursuit 第9节](../../03-architecture/subsystems/pursuit.md#9-安全要点)） |
| 贡献不是归因 | 贡献关系按记录的引用与时间判定，用户可更正，不计算妙洽带来的金额 |
| 租户隔离 | 他租户或不存在的跟进、任务、信号返回相同结果，不泄露标题、负责人与是否存在 |
| 渠道动作同一规则 | 卡片上的“跟进”“完成”调用同一命令、经同一授权；操作开始前的拒绝不消耗令牌；投递重试与重新发送分开（第5段 F5） |
| 审计 | 创建、已存在、撤销创建、改派、协作者变化、任务与截止变化（含自动改时）、关闭、结果修订、贡献关系更正写审计，记录操作者、版本与前后值 |

## 6. 状态

```text
交易型跟进（pursuit 的顶层状态，M2 不细分阶段）：
  （无）──创建──► 进行中 ──关闭（结果）──► 已关闭（成功 / 失败 / 放弃）
           └──撤销创建（10 分钟内且无其他改动）──► 已撤销（不计入统计）
  进行中 ──负责人停用、退出或失去访问──► 进行中 · 无有效负责人 ──改派──► 进行中
  （同一目标、同一目标对象：至多一个进行中；已关闭、已撤销不占用）

授权同步（每个跟进的参与版本）：
  期望版本 N 已写入 ──同步成功──► 已生效（已应用版本 = N）
                   └──暂时失败──► 授权同步中（退避重试；超过 5 分钟告警）──► 已生效 / 授权同步失败（超过 24 小时）
  部分成员被 identity 拒绝 ──► 已生效（其余成员）+ 被拒负责人标“无有效负责人”

创建请求：  成功（已创建）/ 已存在（返回已有跟进，无改变）/ 确定失败 / 暂时失败（可重试）

信号处理状态（detection，派生自跟进）：
  有效关联集合：空 ──关联加入──► 非空（记录转换基线与状态版本 V；待处理 / 已调整处置 / 已忽略 ──► 已转跟进）
  非空 ──再加入或移除一条（仍非空）──► 非空（只记账，状态与基线不变）
  非空 ──最后一条移除──► 空（状态版本仍为 V 时恢复基线，否则保持当前值）
  已移除的关联标识：晚到的加入或移除事件不生效
  已转跟进 ──求值单位终态 / 撤回──► 已关闭
  已转跟进 + 忽略 / 恢复 / 调整处置 ──► 处理状态部分不适用（反馈照常）

任务：  待办 ──完成──► 已完成 ──撤销完成──► 待办
        待办 ──取消──► 已取消
        截止：手工 / 绑定公开截止（随更正、延期、撤回改时）──手工修改──► 手工

提醒（每个任务、截止版本与种类一条）：
  已计划 ──到时──► 已发送（只一次）
  已计划 ──截止改变 / 任务完成或取消 / 跟进关闭──► 已取消（新截止另建）

结果（追加式）：  记录 1 ──修订──► 记录 2（引用记录 1）──► …（当前结果为最新）

持续跟踪：  建档 ──► 跟踪中 ⇄ 已暂停 ──停止──► 已停止 ──► 已归档
```

## 9. 异常、重试与撤销

| 情况 | 处理 |
|---|---|
| 同一目标对象已有进行中的跟进 | 返回“已存在”与已有跟进；请求中的负责人、任务不写入并提示 |
| Web 与卡片并发创建 | 唯一约束只让一个创建成功，另一个得到“已存在”；各自结果固定在各自的操作标识上 |
| 网络超时、响应丢失 | 同一幂等键重发返回该尝试的结果；已提交而响应丢失时返回已提交的结果（已创建），不重复创建 |
| 暂时失败 | 新的幂等键、同一操作标识重试；已提交的不会重复执行 |
| 创建时信号已更新 / 已关闭 / 是排除信号 | `SIGNAL_UPDATED` / `SIGNAL_CLOSED` / `NOT_APPLICABLE`，不创建；排除信号提示从对象页手动跟进 |
| 被分派人无访问或已退出 | 拒绝并说明，不自动授予权限；整个创建不写入 |
| 关联已建立、detection 尚未处理关联事件 | 信号详情以 pursuit 的关联为准显示“已转跟进（处理中）”；此间写入的忽略等动作照常，关联事件到达时信号转为已转跟进，基线记录为当时的实际值 |
| 关联事件发布或消费失败 | 发件箱与消费者退避重试，超过上限进入死信并告警，可人工重放；detection 以关联标识幂等，重放不重复转换 |
| 撤销后立即重建、事件交错 | detection 按有效关联集合处理，不依赖跨跟进的事件顺序；基线不被覆盖，最后一条关联解除时才按状态版本恢复（F3 第1条） |
| 撤销创建冲突 | 跟进已被改动（含之后有信号关联到它）：整项不撤销（`CONFLICT`），显示当前跟进；信号状态版本已变：跟进照常撤销，信号保持当前值并说明 |
| identity 不可用或授权同步失败 | 本地写入照常提交并返回“授权同步中”；准入失败关闭，通知延后到同步完成；超过 5 分钟告警，超过 24 小时标“授权同步失败”并通知决策者（F12） |
| 同步时被分派人已退出或失去访问 | identity 应用其余关系并返回被拒成员；负责人被拒时跟进标“无有效负责人”，提醒转给决策者 |
| 改派、任务、关闭版本冲突 | `CONFLICT` 与当前值；请求的效果已成立为无变化 |
| 负责人退出或失去访问 | 标“无有效负责人”，提醒转给决策者，列表置顶 |
| 提醒投递失败 | 按 channels 的重试与站内兜底；重试发送同一张卡片（令牌不变）；提醒不因投递失败重新计划，截止改变后的新提醒是新卡片 |
| 公开截止事件晚到或乱序 | 按事实版本处理，旧版本不覆盖新值，记录“已忽略过期事件” |
| 公开截止来源中断 | 绑定任务保持最近一次的值，详情显示来源中断起点与“恢复后按最新公告改时” |
| 关闭时缺少必填项 | 不能提交并指出缺少的项；金额条目缺少取值性质或币种时不能保存 |
| 结果写入后 learning 不可用 | 结果照常保存；learning 恢复后按事件补齐（以结果记录标识幂等） |
| 持续跟踪的一期简报生成失败 | 按 channels 的组装重试；当期失败时下一期的实际期间不覆盖失败的那一期，失败期在历史中标“未生成” |

## 10. 非功能要求

- 创建跟进、改派、完成任务 p95 ≤ 1 秒；跟进列表（每页 50 条）与详情 p95 ≤ 1.5 秒；
- 提醒在计划时间后 1 分钟内提交到渠道（p95）；公开截止时间变化后 5 分钟内绑定任务完成改时；
- 提醒定时器持久化，进程重启、部署与故障转移后不丢失、不重复；
- H5 在 375 像素宽度下可完成创建、改派、完成任务与关闭；
- 跟进、任务、结果为租户私有数据；跨租户与无权限负向用例覆盖创建、详情、列表、任务、关闭、撤销、卡片动作与“待我处理”接口。

## 11. 埋点

记录租户、目标、用户、入口（信号详情 / 卡片 / 对象页）、动作、耗时、结果与原因码：从信号生成到创建跟进的时长（按入口与处置分层）、“已存在”的次数与入口、撤销创建次数、改派次数与无有效负责人的时长、任务按时完成率、提醒到完成的时长、截止自动改时次数、关闭时各结果类型与原因分布、结果反馈覆盖（已关闭跟进中有结果与原因的比例）、价值记录完整（金额带取值性质、币种与获知时间的比例）。重点看 A02 跟进候选的转跟进率与跟进关闭时的结果覆盖。

|---|---|---|---|
| 1 | 一个信号 / 采购项目可以有几个跟进 | 同一目标、同一目标对象（A02 为采购项目 + 标包 + 中标方）同时只有一个进行中的跟进；不同目标、不同中标方各自跟进；关闭后可再建 | 同一件事两个负责人会重复联系总包；A01 投标与 A02 供货是不同的生意，同一标包的不同总包是不同的客户，合并反而丢信息 |
| 2 | 已有跟进时 `CreatePursuit` 的结果 | 返回已有跟进，算成功：该信号首次关联到已有跟进时为“已存在 · 已关联”（新增关联，有改变，见 F2 第5条）；已关联过时为“已存在”（无改变）。两种情况下请求中的负责人与任务都不写入并提示；无权查看已有跟进时只给负责人姓名 | 第5段卡片需要确定的回答；静默改派或追加任务会覆盖同事的安排；只给姓名足以协调，又不泄露跟进内容 |
| 3 | 撤销创建 | Web 上创建者 10 分钟内、跟进没有其他改动时可撤销；跟进转为已撤销（保留记录），信号回到转换前；卡片不提供 | 误点“跟进”需要能退回而不留下一个要“放弃”的假跟进；一旦有人改过就说明它已被使用，撤销会抹掉别人的工作 |
| 4 | 已转跟进信号上的忽略等动作 | 处理状态部分不适用，反馈照常；已转跟进只能由撤销创建恢复，关闭跟进不改信号 | 已转跟进说明团队已决定跟进，个人的“不相关”不应把它移出；关闭后信号仍保留“当时跟进过”的事实，便于评估 |
| 5 | Web 创建时的默认负责人 | 分派规则的候选（仍是参与人且有访问）；否则本人 | 分派规则是负责人设的团队分工；候选失效时退回本人，避免默认值导致创建失败 |
| 6 | 提醒时间 | 分钟精度：提前 24 小时与到期；只填日期：前一日与当日 09:00（负责人时区）；逾期次日 09:00 一次 | 覆盖“提前准备”和“当天别忘”；只填日期的不应在半夜或 00:00 提醒；逾期只提醒一次，避免持续打扰 |
| 7 | 公开截止变化时的任务 | 绑定的任务自动改时；手工截止不改、只通知；更正撤回时同样改回 | 与 pursuit 第10节一致；手工截止往往留了提前量，自动改会破坏负责人的安排 |
| 8 | A02 结果类型与原因 | 成功（已进入供货或已签约）/ 失败 / 放弃；失败原因：总包选择其他供应商、价格不具竞争力、品牌或资质不符、联系不上决策人、项目取消或变更、其他；放弃原因：规模太小、回款风险、资源不足、其他。随 APP-TENDER 交付 | 原因要能对应到产品、价格、资质、关系或数据问题，供评估与改进建议使用；与第3段反馈原因分开，因为一个是“值不值得做”，一个是“做的结果” |
| 9 | 关闭时的必填项 | 结果与原因必填；成功与失败必填获知时间（可只到日），放弃可不填；金额可选，填写时取值性质与币种必填 | pursuit 第10节要求 M2 至少记录取值性质、币种与获知时间；不强制填金额，避免为了关闭而编数字 |
| 10 | 重新打开已关闭的跟进 | M2 不支持；结果有变化追加修订，机会复活时新建跟进并引用上一个 | 重新打开会让“结果”与“进行中”交替出现，评估难以按获知时间取值；新建并引用保留了完整的依据链 |
| 11 | 提醒卡片上的快捷动作 | 提供“完成”与“查看”；完成后 10 分钟内可在卡片上撤销；改派、关闭只在 Web | 完成是低风险动作，在卡片上做省一次登录；改派与关闭需要填写原因与结果，适合在 Web 中完成 |
| 12 | “首次提示”的比较口径 | 比较信号生成时间（`created_at`）与获知时间；获知时间只到日且与信号同日时不判定；首次送达时间另行显示 | 生成时间是平台可证明的最早时间；送达受渠道与用户行为影响，可作参考但不作判定，避免以送达失败否定平台的提示 |
| 13 | 持续跟踪是否进 M2 | 进 M2，只做跟踪计划、暂停 / 恢复 / 停止与每周变化简报，对象限组织 | pursuit 第10节已列入 M2 切片；周期研究依赖 M3 研究入口，变化简报复用第5段的简报能力 |
| 14 | 跟进入口何时开启 | 本段功能验收通过后，经发布开关按租户开启；信号详情与卡片同时开启 | 第5段已确认开启前不显示；按租户开启可在试点租户先验证 |

## 附：已知设计缺口

以下缺口在前序段落中发现、不属于本段解决范围，记录在此以便跟踪：

1. **排序列表版本没有所有者**：第5段简报记录“排序列表版本”，但每周 Top-K 列表由谁生成、版本如何定义没有落到 learning 或 detection；
2. **投递幂等键缺少序号**：channels `Delivery` 的幂等键（通知 + 渠道 + 收件人）不能区分重新推送与重新发送的提醒，契约中需要加入投递序号；
3. **企业微信的字段与按钮上限**：卡片字段长度、按钮数量与重复消息检查参数推迟到 M2-P7 由适配器声明；
4. **租户时区没有所有者**：第4、5、6段都使用“租户时区（默认 Asia/Shanghai）”，但 identity 与 customer-context 都没有该字段；本段的截止、提醒与持续跟踪周期同样依赖它；
5. **“首次提示”的送达口径**：pursuit 4.2 只写“以信号时间与 `known_at` 比较”，本段按生成时间判定（第13节第12项），送达时间是否参与需要质量与验收确认。
