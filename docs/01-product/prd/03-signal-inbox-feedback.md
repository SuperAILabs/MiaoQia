# PRD 第3段：信号收件箱与批量反馈

> 状态：设计交接通过 · 版本：1.3 · 更新：2026-10-18 · 负责人：产品负责人、客户智能负责人、招投标领域负责人 · 原型：[prototypes/03-signal-inbox-feedback.html](prototypes/03-signal-inbox-feedback.html)

本段让销售团队每天按目标查看 A02 进入供货的信号，看懂“为什么是这个处置”，并对信号单条或批量反馈“相关 / 不相关”、忽略无关信号。它承接第7段（目标首次激活后才产生信号，首次激活可选回填近 30 天），产出两样东西：团队共享的信号处理状态（第6段从“待处理”的信号创建跟进），以及本租户的反馈集（`learning` 用于 Top-K 精确率、排除正确率等质量评估与改进建议）。反馈不会改变生效策略：策略变化只经第7段的仿真与审批。

## 1. 用户与目标

| 用户 | 角色 | 本段要完成的事 |
|---|---|---|
| 销售 | 业务开拓者 `business_developer`（目标参与人） | 每天处理本目标的新信号：看命中理由，单条或批量反馈，忽略无关信号（◐） |
| 销售负责人 | 决策者 `decision_maker` | 查看目标范围内全部信号，调整处置，看反馈汇总判断是否需要调整策略（第7段） |
| 研究分析者 | `research_analyst` | 查看与反馈目标范围内的信号 |
| 项目推进者 | `pursuit_lead`（目标参与人） | 查看与反馈（◐） |
| 业务专家、租户管理员 | `domain_expert`、`admin`（目标参与人） | 只查看（◐），不能反馈；不是参与人时看不到信号 |

权限依据 [identity 7.2](../../03-architecture/subsystems/identity.md#72-权限矩阵)：查看信号与命中理由需目标上的 `can_view_signals`，反馈、忽略、恢复与调整处置需 `can_feedback`。管理员能查看目标与策略（`can_view`）不等于能看信号（第2段第5节“目标可见性”）。渠道卡片上的快捷反馈（第5段）调用本段同一接口、经同一授权。

**成功标准**：业务开拓者在 10 分钟内处理完一天的 A02 信号（约 20 条），对每条都能说出“为什么是这个处置、哪些项未知”；反馈提交后在本人与同事的收件箱中立即可见，并在下一次反馈汇总中计入；任何反馈都不会悄悄改变策略。

## 2. 范围

| M2 包含 | 不在 M2 |
|---|---|
| 按目标的收件箱：待处理、已处理、已排除、已关闭四个分栏；筛选、排序、游标分页 | 跨目标混排（排序分不可比，[业务不变量第8条](../../02-business/01-business-architecture.md#7-业务不变量)）；团队共享的保存视图（随工作台统一列表组件，M2-P12） |
| 信号详情：处置结论、逐条规则轨迹与未知原因、关键字段依据、版本与更新历史 | Agent 解释与比较多条信号、对选中信号批量发起研究（随 M3 研究入口） |
| 单条反馈：相关 / 不相关（带原因标签）；排除信号的“排除正确 / 排除有误” | 排除信号人工恢复为候选（第13节第7项） |
| 忽略、恢复；单条调整处置（必须写原因） | 批量调整处置（第13节第3项） |
| 批量反馈与忽略：固定选中清单、确认影响、逐项执行与结果、只重试失败项、撤销本次操作 | 批量分派跟进（第6段） |
| 反馈汇总（只读）与“修改策略”入口（第7段） | 由反馈自动生成策略提案或草案（第13节第9项） |
| 报告漏报：记录公共对象、目标与时点 | 漏报的自动诊断（第13节第6项，[learning 第11节](../../03-architecture/subsystems/learning.md#11-漏报反馈与诊断)） |
| Web 与响应式 H5 | 渠道卡片上的快捷反馈（第5段）；信号导出（随导出审批） |

## 3. 前置条件

- 第1段已交付：成员、角色、组织单元可用；
- 第2段已交付：A02 目标、参与人、客户上下文快照；第7段已交付：目标首次激活（激活前不产生信号），可选回填的信号标“回填”；
- `detection` 的 A02 在线匹配、信号存储、`ExplainSignal` 已实现；
- APP-TENDER 交付 A02 的反馈原因标签与信号卡片视图（[M2-P2](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接)，标签建议见第13节第2项）；
- `domain-intelligence` 按信息领域发布服务状态与数据截至时间（`GetCoverage`，M2-P3）；
- 目标、信号的单元级授权与列表过滤运行时接入（M2-P8）；试点来源与品类增强满足 M2-P11（品类增强置信度 ≥ 0.7，否则读取为未知、转复核）；
- 证据查看由第4段提供，本段只提供入口。第4段交付前，详情中的依据显示字段值与原文链接。

## 4. 主流程

### F1 进入收件箱

1. 导航“信号”列出当前用户有 `can_view_signals` 的目标（Web 左栏，H5 顶部下拉），每个目标显示待处理数与数据截至时间。默认进入上次查看的目标；只有一个目标时直接进入。不提供“全部目标”混排；
2. 目标未激活时显示“目标尚未激活，激活后才会产生信号”与第7段入口；目标已停用时显示“已停用，不再产生新信号；已有信号保留，可查看与反馈”；
3. 列表顶部按策略版本启用领域集合内的信息领域分别显示数据截至时间（例如“采购公告截至 10-17 08:40 · 企业数据截至 10-16”）。某个来源中断时显示受影响的领域、区域与中断起点，说明“恢复后自动补齐，补齐的信号标为新到达”。

### F2 浏览与筛选

1. 四个分栏：
   - **待处理**：处理状态为待处理或已调整处置的信号；
   - **已处理**：已转跟进（第6段）、已忽略；
   - **已排除**：处置为排除的信号，默认不出现在待处理中，可查看与反馈；
   - **已关闭**：求值单位进入终态或公告被撤回的信号；
2. 每行显示：项目名称、事实类型（中标结果 / 候选人公示 / 合同公告 / 施工许可）、中标方、金额（注明“中标金额”“合同金额”；未公布显示“未公布”，不用预算或其他金额代替）、地区、品类、处置（人工调整的显示人工处置，小字标系统原处置）、排序分、最多两条命中理由（规则 `say` 文本）、未知项数、发现时间，以及标记：回填、已更新（7 天内有更新）、我已反馈。同一标包多家中标时每家一条信号，行内标“同标包共 3 家中标”；
3. 筛选：处置、地区、品类、金额区间、发现时间、事实类型、我的反馈（未反馈 / 相关 / 不相关）、标记（回填、已更新、有未知项）。默认按排序分降序，同分按发现时间新到旧；可改按发现时间或金额排序。筛选与排序写入链接，打开链接的人仍按自己的权限看到结果；
4. 游标分页，每页 50 条；详情与列表保持上下文（上一条、下一条、返回原筛选）；
5. 有新信号或信号更新时列表不自动重排，顶部提示“有 3 条新信号、2 条已更新，点此刷新”，避免用户勾选时行位置变化。

### F3 查看命中理由

1. 点开信号进入详情（Web 右侧抽屉，H5 新页面），内容来自 `ExplainSignal`（基于信号记录，[策略 DSL 4.3](../../03-architecture/11-policy-dsl.md#43-确定性与记录)）：
   - **结论**：一句话说明处置与原因，例如“跟进候选：硬条件全部满足，得分 75（基础 50 + 已有客户 15 + 大额 10），达到跟进阈值 60”；“复核候选：‘项目标的包含我方产品品类’未能确定，需人工复核”；“排除：中标方是我方主体（SELF_IS_WINNER）”；
   - **规则轨迹**：按硬条件、排除、观察、加分、减分分组，每条显示说明文字、结果（满足 / 不满足 / 未知 / 未生效）与分值。未知写明原因码与文案：`DOMAIN_NOT_ENABLED` 数据未接入（启用领域集合外，本版本不生效）、`FIELD_MISSING` 公告未公布该字段、`BELOW_EVIDENCE` 低于证据门槛（例如中标方识别置信度低于 0.9）、`CATEGORY_UNCERTAIN` 品类未能可靠识别（增强置信度低于 0.7 或模板门槛）、`SELF_NOT_LINKED` 未关联本企业（X-SELF 未生效，第2段 F1）、`HISTORY_INSUFFICIENT` 历史数据不足；
   - **依据**：中标方、金额、标的、地区等关键字段带证据角标，进入第4段对象页与原文定位；
   - **版本与时间**：策略版本（模板版本、启用领域集合）、客户档案上下文版本、事实版本、逻辑求值时间、发现时间。信号由旧策略版本产生时标“按 v3 判断（当前生效 v4），不随新版本重算”；回填信号标“回填”；
   - **更新历史**：每次更新的时间、触发（更正公告、公告撤回、中标方实体合并等）、变化的字段与处置前后；
   - **反馈与处理**：本人与团队成员的反馈（谁、何时、结果、原因、基于的信号版本），处理状态的变化记录；
   - **候选负责人**：分派规则给出的候选只作建议（[customer-context 第11节](../../03-architecture/subsystems/customer-context.md#11-分派配置)）；“跟进”入口随第6段交付出现。M2 不展示研究入口，策略中的自动研究路由不执行；
2. 展示内容受查看者权限与来源权利约束：信号解释组合了多个来源的字段，展示级别逐维取各输入中最严格的结果（[数据架构第12节](../../03-architecture/02-data-architecture.md#12-来源权利与数据权益)），例如某字段的来源只允许引用与链接时，只显示标题与原文链接，并说明原因。

### F4 单条反馈

1. 有 `can_feedback` 的成员在列表行或详情中反馈：
   - **相关**：可选标签“新线索”或“已掌握”；
   - **不相关**：至少选一个原因标签（第13节第2项），选“其他”须填写说明；默认同时“移出待处理（忽略）”，可取消勾选（第13节第1项）；
   - 排除信号上为 **排除正确 / 排除有误**，排除有误须选原因；
2. 提交携带操作标识、请求幂等键和用户看到的信号内容版本（F9）。成功后行内显示“你：不相关 · 品类不符”；同时忽略的移入已处理，并出现 10 秒的“撤销”（按 F9 恢复操作前的值）；
3. 每人对每条信号有一个当前反馈。再次反馈即修改，“撤回我的反馈”即撤回；两者都追加记录，以最新为准。不同成员的反馈各自保存，互不覆盖，团队内能看信号的成员都可见（第13节第10项）；
4. 反馈不改变策略、系统处置、排序分或其他成员的反馈。只有忽略、恢复与调整处置改变团队共享的处理状态；
5. 信号已被忽略时仍可反馈：本人的新反馈照常写入，处理状态不变。

### F5 忽略、恢复与调整处置

1. **忽略**：可单独忽略（不带反馈，质量评估中仍计为“未反馈”）或随“不相关”一起忽略；信号移入已处理，团队共享，记录操作者；
2. **恢复**：已忽略的信号回到待处理；
3. **调整处置**（仅单条，非排除、未关闭的信号）：在跟进候选、复核候选、观察之间调整，必须写原因。保留系统原处置、得分与轨迹，列表与详情同时显示两者。人工调整不触发策略的通知路由（第13节第8项），需要同事跟进时使用第6段的跟进；
4. **并发**：处理状态与人工处置共用一个状态版本，每次改变其中任一项时递增。提交时先看请求的效果是否已经成立：已忽略的信号再忽略、人工处置已是“跟进候选”时再调为“跟进候选”，该项为“无变化”，不写记录、不要求版本一致；效果尚未成立时，所带状态版本必须等于当前版本，否则返回冲突与当前值（“王磊于 09:12 已调整为跟进候选”），不覆盖前者。例如两人基于同一版本分别调为“跟进候选”与“观察”，先提交者成功，后提交者收到冲突；“无变化”按动作实际改变的值判断，人工处置不同即不是无变化，不能只看处理状态都是“已调整处置”。一个动作同时含反馈与状态变化时逐项判断：状态无变化不影响反馈写入。

### F6 批量反馈

1. **选择**：行复选框、“全选本页”、“选择全部 N 条符合筛选的信号”（N ≤ 200，第13节第3项；超过时提示收窄筛选，不截断）。选择后固定为信号标识清单：之后筛选、排序变化或新信号到达都不扩大选中范围；已选但不在当前视图中的项提示“另有 4 条已选不在当前视图”；
2. **动作**：标相关、标不相关（同一组原因，默认同时忽略）、忽略、恢复；排除信号只能批量标“排除正确 / 排除有误”。与动作不适用的信号混选时，确认页列出不适用的条数，这些项的结果为“不适用，未处理”；
3. **确认**：显示数量与影响，例如“将把 23 条标为不相关（品类不符），并移出待处理。其中 3 条你已反馈过，将被修改；2 条已被他人忽略，只记录你的反馈”；
4. **执行**：提交返回批量作业，每个选中项有一个固定的操作标识（批次标识 + 信号标识），逐项执行与单条相同的检查：信号属于本租户与所选目标、实时检查 `can_feedback`、内容版本与选中时一致、处理状态与人工处置按 F5 第4条判断；
5. **结果**：逐项为 成功 / 无变化 / 失败 / 未处理（作业取消或中断时尚未尝试）。一项的结果按它的各部分（本人反馈、处理状态、人工处置）汇总：任一部分发生了改变即为**成功**，并显示哪些部分改变，例如“状态无变化，反馈已记录”（信号已被同事忽略、本次只写入了你的反馈）；请求的效果全部已经成立、没有任何部分改变时才为**无变化**。失败分两类（F9）：**确定失败**（`FORBIDDEN` 无权限、`SIGNAL_UPDATED` 信号已更新、`SIGNAL_CLOSED` 信号已关闭、`NOT_APPLICABLE` 不适用、`CONFLICT` 他人已改变）是该项的最终结果；**暂时失败**（`INTERNAL`、`UNAVAILABLE`，确认未提交）可以重试。汇总显示各类数量，失败项可筛出查看原因；
6. **重试与撤销**：“重试暂时失败项”与“继续未处理项”为这些项发起新的尝试，仍用原操作标识，已提交的项不会重复执行；确定失败的项不在重试中，需重新查看后另行操作。结果页可“撤销本次操作”：撤销范围是本批中已提交且至少有一个部分发生改变的全部项（即全部成功项，含“状态无变化，反馈已记录”的项），每项只补偿它实际改变的部分（F9）；无变化与失败的项不在撤销范围内。撤销同样逐项给出结果。

### F7 反馈汇总

1. 目标的“反馈”标签（`can_view_signals`）显示近 30 天的汇总，原因可点开到对应的信号列表。口径：
   - **窗口**：发现时间在统计截至时间之前 30 天内的信号；这些信号上的反馈不论何时提交都计入，取统计截至时各成员的当前反馈（撤回的不计）；
   - **按当前内容版本计**：只有基于信号当前内容版本的反馈参与下列计数；基于更新前版本的反馈单列为“基于旧版本 N 条”，不计入相关、不相关与反馈率；
   - **反馈率**：分子为至少有一条当前版本相关性反馈的非排除信号数，分母为窗口内的非排除信号数；排除信号另计“已反馈的排除信号 / 排除信号数”；
   - **相关、不相关与分歧**：按信号计，每条信号只计一次。当前版本的反馈全部为相关计相关、全部为不相关计不相关；同时有相关与不相关计为分歧，不计入前两者。比例的分母为相关 + 不相关 + 分歧；排除正确、排除有误与排除分歧同理；
   - **原因分布**：在计为不相关的信号中，按原因标签计信号数（同一信号多人选同一原因只计一次，一条信号可计入多个原因）；
2. 每个原因旁提示可能相关的规则或参数（例如“品类不符 ↔ R-CAT 与品类参数”），只作提示；
3. 固定文案：“反馈只用于评估与改进建议，不会自动修改策略。需要调整时在策略页修改，经仿真与审批后生效。”有 `can_draft_policy` 的成员看到“修改策略”入口（第7段 F2）；
4. 统计由 `learning` 异步汇总，显示统计截至时间；样本少于 20 条时只显示数量，不显示比例（第13节第9项）。

### F8 报告漏报

1. 收件箱提供“报告漏报”（对象页与手动跟进上的入口随第4、6段）；
2. 填写：公共对象（检索项目或公告选择；检索不到时填外部链接与说明）、目标（本人有 `can_feedback` 的目标）、当时时点、说明。时点按用户输入的精度保存并带时区：可精确到分钟（默认取对象的发布时间，含时区），也可只填日期。只填日期时，诊断窗口为该日期在所填时区的 00:00 至次日 00:00，诊断按窗口报告各环节在窗口内的状态与变化时间（例如何时采集、何时生成信号、各次投递结果），不给出某个精确时刻的单一结论，也不视为等同于当天任何一个时刻；
3. 该对象在本目标现有信号（含已排除、已关闭）时，只作关联提示，不判断是否漏报：显示“本目标现有这条信号（10-11 生成，晚于你填写的时点 10-09）”与链接，报告照常可提交。漏报判断的是所填时点当时是否应出现：信号晚于该时点才生成（例如补采后生成），或当时已有信号但没有送达，都可能是漏报（[learning 第11节](../../03-architecture/subsystems/learning.md#11-漏报反馈与诊断)）。报告保存所填时点，并附上关联的信号与投递记录引用；
4. **去重**：每份报告单独保存（报告人、时点、说明、提交时间）。只有诊断输入完全相同时才共用一次诊断：同一目标、同一对象、同一时点（相同精度与时区下的同一时刻；只填日期的，同一日期与时区）。同一天的不同时刻、精确时刻与只填日期的报告都分开诊断：例如 09:00 时对象可能尚未采集，15:00 时已有信号但没有送达，两者需要不同时点的事实、策略、权益与投递记录；
5. M2 只记录漏报（`ReportMiss`），状态“已记录，待诊断”，报告人在“我的漏报”中查看；诊断运行前不显示任何结论。自动诊断在 [learning 第11节](../../03-architecture/subsystems/learning.md#11-漏报反馈与诊断) 的验收用例通过后启用，启用后按报告中的时点补做诊断（第13节第6项）；
6. 漏报不改变策略与信号。

### F9 幂等、重试与撤销

1. **操作与尝试**：用户的每一次意图（一次单条提交，或批量中的一项）有一个固定的操作标识；每次向服务端发出的请求是一次尝试，带自己的幂等键。服务端以操作标识去重：同一操作最多提交一次，提交后的结果（成功、无变化或确定失败）固定在操作标识上；
2. **同键同结果**：同一幂等键的重复请求（例如网络超时后客户端重发）返回该尝试的结果；该尝试已提交而响应丢失时，重发得到已提交的结果，不再执行；
3. **新的尝试**：尝试以暂时失败结束且确认未提交（`INTERNAL`、`UNAVAILABLE`）时，该幂等键的结果就是这次失败，不会变；重试使用新的幂等键、同一操作标识，执行前先按操作标识查找，已提交则直接返回已提交的结果。确定失败不能用同一操作标识重试，用户重新查看后的再次提交是新的操作；
4. **取消与继续**：取消批量作业后不再发起新的尝试，进行中的尝试照常结束；尚未尝试的项为“未处理”，“继续未处理项”为它们发起首次尝试；
5. **记录被改变的部分**：每个动作最多改变三个部分：本人的反馈、处理状态、人工处置。系统只为实际改变的部分记录操作前的值、操作后的值和写入后的版本（反馈版本按人与信号计，处理状态与人工处置用状态版本）；无变化的部分不记录；
6. **撤销**：对每个被改变的部分追加一条补偿，未改变的部分不补偿：
   - **反馈**：操作前没有反馈则撤回；操作前有反馈则恢复原来的结果、原因、说明及其所基于的内容版本。例如原为“相关 · 已掌握”，批量改为“不相关 · 品类不符”后撤销，恢复为“相关 · 已掌握”；
   - **忽略**的反向是回到操作前的处理状态（待处理，或带原人工处置的已调整处置）；**恢复**的反向是重新忽略；**调整处置**的反向是恢复原人工处置，原来没有人工处置时回到待处理；
   - **版本保护**：每条补偿执行前核对该部分的当前版本仍等于原操作写入后的版本，不一致说明之后有人（包括本人）改过，该项不撤销，结果为 `CONFLICT` 并显示当前值；
   - **内容与关闭**：原操作之后信号内容已更新，该项不撤销（`SIGNAL_UPDATED`），由用户看过变化后自行操作；信号已关闭，该项不撤销（`SIGNAL_CLOSED`）；
   - 撤销范围按项确定：已提交且至少一个部分发生改变的项都在范围内，只有部分改变的项也不能遗漏；一项内各部分的补偿一起提交，要么全部生效，要么全部不生效。撤销本身是新的操作，有自己的操作标识，同样逐项给出结果；撤销不能再撤销。

## 5. 业务与权限规则

| 规则 | 说明 |
|---|---|
| 按目标查看 | 收件箱一次只看一个目标；信号随目标授权，按 `can_view_signals` 判断，不逐条授权。目标列表用 `ListPermitted` 求出有 `can_view_signals` 的目标（[identity 7.7](../../03-architecture/subsystems/identity.md#77-列表与过滤)） |
| 反馈逐项授权 | 反馈、忽略、恢复、调整处置需 `can_feedback`，在提交时实时检查；批量逐项检查。业务专家与管理员只读，看不到反馈入口，直接调用被拒绝。页面打开后权限被收回的，之后的提交被拒绝 |
| 租户隔离 | 不属于当前租户的信号与不存在的信号返回相同结果“信号不存在或你无权查看”，不泄露是否存在；批量中混入的这类标识逐项失败，结果不显示其标题。M2 一个账号只属于一个租户，没有租户切换（第1段第13节第2项） |
| 反馈不改策略 | 反馈进入本租户反馈集，用于质量评估与改进建议，不改变生效策略、系统处置与排序分，不用于其他租户的策略（[learning 第2节](../../03-architecture/subsystems/learning.md#2-职责与非职责)）。策略变化只经第7段仿真与审批 |
| 反馈不改事实 | “公告信息有误”等反馈只进入本租户反馈集，不修改公共事实（[业务不变量第12条](../../02-business/01-business-architecture.md#7-业务不变量)）；用户发现的数据问题经支持渠道报告 |
| 未反馈不等于相关 | 查看、点击、停留都不当作反馈；未反馈的信号在质量评估中计为未反馈（[质量与验收第10节](../../05-delivery/02-quality-and-acceptance.md#10-指标执行口径)） |
| 个人反馈、共享状态 | 反馈按人保存；处理状态与人工处置属于信号，团队共享，带状态版本，并发修改以冲突返回 |
| 版本绑定 | 每次反馈与处理状态变化记录用户看到的信号内容版本；提交时内容版本已变化的被拒绝，用户看过变化后重新确认（第13节第5项）。已有反馈在信号更新后保留，标“基于更新前的版本” |
| 更正、撤回与合并 | 求值单位状态变化导致重新求值时更新原信号、追加更新记录，不新建信号；公告被撤回时信号转为已关闭并说明撤回原因与发现时间；已忽略信号遇到更新时的处理见第13节第4项。A02 结果公告被更正时的重新求值见第13节第11项 |
| 已有信号不重算 | 策略激活与回滚只影响之后的求值；已有信号保留产生时的策略版本与解释（第7段第5节） |
| 未知如实显示 | 规则结果为未知时显示“未知”与原因，不显示为满足或不满足；未知的硬条件按 `missing` 进入复核（[策略 DSL 4.2](../../03-architecture/11-policy-dsl.md#42-处置决策)） |
| 派生可见性 | 解释与列表中的公共字段按来源权利与暴露配置展示，多来源组合时逐维取最严格的结果；权益或权利变化后不可见的内容不再展示，信号与反馈保留 |
| 幂等 | 所有写操作带幂等键，同键同结果；同一用户意图有固定的操作标识，以操作标识去重，暂时失败的重试使用新的幂等键（F9），重复点击与重试都不产生重复记录 |
| 撤销只恢复本操作改变的部分 | 撤销按部分恢复操作前的值，以版本保护，不覆盖之后的任何修改（F9） |
| 审计 | 忽略、恢复、调整处置、批量作业与撤销写审计，记录操作者、信号版本与原因；反馈记录本身追加保存 |

## 6. 状态

```text
处理状态（团队共享）：
  待处理 ──调整处置──► 已调整处置（跟进 / 复核 / 观察）──调整为另一处置──► 已调整处置
     │                     │
     ├──忽略──► 已忽略 ◄──忽略──┤
     │           └──恢复──► 待处理（有人工处置时回到已调整处置）
     └──创建跟进（第6段）──► 已转跟进
  任一状态 ──求值单位终态 / 公告撤回──► 已关闭
  （处理状态与人工处置共用状态版本，任一项改变即递增；“无变化”按两者的实际值判断）

信号内容：  已生成 ──重新求值──► 已更新（追加更新记录，内容版本 +1；处置可能变化）

个人反馈：  未反馈 ──反馈──► 相关 / 不相关（原因）/ 排除正确 / 排除有误
                     └──修改或撤回（追加记录，以最新为准；反馈版本按人与信号递增）

批量作业：  已提交 ──► 执行中 ──► 完成 / 部分成功 / 失败
                         └──取消──► 已取消（未尝试的项为未处理）

批量中的一项（操作标识固定）：
  未处理 ──尝试──► 成功 / 无变化 / 确定失败（最终）
                 └──► 暂时失败（未提交）──新的尝试──► …（按操作标识去重，最多提交一次）

撤销（逐项，按被改变的部分补偿）：
  已提交的操作 ──撤销──► 已撤销 / 未撤销（CONFLICT、SIGNAL_UPDATED、SIGNAL_CLOSED）

漏报：      已记录，待诊断 ──诊断启用后──► 诊断中 ──► 已诊断 / 暂不能诊断
```

## 9. 异常、重试与撤销

| 情况 | 处理 |
|---|---|
| 提交时信号已更新 | 拒绝（`SIGNAL_UPDATED`），详情刷新为新版本并高亮变化，用户重新确认；批量中该项为确定失败，不在重试中 |
| 两人同时改变处理状态或人工处置 | 请求的效果已成立为“无变化”；否则版本不一致的后提交者收到冲突（`CONFLICT`）与当前值，不覆盖（F5 第4条） |
| 网络超时、响应丢失 | 客户端用同一幂等键重发：已提交则返回已提交的结果，未提交则返回该尝试的结果（F9） |
| 暂时失败（`INTERNAL`、`UNAVAILABLE`，未提交） | 页面保留已选内容；重试是新的尝试（新幂等键、同一操作标识），已提交的不会重复执行 |
| 批量部分失败 | 逐项结果；只重试暂时失败项、继续未处理项；确定失败项需重新查看后另行操作 |
| 批量作业取消或中断 | 已尝试的项保留结果，未尝试的项为“未处理”，可继续 |
| 撤销 | 单条 10 秒内、批量在结果页撤销；按被改变的部分追加补偿，恢复操作前的值；之后有人（含本人）改过、内容已更新或信号已关闭的项不撤销并说明（F9） |
| 权限在操作中被收回 | 之后的提交逐项被拒绝（`FORBIDDEN`）；已打开页面刷新后不再显示信号 |
| 信号已关闭（终态或撤回） | 不能忽略、恢复或调整处置；仍可反馈相关性，反馈标注信号已关闭 |
| `learning` 暂不可用 | 反馈照常提交（写入 detection 的处理记录），反馈集与汇总在事件处理恢复后补齐，汇总显示统计截至时间 |
| 来源中断 | 列表与详情可用，显示受影响领域与截至时间；恢复后补齐的信号作为新信号到达 |
| 解释加载失败 | 显示信号基本信息与“命中理由暂不可用，可重试”，不显示猜测的理由；反馈入口仍可用 |

## 10. 非功能要求

- 收件箱列表（每页 50 条）与信号详情 p95 ≤ 1.5 秒；单条反馈 p95 ≤ 1 秒；200 条批量作业 p95 ≤ 30 秒；
- 新信号与更新提示在信号生成后 1 分钟内出现；反馈汇总在反馈提交后 5 分钟内计入；
- 收件箱 H5 在 375 像素宽度下可完成筛选、查看理由、单条与批量反馈；
- 信号、处理记录、反馈、批量作业与漏报为租户私有数据，跨租户负向用例覆盖列表、详情、解释、单条与批量反馈、汇总与漏报接口。

## 11. 埋点

## 13. 已确认事项

以下事项由项目负责人 Sean 于 2026-10-18 确认（[PR #21 决策记录](https://github.com/SuperAILabs/MiaoQia/pull/21#issuecomment-6252412982)），附带的约束来自同一 PR 的技术评审。

| # | 事项 | 确认方案 | 理由 |
|---|---|---|---|
| 1 | “不相关”是否默认同时忽略 | 默认勾选“移出待处理”，可取消 | 销售标不相关后通常不想再看到；保留取消，让想留给同事复核的人不必再点恢复 |
| 2 | A02 反馈原因标签 | 不相关：品类不符、不在服务区域、规模太小、中标方不做此类采购或无法接触、中标方是我方或关联方、时机已过（材料已采购）、公告信息有误、与其他信号重复、其他（须说明）；相关：新线索、已掌握（可选）；排除有误：中标方并非我方主体、名单已过时、其他。随 APP-TENDER 交付（M2-P2） | 每个标签都能对应到规则、参数、清单或数据质量中的一处，便于汇总提示和后续提案；“已掌握”区分“相关但不新”，避免误计为不相关 |
| 3 | 批量上限与动作范围 | 单次最多 200 条；批量只做相关、不相关、忽略、恢复与排除反馈，不批量调整处置 | 200 条覆盖试点目标约 1–2 周的信号量且能在 30 秒内完成；调整处置要逐条写原因，批量写同一原因会稀释其作为评估依据的价值 |
| 4 | 已忽略的信号遇到更新 | 处置上调（向跟进候选方向）或中标方、金额、品类被更正时回到待处理并标“已更新”；其他更新保持已忽略。已有反馈保留并标“基于更新前的版本” | 更正可能让不相关变成相关，静默留在已忽略会漏掉机会；只按影响判断的变化重开，避免反复打扰 |
| 5 | 提交时信号内容已更新 | 拒绝并要求重新确认，不按旧版本静默接受 | 反馈要作为评估标签，必须对应用户实际看到的内容；拒绝的代价只是多看一眼 |
| 6 | 漏报的 M2 范围 | M2 只记录，状态“已记录，待诊断”；诊断在 learning 第11节验收用例通过后启用，按报告时点补做。为此 detection 的候选与匹配记录从 M2 首次激活起保留至少 180 天 | 诊断依赖采集、归并、权益、候选与投递多个所有者的时点查询，M2 不全部就绪；诊断按当时版本回放，晚做不影响结论，前提是记录保留 |
| 7 | 排除信号能否人工恢复为候选 | M2 不能，只能反馈“排除有误”；确需跟进时从对象页手动创建跟进（第6段） | 排除来自客户自己的名单与本企业关联，反复误排除应修正名单或档案；保持排除规则权威，也保证“排除正确率”的口径干净 |
| 8 | 人工调整处置是否触发通知 | 不触发策略的通知路由，也不改变排序分 | 通知受众与方式由策略决定并经审批；人工上调需要同事跟进时用跟进的指派与提醒，避免绕过策略 |
| 9 | 反馈如何进入策略改进 | M2 只提供只读汇总（近 30 天，少于 20 条不显示比例）与“修改策略”入口，不自动生成提案或草案 | 一个目标同时只有一份草案（第7段），自动生成可能占用或覆盖成员的草案；试点期反馈量小，人看汇总后修改更可靠 |
| 10 | 反馈在团队内是否可见 | 能看信号的成员都能看到彼此的反馈（人、时间、结果、原因） | 团队分工处理同一目标，看到同事“已掌握”“不相关”能避免重复跟进；反馈不含信号外的私密信息 |
| 11 | A02 结果公告被更正时的重新求值 | A02 结果视图增加以更正公告为触发、读取应用更正后的结果；实现前，详情在发现针对该结果公告的更正时显示“该结果已有更正公告，本信号按原公告判断，请核对”并链接更正 | A02 视图以单条结果公告为求值单位，目前只在首次发布时求值（[视图目录](../../../packs/application_domains/tendering/policy/views.yaml)），中标方或金额被更正不会更新信号；改变视图属于应用领域包，不在本段直接修改。本项确认的是方向：视图的正式修订与投影实现作为应用领域包的后续交付，交付前不宣称已支持；实现前的提示依赖在实现验收中验证 |
