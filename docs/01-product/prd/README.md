# 首条客户旅程功能 PRD

> 状态：评审中 · 版本：2.2 · 更新：2026-10-19 · 负责人：产品负责人、设计负责人、首席架构师

M2 的验收单位是首条客户旅程（建材供应商 A02 进入供货）**逐环节可运行、可解释、可验证**，不是文档数量。本目录按旅程顺序逐段交付功能 PRD、低保真原型和接口说明，每段评审通过后交给实现。PRD 的必备结构与原型状态要求见[产品需求落地规格第3节](../05-product-requirements.md#3-每个功能prd的必备产出)，阶段门禁见[阶段基线 M2-P1](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接)。

## 2. 每段的“可运行、可解释、可验证”

每段 PRD 的验收一节必须分别写明三项，评审按这三项关闭：

| 维度 | 含义 | 证据 |
|---|---|---|
| 可运行 | 真实客户角色在目标环境里完成本段主流程，前一段的产出是本段的输入 | 一次完整走查记录：环境、账号角色、操作步骤、结果截图 |
| 可解释 | 用户在界面上能看懂“为什么是这个结果”：状态、原因、数据截至时间、下一步，失败和不可用都有原因 | 原型中每个状态的文案，以及对应的原因码 |
| 可验证 | 主流程、权限与异常有可自动执行的用例，含跨租户与无权限的负向用例 | 验收用例清单与测试位置 |

## 3. 交接规则

- **PRD 与子系统规格的分工**：PRD 写用户可见的流程、规则、状态、文案与验收；数据所有权、实体与接口语义以子系统规格为准。PRD 新增或改变实体、命令、事件时，同一 PR 同步修改对应子系统规格，不在 PRD 中另建一套定义；
- **接口**：PRD 列出本段用到的命令、查询与事件，以及 Web BFF 的读取需要。机器可读的 OpenAPI 与事件契约在该段开始实现时写入 `contracts/`，与生成代码和契约测试一起评审，按冻结规则管理版本；
- **原型**：低保真可交互原型放在 [`prototypes/`](prototypes/)，每个页面能切换[必备状态](../05-product-requirements.md#3-每个功能prd的必备产出)（不适用的状态写明原因）。高保真设计由设计团队在原型评审后产出，不改变 PRD 已确认的规则；
- **待决事项**：PRD 中凡是由编写人选定的默认做法，集中列在“待决事项”一节，评审时逐条确认或改写；确认后改名为“已确认事项”，注明确认人与日期；
- **两个关闭点**：“设计交接”指 PRD、原型与子系统规格评审通过、允许实现；“功能验收”指实现后 PRD/原型版本、产品评审、用户任务观察、验收用例执行结果与缺陷处置记录齐备（[产品需求落地规格第4节](../05-product-requirements.md#4-指标与验收证据)）。文档与原型不能代替后者的证据，PRD 中的用例在执行前是待实现清单；
- **可追溯**：验收一节用表格把每条用例对应到它覆盖的流程或规则、原型状态和证据位置，权限、恢复、同步失败与时效边界都要有用例；
- **安全语义先定**：身份验证、授权、失效与失败处理的语义在设计交接时确定，不推迟到写契约时；
- **“不适用”要按实际流程**：原型中标为不适用的状态必须说明在该页面的真实流程中为何不会出现；原型的状态切换不代替完整任务流程的走查；
- **同步修改**：修订时同时更新 PRD、相关子系统规格、原型、验收用例及受影响的上层文档。
