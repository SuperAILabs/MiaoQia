# PRD 第7段：策略编辑、仿真与审批

> 状态：设计交接通过 · 版本：1.1 · 更新：2026-10-17 · 负责人：产品负责人、客户智能负责人、身份与安全负责人 · 原型：[prototypes/07-policy-simulation-approval.html](prototypes/07-policy-simulation-approval.html)

本段让决策者把第2段启用的 A02 目标从“未激活”变成“生效”，并在之后安全地调整它：在表单里修改策略草案，系统用历史公告仿真出“改了以后会多出、少掉、变了哪些信号”，申请人凭仿真报告提交激活申请，另一位有批准权的成员强认证后批准，系统才激活新版本。回滚走同样的申请与批准。旅程上，本段的首次激活发生在第2段之后、第3段之前：激活前目标不产生信号，激活后第3段的收件箱才有内容。

## 1. 用户与目标

| 用户 | 角色 | 本段要完成的事 |
|---|---|---|
| 销售负责人 | 决策者 `decision_maker` | 修改草案、查看仿真、提交激活或回滚申请；批准他人提交的申请 |
| 销售 | 业务开拓者 `business_developer`（目标参与人） | 起草与仿真（◐）、提交申请（◐），不能批准 |
| 客户 IT 或负责人 | 租户管理员 `admin` | 查看目标与策略、批准激活与回滚；不起草策略 |

权限依据 [identity 7.2](../../03-architecture/subsystems/identity.md#72-权限矩阵) 与 [7.3](../../03-architecture/subsystems/identity.md#73-高影响动作与审批)：起草与仿真需 `can_draft_policy`，提交申请需 `can_request_activation`，批准需 `can_approve_activation`（目标所在范围的决策者或租户管理员）。申请人不能批准自己的申请。提交申请与批准都是强认证动作（[第1段 F3](01-login-and-channel-binding.md#f3-登录与强认证)）。

**成功标准**：决策者能在一次会话内读懂仿真报告并提交首次激活；审批人不离开审批页就能判断“批准后每周大约会收到多少信号、哪些规则因数据未接入不生效、和当前版本相比变了什么”；任何激活与回滚都能追溯到申请人、批准人、仿真报告与策略版本。

## 2. 范围

| M2 包含 | 不在 M2 |
|---|---|
| 策略页：生效版本、草案、版本历史与规则级差异 | 自然语言调优（随 M3，[路线图](../../05-delivery/01-roadmap.md)） |
| 表单编辑：模板参数、非锁定规则的启停、加减分权重、处置阈值、通知受众与方式 | 追加规则与直接编辑表达式（高级模式，随 M4 策略实验室） |
| 保存即编译与校验，草案保存后自动仿真 | 影子与比例灰度、在线效果对比（随 M3 扩展仿真） |
| 最小确定性仿真报告：固定数据集、处置分布、与生效版本的差异、代表样本、逐条规则命中与未知比例 | 仿真结果的通过阈值（监测层阈值在 [M2-P10](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接) 冻结前，报告只作审批依据，不自动判定通过） |

| 首次激活可选回填近期公告 | 决策审批与审批额度（随判断审批 PRD） |
| 模板新版本与信息领域上线时的“可升级”提示与升级草案 | 渠道内直接批准（渠道只通知并跳转 Web） |

## 3. 前置条件

- 第1段已交付：成员、角色、组织单元、TOTP 与强认证可用；
- 第2段已交付：目标已启用并有首版策略草案，客户上下文快照可读；
- `learning` 的最小仿真可运行，固定数据集来自 M1 已启用来源的公共事实（[M2-P6](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接)）；
- `identity` 的审批服务与 `identity.approval.*` 事件已实现（M2-P6）；
- `domain-intelligence` 按信息领域发布服务状态，供启用领域集合与“数据未接入”标示（M2-P3）。

## 4. 主流程

### F1 查看策略

1. 目标页的“策略”标签显示：生效版本（版本号、模板版本、启用领域集合、激活时间、申请人与批准人）、当前草案（如有）及其仿真与申请状态、版本历史；
2. 规则按子句分组（硬条件、排除、观察、加分、减分），每条显示 `say` 文本、用到的档案字段或清单、所需数据可用性，与第2段规则预览一致。启用领域集合外的规则标“数据未接入，本版本不生效”；
3. 任意两个版本可对照：规则级差异（新增、删除、启停、权重、参数、阈值、通知）与各自的仿真报告。

### F2 编辑草案

1. 有 `can_draft_policy` 的成员点“修改策略”，基于生效版本（首次激活前基于首版草案）打开草案。每个目标同时只有一份草案，带乐观并发版本号，两人同时编辑时后提交者收到冲突提示与差异；
2. 可修改的内容：
   - **参数**：模板声明的参数，按参数 Schema 校验。带 `default_from` 的参数默认“随档案”，可改为档案的子集（第2段已确认事项第2项）；
   - **规则启停**：非锁定规则可停用、重新启用；锁定规则不显示开关。停用硬条件时页面提示“停用后不再以此条件过滤，信号数量可能大幅增加”，仿真报告与审批页高亮该变化；
   - **权重**：加分、减分规则的权重为 1–50 的正整数（第13节第5项），服务端按模板约束校验；
   - **阈值**：`base_score`、`pursue_at`、`drop_below`，须满足 `drop_below < pursue_at`；
   - **通知**：各处置的通知受众（目标负责人、全部参与人、某个角色）与方式（即时、汇入简报）。受众只能是目标的参与人或目标范围内的角色，不能引入目标外成员（[customer-context 第11节](../../03-architecture/subsystems/customer-context.md#11-分派配置)）；
3. 保存时 `customer-context` 合成完整策略文档并编译：表达式类型、规则数与成本上限（[策略 DSL 第8节](../../03-architecture/11-policy-dsl.md#8-限制与安全)）、参数约束。编译失败时逐条指出原因，草案保存但标“未通过校验”，不能仿真；
4. 编译通过后运行模板样例：样例的期望处置与草案结果不一致时列出，作为仿真报告的一部分提示，不阻止保存（租户调整阈值可能有意改变样例结果）；
5. 每次保存形成草案的新修订，发布 `customer_context.policy.drafted.v1`，`learning` 据此自动仿真。放弃草案即删除，不影响生效版本。

### F3 仿真

1. 仿真异步执行，草案页显示排队、运行中、完成、失败；一份报告固定对应一份草案修订与一个对比版本，草案再保存，或目标的生效版本在仿真后发生变化（另一激活或回滚），旧报告都标“已过期”；
2. **启用领域集合在仿真时确定**：按提交仿真时各信息领域的服务状态，确定本草案实际读取的领域集合，与草案一起保存；仿真报告与审批材料引用同一集合（[策略 DSL 3.3](../../03-architecture/11-policy-dsl.md#33-模板与租户策略的合成) 第5条）。视图声明的历史窗口在仿真时未覆盖的，在本版本中固定为未知（[M2-P3](../../05-delivery/06-stage-baseline.md#4-m2-前置条件与能力交接)）；
3. **用途与输入**：本仿真是候选变更仿真（反事实），回答“如果当时就按这份草案和现在的档案运行，会产生哪些信号”，结果不是当时实际产生的信号。它与历史实况回放分开：效果评估与漏报诊断按当时生效的策略与上下文回放（[learning 8.1](../../03-architecture/subsystems/learning.md#81-时点正确)）。
   - **两侧共同的输入**：同一公共数据集版本、窗口实际起止、提交仿真时的客户上下文快照版本、逐个被回放事件的逻辑求值时间。公共事实、实体与关系按逻辑求值时间只取当时已可得的版本；报告不使用结果（`Outcome`）标签；
   - **草案一侧**：草案修订的合成文档、模板版本与本次确定的启用领域集合；
   - **对比一侧**：提交仿真时的生效版本，使用它激活时的合成文档与启用领域集合。目标首次激活时没有对比一侧，只给草案一侧的绝对结果；
   - 窗口默认近 90 天（第13节第1项），可得历史不足时按实际可得截断，报告写明实际覆盖起止，不当作完整覆盖；
4. **报告内容**：
   - 用途与输入：标明“候选变更仿真，非当时实际信号”，列出上述固定项与对比版本及其策略代次（首次激活时没有对比版本）；
   - 处置分布：跟进候选、复核候选、观察、排除的数量，并折算为“平均每周”；
   - 差异：相对生效版本新增、移除、处置变化的信号数，各附最多 20 条代表样本（按金额与时间确定性抽样）；
   - 逐条规则：命中为真、为假、未知的比例；未知比例最高的规则与原因（数据未接入、字段缺失、低于证据门槛、未关联本企业等）；
   - 提示：模板样例不一致、停用了硬条件、需复核比例超过一半、窗口内结果为零、历史覆盖不足；
5. 代表样本可点开到对象页与证据（第4段），只展示申请人有权查看的公共事实；
6. 仿真失败（数据集不可用、超时）时报告状态为“失败”并给出原因与重试入口；失败的仿真不能用于申请。

### F4 提交激活申请

1. 有 `can_request_activation` 的成员在报告完成后点“提交激活”。系统核对：报告对应当前草案修订、报告未过期、报告的对比版本仍是当前生效版本、目标没有其他进行中的申请。首次激活时再次提示第2段的未关联本企业、规则数据未接入等情况，不阻断；
2. 申请人填写说明（为什么改、希望审批人关注什么），首次激活时选择是否回填近 30 天（默认勾选，第13节第2项），申请固定回填窗口与范围；
3. 提交需强认证；提交后草案锁定为“待审批”，不能再编辑。需要修改时先撤回申请；
4. `identity` 创建审批请求（类型：策略激活；对象：目标与草案修订；依据：仿真报告；基准：申请时的生效版本与策略代次），发布 `identity.approval.requested.v1`；`channels` 通知目标范围内有批准权的成员（不含申请人）。重复提交（相同草案修订与幂等键）不产生第二个请求。

### F5 审批

1. 审批人从通知或“待我审批”列表进入审批页，看到：申请说明、规则级差异、仿真报告、启用领域集合与“数据未接入”规则、首次激活的回填选择、申请人与提交时间；
2. 批准或驳回都需强认证，驳回必须填写原因。审批人在决定时由 `identity` 实时检查 `can_approve_activation`，申请人本人的批准请求被拒绝；
3. 任一有批准权的成员决定后，请求关闭，其他审批人看到“已由某人处理”；
4. **批准后**：`identity` 发布 `identity.approval.decided.v1`，`customer-context` 校验申请仍对应草案的当前修订、目标的生效版本与策略代次仍等于申请时的基准后，激活为新版本（全量），旧生效版本标“已替代”，发布 `customer_context.policy.activated.v1`。激活提交返回后开始的匹配批次使用新版本（生效边界见第5节）；选择了回填的，`detection` 对回填窗口执行 `RunBackfill`，回填产生的信号标“回填”；
5. **驳回后**：草案回到可编辑状态，保留驳回原因；
6. **失效**：以下情况请求自动失效，草案回到可编辑并通知申请人：超过 7 天未决定（第13节第3项，最长有效期）；申请人失去 `can_request_activation` 或离开租户；同一目标的生效版本在此期间发生变化（例如另一回滚已批准），因为报告的对比基准已不成立；
7. 申请人可在决定前撤回申请。

### F6 回滚

1. 版本历史中，曾经生效过的版本可“回滚到此版本”，默认选上一生效版本；
2. **绑定**（第13节第6项）：回滚申请不绑定草案，绑定三项不可变内容：
   - 目标版本（曾经生效过的版本）；
   - 该版本激活时的仿真报告。审批页注明报告的生成时间，并说明它反映当时的数据，不是当前数据下的新预测；
   - 申请时的生效版本与策略代次，作为基准；
3. **与草案的关系**：
   - 没有草案时，可直接申请回滚；
   - 有草案但没有进行中的申请时，回滚不锁定草案，草案保持可编辑。回滚执行后，草案报告的对比版本不再是生效版本，报告标“已过期”，需重新仿真；
   - 草案已有进行中的激活申请时，不能提交回滚（一个目标同时只有一个进行中的申请），需等它结束或由申请人撤回；
4. **提交与审批**：说明必填；权限、强认证、审批时限与申请人失权失效同 F4、F5。基准变化（生效版本或策略代次与申请时不同）时申请失效。撤回、驳回、失效只关闭回滚申请，不改变草案与生效版本；
5. **执行**：批准后、执行前，`customer-context` 再次核验目标版本存在且曾经生效、生效版本与策略代次仍等于基准，不满足则不执行并通知双方。执行时重新激活该版本：使用它原来的合成文档与启用领域集合，不重新合成模板，不按当前领域状态扩展集合；发布 `customer_context.policy.rolled_back.v1`。已有信号保留产生时的策略版本与解释，不重新求值。

### F7 升级提示

1. **模板新版本**：策略页提示“模板有新版本”，列出模板差异。点“基于新模板创建草案”时按规则 `id` 对齐保留租户的参数与覆盖；新版本删除了被覆盖的规则、或把被覆盖的规则改为锁定时，逐条列出并要求确认。之后按 F2–F5 仿真与审批；
2. **信息领域上线**：草案或生效版本的启用领域集合外的领域状态提升（例如 M3 的 INF-CRED 上线）时，策略页提示“可升级：企业信用数据已接入，P-CREDIT 可生效”。升级即创建新草案，仿真时按当时状态重新确定集合，再按 F4–F5 激活；未升级的版本保持原行为；
3. 升级提示不自动创建草案、不自动激活。

## 5. 业务与权限规则

| 规则 | 说明 |
|---|---|
| 申请与批准分离 | 申请人不能批准自己的申请；授权模型只表达谁有资格批准，分离由 `identity.approvals` 执行。只有一名有批准权成员的企业租户不能自批，须邀请在目标范围内有批准权的成员（第13节第4项） |
| 激活只经审批 | 草案保存、仿真都不改变生效版本；只有批准后由系统执行激活或回滚，任何人不能绕过审批直接激活 |
| 申请按类型绑定 | 激活申请绑定草案修订、该修订的仿真报告，以及申请时的生效版本与策略代次；草案再保存或生效版本变化后，报告过期，需重新仿真与申请。回滚申请绑定目标版本、其原激活报告，以及申请时的生效版本与策略代次，不涉及草案（F6）。两类申请在决定时与执行前都核验基准 |
| 启用领域集合随版本固定 | 集合在仿真时确定并随版本保存；领域上线只提示升级，不改变已激活版本（[策略 DSL 3.3](../../03-architecture/11-policy-dsl.md#33-模板与租户策略的合成)） |
| 生效边界 | 激活与回滚在同一事务中写入新的生效版本并递增目标的策略代次；激活或回滚返回后开始的匹配批次一律使用新代次，`detection` 每批求值前读取当前代次，本地缓存较旧时先重新加载；`policy.activated`、`policy.rolled_back` 事件只用于提前刷新缓存，丢失或迟到不影响正确性。返回前已开始的批次使用旧版本，信号记录所用策略版本 |
| 已有信号不重算 | 激活与回滚只影响之后的求值；已有信号保留产生时的策略版本与解释。需要按新版本处理近期公告时用回填 |
| 一个目标一份草案、一个进行中申请 | 每个目标同时最多一份草案、一个进行中的激活或回滚申请；M2 只有全量激活，没有灰度版本 |
| 通知不扩大权限 | 审批通知只发给当时有批准权的成员；审批人看到的代表样本按其本人权限过滤 |
| 审计 | 草案保存、仿真提交与结果、申请、撤回、批准、驳回、失效、激活、回滚全部写审计，记录操作者、版本与原因 |
| 租户私有 | 草案、报告、申请均为租户私有；仿真只读本租户的上下文与公共事实，不读取其他租户数据 |

## 6. 状态

```text
草案修订：  编辑中 ──保存──► 未通过校验 / 已校验 ──自动仿真──► 仿真中 ──► 仿真完成 / 仿真失败
                               （再次保存：新修订，旧报告“已过期”）

激活申请：  待审批 ──批准──► 已批准 ──系统激活──► 已激活 / 激活失败（基准已变）
               ├──驳回──► 已驳回（草案回到可编辑）
               ├──撤回──► 已撤回（草案回到可编辑）
               └──超时 / 申请人失权 / 生效版本或代次已变──► 已失效（草案回到可编辑）

回滚申请：  待审批 ──批准──► 已批准 ──系统回滚──► 已回滚 / 回滚失败（基准已变）
               └──驳回 / 撤回 / 超时 / 申请人失权 / 基准已变──► 已关闭（草案与生效版本不变）

策略版本：  生效 ──新版本激活──► 已替代 ──回滚到此版本──► 生效
目标（第2段）：未激活 ──首次激活──► 生效
```

## 9. 异常、重试与撤销

| 情况 | 处理 |
|---|---|
| 编译失败 | 草案保存、标“未通过校验”，逐条显示原因；不能仿真与申请 |
| 仿真失败或超时 | 报告状态“失败”并给原因；可重试，相同修订与相同输入的重试复用同一运行，不重复计算 |
| 仿真期间领域状态变化 | 集合已在提交仿真时固定，报告按固定集合完成；状态变化只在策略页提示可升级 |
| 申请提交失败 | 草案不锁定，可重试；同一幂等键的重试不产生第二个请求 |
| 批准后激活失败（例如生效版本已变或草案修订不一致） | 不激活，申请标“激活失败”并通知申请人与审批人，原生效版本不变；不能静默改用其他修订 |
| 审批时权限已变化 | 审批人失去批准权时决定被拒绝；申请人失去申请权时请求失效 |
| `detection` 读取策略代次失败 | 该批求值重试，不用可能过期的缓存求值；超过重试上限进入死信并告警，恢复后重放 |
| 误激活 | 通过 F6 回滚到上一版本；已产生的信号保留，可在收件箱反馈 |

## 10. 非功能要求

- 策略页与审批页 p95 ≤ 1.5 秒；保存草案（含编译与样例）p95 ≤ 3 秒；
- 90 天窗口的单目标仿真在 15 分钟内完成，超过 1 小时判为失败；仿真与在线匹配资源隔离（[learning 第8节](../../03-architecture/subsystems/learning.md#8-伸缩与可靠性)）；
- `GetActivePolicies` 的策略代次读取 p95 ≤ 50 毫秒，detection 每批求值读取一次；
- 草案、报告、申请为租户私有数据，跨租户负向用例覆盖策略、草案、报告、申请与审批接口。

## 11. 埋点

记录租户、用户、动作、耗时、结果与原因码：草案保存次数与校验失败原因、仿真排队与运行时长、报告查看时长、从报告完成到提交申请的时长、申请到决定的时长、驳回原因分布、失效原因分布、回滚次数与距上次激活的时长。重点看首次激活从启用目标（第2段）到激活完成的总耗时。

## 13. 已确认事项

以下事项由项目负责人 Sean 于 2026-10-17 确认（[PR #19 决策记录](https://github.com/SuperAILabs/MiaoQia/pull/19#issuecomment-6235132668)），附带的约束来自同一 PR 的技术评审。

| # | 事项 | 结论 | 约束与理由 |
|---|---|---|---|
| 1 | 仿真窗口 | 默认近 90 天；可得历史不足时按实际可得截断，报告写明实际起止 | 报告展示实际覆盖起止与每周折算口径，历史不足或有缺口时不能当作完整覆盖。中标结果与合同公告按周计数，90 天足以看出每周数量与规则未知比例 |
| 2 | 首次激活回填 | 申请时可选回填近 30 天（默认勾选），审批人可见；之后的激活默认不回填 | 申请固定回填窗口与范围，审批人看到的就是将执行的内容。回填与实时处理重叠的公告按信号幂等键去重，不重复产生信号或通知；部分失败可重试失败部分，不可得的历史在结果中写明。回填信号标“回填” |
| 3 | 审批时限 | 7 天未决定自动失效 | 7 天是最长有效期，不替代基准变化、申请人失权等即时失效条件（F5、F6） |
| 4 | 只有一名有批准权成员的企业租户 | 不能自批；提交时提示“需要另一位决策者或管理员批准”，引导管理员邀请 | 被邀请的人须在该目标范围内有 `can_approve_activation`，仅是“第二位成员”不够。申请与批准分离是 identity 7.3 的既定规则；个人租户的例外不在 M2 |
| 5 | 表单可调范围 | 参数、非锁定规则启停、权重 1–50、阈值（`drop_below < pursue_at`）、通知受众与方式；追加规则与表达式编辑随 M4 策略实验室 | 权重范围、锁定规则与通知受众由服务端按模板约束校验，不靠界面隐藏入口保护 |
| 6 | 回滚是否必须重新仿真 | 不必，附目标版本激活时的报告，按 F6 绑定目标版本与基准 | 审批页注明报告生成时间，说明它不代表当前数据下的新预测；回滚不重新合成模板，已有信号不重算。回滚通常是止损，重新仿真会延迟 |
| 7 | 停用硬条件 | 允许停用非锁定硬条件，差异、仿真报告与审批页高亮 | 模板锁定的规则不能停用或修改；停用业务条件不改变权限与合规限制 |
